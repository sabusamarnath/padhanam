# Architectural Decisions

Append-only log. One entry per decision. Reviewed at phase audits.

Format:
- **Decision N: [name]** (Package P, Session S)
  - Choice: [what was decided]
  - Reasoning: [one or two sentences]
  - Alternatives considered: [if relevant]

## Phase 1 baseline decisions

These were made before Session 1 and form the starting architecture.

- **D1: Tenancy model is database-per-tenant.** Strongest isolation. V1 runs one tenant locally; architecture is forward-built for many.
- **D2: No sub-workspaces inside a tenant in V1.** Tenant is the unit of organization. Workspaces deferred to V2 if needed.
- **D3: Identity is Keycloak in V1 Docker Compose.** Reference open-source IdP, OIDC + SAML + SCIM. ~1GB RAM cost accepted.
- **D4: LLM access via LiteLLM gateway.** No vendor SDKs in domain code. Ollama default in dev.
- **D5: Retrieval is hybrid, configured per agent.** Vector via pgvector and graph via Neo4j, both behind `RetrievalClient`. Strategy fixed at agent config in V1; runtime selection deferred to V2.
- **D6: Orchestration is LangGraph behind `AgentOrchestrator` interface.** CrewAI or custom orchestrators swappable later.
- **D7: Trace store is self-hosted Langfuse 3, behind an interface.** OpenTelemetry GenAI conventions used throughout.
- **D8: V1 metric scope is bounded.** Cache hit rate, output token distribution, context length trajectory, tool call patterns, cost per successful task, latency components decomposed, model substitution similarity scores. New metrics require documented decisions they inform.
- **D9: Optimization output is recommendation-shaped.** Every dashboard view ties to a recommended action.
- **D10: Stack versions pinned.** Python 3.14, Node 24 LTS, Postgres 17 with pgvector, Neo4j 5 Community, Keycloak 26, Redis 7, Vite 6, React 19, React Router 7, FastAPI, SQLAlchemy 2.0 async, LangGraph current, LiteLLM current, Langfuse 3.

## Session decisions

- **D11: Scaffold grows incrementally** (Package P1, Session 1)
  - Choice: Each package adds the Compose services it requires. P1 ships repo structure, charter docs, and structural tooling. Compose at P1 close contains only services exercised by P1 or P2.
  - Reasoning: Big-bang scaffold front-loads complexity before any service has earned a use case, contradicting the learning-sprint framing of Phase 1. Incremental scaffold reaches agent work faster and prevents unused-service drift.
  - Alternatives considered: Big-bang scaffold (Postgres, Neo4j, Keycloak, Redis, LiteLLM, Langfuse all at P1 close). Rejected on learning-value and drift grounds.

- **D12: Jurisdiction is a first-class architectural attribute** (Pre-S2 charter edit)
  - Choice: Tenant context carries jurisdiction from P3 onward. Every component that touches customer data (databases, object storage, identity, trace store, LLM endpoints) is built to be regionally partitionable. Phase 1 deploys a single region; the architecture does not assume a single region anywhere in code.
  - Reasoning: Retrofitting jurisdiction across forty tables and every interface signature later is a quarter of work and a migration risk. Building it in from inception is free at the data-model layer and cheap at the interface layer. The discipline is "by construction, not by policy", which is the framing enterprise procurement and auditors require.
  - Alternatives considered: Treat jurisdiction as a Phase 2 concern and add it when the first non-default-region tenant arrives. Rejected on retrofit-cost grounds.

- **D13: Tenant onboarding is configuration, not deployment** (Pre-S2 charter edit)
  - Choice: Per-tenant decisions (jurisdiction, identity federation, classification policy, model endpoints, retention) live in the tenant registry as configuration. The application reads the registry; no code path hardcodes per-tenant behaviour. Adding a tenant to an existing regional stack is an idempotent provisioning workflow. Adding a region is a separate infrastructure event, scoped explicitly when a customer's residency requirement crosses an existing region boundary.
  - Reasoning: Onboarding through configuration scales; onboarding through deployment does not. The architectural commitment that adding a tenant requires no code changes is what makes the platform sellable to enterprise customers with custom IdP, jurisdiction, and classification requirements. Distinguishing tenant-add from region-add prevents over-claiming.
  - Alternatives considered: Conflate tenant and region provisioning into one workflow. Rejected because they have different actors, different lifecycles, and different cost profiles.

- **D14: Customer-specific behaviour is configuration; capability extensions are bounded** (Pre-S2 charter edit)
  - Choice: The platform exposes parameters, schemas, and tool integration points that cover the large majority of per-tenant requirements. Tools (external services called by the platform on the tenant's behalf) are the primary mechanism for customer-supplied logic and are configuration, not code. Extension points exist for the residual cases where logic must run inside the platform with access to internal state; extensions are versioned, sandboxed, and isolated per tenant, and are bounded to a small named set of interfaces (RetrievalClient, scorer, pre-processor). Forking the platform codebase for customer-specific logic is forbidden.
  - Reasoning: Configuration-only positions cannot survive contact with enterprise customers; codebase-forking destroys the platform. The middle path (configuration first, tool calls for most customer logic, sandboxed extensions for the residue) is the position every mature platform vendor converges on. Setting the boundary now prevents the rot.
  - Alternatives considered: Pure configuration with no extension surface (insufficient for enterprise). Open extension surface with arbitrary plugin points (becomes a fork farm). Rejected.

- **D15: Default development model is Qwen 2.5 7B** (Package P2, pre-S6)
  - Choice: Qwen 2.5 7B served via Ollama is the default model for development and the eval harness baseline.
  - Reasoning: Tool-calling fidelity matters once the agent surface lands, and Qwen 2.5's tool-call behaviour is more reliable than Llama 3.1 at comparable memory cost. Reversible if the eval harness surfaces problems.
  - Alternatives considered: Llama 3.1 8B (conservative default, weaker tool calling). Rejected on tool-call grounds.

- **D16: Codebase structure is bounded contexts on hexagonal, with platform / contexts / shared_kernel separation and import-linter enforcement** (Package P2, pre-S7)
  - Choice: The codebase organizes around bounded contexts at the top level (`contexts/`), with cross-cutting platform concerns (`platform/`), a strictly bounded `shared_kernel/`, and deployable units (`apps/`) that compose contexts and adapters into runnables. Each context internally follows hexagonal layers (`domain/`, `application/`, `ports/`, `adapters/inbound/`, `adapters/outbound/`). Boundaries are enforced by `import-linter` contracts in CI, not by convention. The `shared_kernel/` contains only types that must be referentially equal across contexts (TenantId, Jurisdiction) and forbids Pydantic imports to prevent framework version coupling. Packaging uses uv workspaces, with per-context `pyproject.toml` files added when a context first acquires a third-party dependency that should not bleed across boundaries. The observability split (`platform/observability/` is mechanism, `contexts/observability/` is intelligence) is deliberate: span emission is infrastructure every context uses; trace analysis and recommendation generation are a product feature with their own domain model.
  - Reasoning: Enterprise architecture review requires the answer to "where does retrieval live" to be a single folder, "how is multi-tenancy enforced" to be a build-time invariant, and "how do we swap a vendor" to be a port contract. Organizing by technical layer at the top level fails all three; organizing by bounded context with hexagonal layers within each passes all three. The platform / contexts / shared_kernel split keeps the import graph a DAG. Import-linter turns the architectural rules into CI failures rather than review comments.
  - Alternatives considered: Top-level layered structure (`domain/`, `application/`, `adapters/` at the root). Rejected: scatters each business concern across four directories and produces the modular-monolith-becomes-hairball failure mode. Top-level `ports/` directory. Rejected: ports are owned by the domain that needs them, not global. Pure flat package. Rejected: structurally indefensible at enterprise audit.

- **D17: Contexts communicate via published query APIs for reads and a domain event bus for state changes** (Package P2, pre-S7)
  - Choice: Each bounded context exposes a single `api.py` module at its root containing read-only query methods other contexts may call. State-changing interactions flow through a domain event bus in `platform/events/`: contexts publish events from their domain or application layer, other contexts subscribe through wiring in `apps/`. No context imports another context's internals. The bus is synchronous in-process in Phase 1; the interface is broker-ready so Phase 2 can swap to a real event broker without changing context code. `import-linter` enforces the rule that `contexts/X/*` may import only `contexts/Y/api`, never `contexts/Y/domain` or `contexts/Y/adapters`.
  - Reasoning: "Contexts communicate through ports or shared_kernel" is too vague to defend at audit. The hybrid (queries direct, commands eventful) is the pattern mature platform vendors converge on after the fact and is cheap to adopt now. It reflects Quorum's actual data flow: observability queries trace state on the hot path (read-shaped, latency-sensitive) and reacts to inference completions for recommendation generation (event-shaped, decoupled). Forcing reads through events adds latency without benefit; forcing writes through direct calls couples contexts that should stay separable.
  - Alternatives considered: Direct synchronous calls only (modular monolith, couples deployment). Events for everything (latency on the hot path, no benefit). Rejected on the trade-offs above.

- **D18: Redis is shared between Quorum application use and Langfuse ingestion in development; production Redis topology is deferred** (Package P2, Session 4)
  - Choice: A single Redis instance serves both Quorum application caching and queueing (DB 0) and Langfuse ingestion queueing (DB 1) in the local Compose stack. The configuration interface (per `platform/config/`, landing in S5) is structured so production deployments can resolve Quorum Redis and Langfuse Redis to either the same instance or separate instances by configuration, without code change.
  - Reasoning: Local development cost favours sharing; production posture depends on factors (queue depth, eviction policy compatibility, security boundary requirements) that are not yet known. Forcing a production decision now would commit on missing information. The architecture commits to the configuration interface that defers the decision cleanly.
  - Alternatives considered: Separate Redis instance for Langfuse from inception. Rejected: doubles development cost without benefit at this stage. Shared instance hardcoded with no config swap path. Rejected: forces production into a posture that may not fit.

- **D19: Configuration is read through `platform/config/` exclusively, no direct `os.getenv` or `.env` reads** (Package P2, Session 5)
  - Choice: A single `platform/config/` module is the only place secrets and environment-derived configuration enter the application. Pydantic Settings is the dev-time implementation, reading from `.env`. Production reads from a secret manager via the same `Settings` interface. `import-linter` contract forbids `os.getenv` outside `platform/config/`. Settings classes are per-concern (`InferenceSettings`, `ObservabilitySettings`, etc.), not god-objects.
  - Reasoning: "Secrets in `.env`" without an enforcement mechanism is a development convenience that pretends to be a security posture. The unified config interface is what makes "production swap is configuration not refactor" true on the secrets path. Pydantic Settings is chosen because it composes source priorities (env vars, dotenv, secret-manager-shaped backends) through a stable interface and is well-understood at audit.
  - Alternatives considered: Direct `os.getenv` calls (no enforcement, retrofits expensively). Per-context config modules (fragments the audit surface). Custom secrets layer (reinvents Pydantic Settings poorly).

- **D20: TLS configuration is read through `platform/config/`, dev profile defaults to plaintext for Compose-internal traffic, prod profile defaults to mTLS with no plaintext escape hatch** (Package P2, Session 5)
  - Choice: Every adapter that opens a network connection reads its TLS configuration through `platform/config/`. The dev profile resolves to plaintext for Compose-internal traffic (mkcert TLS at the Caddy edge stays in place). The production profile resolves to mTLS with private CA bundles. There is no code path that bypasses TLS in production; the production profile has no plaintext option.
  - Reasoning: The internal/external network distinction does not survive defence-in-depth review. ISO 27001 Annex A 8.20 explicitly requires controls on internal networks. Forcing TLS configuration through the unified config interface means the dev and production postures are profile selection, not code change.
  - Alternatives considered: Plaintext internal in production (rejected: fails Annex A 8.20). Per-adapter TLS configuration (rejected: fragments the audit surface). Service mesh (deferred: appropriate for production but premature in Phase 1).

- **D21: Field-level encryption uses envelope encryption via `platform/security/crypto.py`** (Package P2, Session 5)
  - Choice: Field-level encryption is implemented in `platform/security/crypto.py` using envelope encryption: a Key Encryption Key (KEK) wraps per-row Data Encryption Keys (DEKs); only DEKs touch field data. Field categories requiring crypto: per-tenant credentials, customer PII, audit log integrity hashes. The dev profile uses a fixed KEK from `platform/config/`. The production profile resolves the KEK to a KMS-managed key. The KMS vendor is deferred until production deployment context exists. Production crypto design is a candidate for explicit external review when production deployment context lands.
  - Reasoning: Disk-level encryption (platform-provided in production) protects against disk theft. Field-level encryption protects against database compromise where the attacker has DB credentials but not application crypto state. SOC 2 confidentiality, ISO 27001 Annex A 8.24, and sector frameworks like HIPAA all require field-level for sensitive categories. Envelope encryption is the standard pattern because it confines KEK use to the wrapping operation, allowing per-row key rotation without rewrapping the entire dataset.
  - Alternatives considered: Direct field encryption with a single key (rejected: no per-row rotation, larger blast radius). Application-transparent encryption via the database (rejected: couples to specific DB vendor and does not protect against DB credential compromise).

- **D22: Audit logging is a bounded context (`contexts/audit/`) with hash-chained append-only storage** (Package P2, Session 5)
  - Choice: Audit is a bounded context, not platform plumbing. `contexts/audit/` contains the domain model (AuditEvent value object, hash-chaining logic), the port (`AuditPort` for emitting events), and adapters. P2 ships with a no-op adapter for use in S6/S7. The real adapter (writing to a tenant-scoped append-only Postgres table with hash chaining) lands in P3 when the tenant registry exists. Schema: actor (user or system), tenant_id, jurisdiction, timestamp, action_verb, resource_type, resource_id, before_state (JSONB), after_state (JSONB), correlation_id, previous_event_hash, this_event_hash. Hash chain provides tamper-evidence: any insertion or modification breaks the chain at and after the affected entry, detectable by chain verification.
  - Reasoning: Audit data is tenant-scoped and has its own domain logic (querying, integrity verification, retention enforcement); it is a bounded context by the same criteria that make observability one. Hash chaining is the lowest-cost tamper-evidence mechanism that provides real audit value; full append-only storage with cryptographic signatures is overkill at this stage and can be added later by extending the chain logic. SOC 2 CC7.2, ISO 27001 Annex A 8.15, and sector framework per-record requirements all converge on this shape.
  - Alternatives considered: Audit as platform plumbing (rejected: tenant-scoping makes it a context). External audit service (rejected: introduces a dependency that does not earn its keep at Quorum's stage). No tamper-evidence (rejected: insufficient for SOC 2 and ISO 27001).

- **D23: Authentication and authorization are platform concerns; no endpoint ships without auth middleware** (Package P2, Session 5)
  - Choice: `platform/security/auth.py` provides the authentication interface. `platform/security/policy.py` provides the authorization interface. Both have dev backends (signed-token AuthN, single-tenant-single-role policy) and Keycloak-shaped production backends stubbed. The FastAPI surface in S7 ships with authentication middleware in front of every endpoint from the first commit. Policy checks gate every tenant-scoped operation. Privileged actions (admin operations, cross-tenant access) emit security events in addition to audit events.
  - Reasoning: Endpoints without authentication middleware ship in development and stay in production. The architectural rule is that the middleware is non-removable, enforced by an integration test that fails if any FastAPI route is reachable without it. Policy-as-code (rather than role-baked-into-handlers) is what makes per-tenant authorization tenable at scale.
  - Alternatives considered: Auth as middleware on a per-router basis (rejected: opt-in security is no security). Authorization in handlers (rejected: scatters the policy surface, fails audit). External authorization service (deferred: appropriate at scale, premature in Phase 1).

- **D24: Tenant isolation is verified by `tests/contract/tenant_isolation/` against every adapter touching tenant-scoped data** (Package P2, Session 5)
  - Choice: Cross-tenant access tests live in `tests/contract/tenant_isolation/`. They are red-team shaped: each test attempts unauthorized cross-tenant access and asserts the access fails. The harness is scaffolded in S5 with one example test against the no-op audit adapter. Every adapter that touches tenant-scoped data must have isolation tests in this directory. CI fails if a tenant-scoped adapter ships without corresponding isolation tests, enforced by a coverage rule (any module under `contexts/*/adapters/` referencing tenant_id must have a test under `tests/contract/tenant_isolation/`).
  - Reasoning: Tenant isolation by assertion is tenant isolation by hope. SOC 2 confidentiality, ISO 27001 Annex A 8.3, and the database-per-tenant principle (D1) all require verification, not declaration. Red-team shaped tests catch the failure mode the architecture is most exposed to: unintended cross-tenant data flow through poorly-scoped queries.
  - Alternatives considered: Manual review only (rejected: not durable). Property-based isolation testing (deferred: complementary, not replacement, and premature at Phase 1).

- **D25: Supply chain hardening: image digest pins, dependency lockfiles, vulnerability scanning, SBOM, scheduled monitoring of high-velocity dependencies** (Package P2, Session 5)
  - Choice: Container images pin to SHA256 digests in `compose.yaml` and any production manifests. Python dependencies pin via uv lockfile (lands in S7 with the FastAPI skeleton). Vulnerability scanning runs via `make scan`: Trivy against pulled images, `pip-audit` against Python deps. CI fails on critical CVEs (severity threshold configurable, default critical-only). SBOM generation is scaffolded as a Make target in S5 and emits real SBOMs from S7 onward. Scheduled dependency monitoring for high-velocity dependencies is part of supply chain hygiene; the first instance is monthly Langfuse patch checking, established at S4 close. Scheduled checks open digest-bump PRs with changelog excerpts and breaking-change flags; the operator reviews and merges; no auto-merge. Local CI runs via `make scan`; remote CI deferred to first remote deployment.
  - Reasoning: ISO 27001 Annex A 8.30 (outsourced development), 8.8 (vulnerability management), and SOC 2 CC8.1 (change management) all converge on supply chain controls. Digest pinning prevents image-tag mutation attacks and forces explicit upgrades. SBOMs are increasingly expected by enterprise procurement. Scheduled monitoring catches version drift before it becomes a CVE response.
  - Alternatives considered: Tag pinning only (rejected: tags mutate). External SCA service (deferred: appropriate at scale, premature now). No SBOM (rejected: enterprise procurement increasingly requires). Auto-merging dependency updates (rejected: removes operator judgment from a security-relevant change).

- **D26: Security events log separately from application logs via `platform/observability/security_events.py`** (Package P2, Session 5)
  - Choice: `platform/observability/security_events.py` provides a `SecurityEventLogger` interface. Event categories: auth_failure, authz_denial, config_change, tenant_scope_violation, privileged_action. Local backend writes structured JSON to `logs/security.jsonl` (separate from application log path, gitignored). Production backend ships to a SIEM, vendor deferred. Every auth middleware execution, every policy check, every audit log write also emits a security event for the corresponding category when applicable.
  - Reasoning: Application logs and security events have different lifecycles (application logs rotate, security events retain), different consumers (operators vs. security analysts vs. auditors), and different requirements (verbose vs. structured-and-filtered). Conflating them produces logs that are too verbose for SIEM and too sparse for debugging. SOC 2 CC7.2/CC7.3 and ISO 27001 Annex A 8.16 both require dedicated security monitoring.
  - Alternatives considered: Single log stream with severity tagging (rejected: SIEMs do not consume well, retention policies conflict). External security event service (deferred: appropriate at scale).

- **D27: OTel is the observability portability boundary; vendor-specific observability code is confined to adapters** (Package P2, Session 5)
  - Choice: All observability emission in `platform/observability/` and in `contexts/*/` uses OpenTelemetry APIs with GenAI semantic conventions. Langfuse-specific code is confined to `contexts/observability/adapters/outbound/langfuse/` and contains only the OTLP exporter configuration and the trace-query adapter for the read path. The OTLP collector endpoint is read through `platform/config/`. Switching to a different OTel-consuming observability tool is a configuration change plus a trace-query adapter rewrite.
  - Reasoning: D7 commits to self-hosted Langfuse 3 with OTel GenAI conventions. The portability claim that follows from that commitment needs to be explicit and architecturally enforced, or it decays into vendor lock-in by accretion. OTel as the wire protocol is the portability mechanism; the adapter pattern is the structural enforcement. OTel has consolidated as the cross-vendor observability standard, meeting the optionality principle's threshold for committed adoption.
  - Alternatives considered: Langfuse SDK directly in domain code (rejected: vendor lock-in by import). OTel emission with no architectural constraint on Langfuse-specific code (rejected: Langfuse-specific code spreads, swap cost rises).

- **D28: Python package is named `zephyr` to decouple implementation namespace from product name and resolve stdlib collision** (Package P2, pre-S6)
  - Choice: The top-level Python package is named `zephyr` (Esperanto for "north," continuing the navigation-theme lineage of the Quorum project name). The product name "Quorum" remains in user-facing surfaces, charter strategic framing, and external references; the package name `zephyr` is the implementation namespace. From this commit forward, charter decisions and working docs refer to `zephyr/config/`, `zephyr/security/`, `zephyr/observability/` as the file-path locations of the cross-cutting layer. Historical D-entries (D16, D19–D27) retain their original `platform/` wording as append-only record; the architectural concept they describe is unchanged.
  - Reasoning: The original `platform/` package name collides with Python's stdlib `platform` module, requiring a `conftest.py` shim as workaround. Trademark uncertainty around "Quorum" makes a package name tied to the product name a future-rebranding risk. Decoupling the package name from the product name protects against both: stdlib collision goes away with the rename, and a future product rename does not require touching every Python file.
  - Alternatives considered: `core_platform` (still contains the colliding word, generic, weak). `quorum` (couples package to potentially-changing product name). Other navigation-theme names (`compass`, `bearing`) lack the personal resonance and language-specific distinctiveness.

- **D29: Product name changes from Quorum to Zephyr** (Package P2, post-S6)
  - Choice: The product name is Zephyr from this commit forward. The package name was already `zephyr` per D28; the product and package names now align. User-facing surfaces (README, charter strategic framing, future UI copy, customer-facing communications) refer to Zephyr. Historical D-entries and session log reflections retain their original "Quorum" wording per the append-only principle in `principles.md`. The original D28 text, which committed to Quorum as the user-facing product name, stands as written.
  - Reasoning: The trademark uncertainty around "Quorum" cited in D28's reasoning has resolved, and the package-name decoupling D28 introduced means the product rename touches user-facing surfaces, charter narrative, operational defaults, and one config class name, but not the import namespace. "Zephyr" (Esperanto for "north") carries personal resonance for the operator and continues the navigation-theme of the package name. The decision is recorded as a charter D-entry rather than absorbed silently because future audits need a single locatable explanation for why the product name changes between commits visible in git history.
  - Alternatives considered: In-place edits to historical D-entries and session reflections (rejected: violates the append-only principle in `principles.md`, destroys audit-trail value, and the "one-time exception" framing is precisely how append-only erodes). Carrying forward both names in user-facing surfaces during a transition period (rejected: the project is pre-customer, no external surface depends on either name, clean break is cheaper than dual-naming).

- **D30: uv workspace topology — root pyproject is the cross-cutting platform package; bounded contexts and apps are workspace members** (Package P2, Session 7)
  - Choice: The repo-root `pyproject.toml` represents the `zephyr` cross-cutting platform package: it carries the runtime dependencies for `zephyr/config/`, `zephyr/security/`, `zephyr/observability/`, `zephyr/events/`, and `shared_kernel/`. Bounded contexts (`contexts/inference`, `contexts/observability`, `contexts/audit`) and deployable apps (`apps/api`) are uv workspace members declared in `[tool.uv.workspace]`, each with its own `pyproject.toml` declaring only the third-party dependencies that context or app uses. Members use `[tool.uv] package = false` so they are dependency-tracked but not built as wheels in dev — Python imports continue to resolve through `pythonpath = ["."]` in the root pytest config, which keeps the import-linter root packages and the AST enforcement walkers unchanged. Cross-context imports continue to be policed by import-linter (D16, D17) regardless of workspace topology; the workspace topology adds the second layer of enforcement at the dependency-manifest level.
  - Reasoning: The bounded-context boundary (D16) is enforced at the import level by import-linter; the workspace topology adds a second, complementary layer of enforcement at the dependency level. Declaring `litellm` only in `contexts/inference/pyproject.toml` and `langfuse` only in `contexts/observability/pyproject.toml` makes a vendor SDK leaking into another context a manifest-resolution failure, not just an import-linter failure. Keeping `zephyr/` (and `shared_kernel/`) at the workspace root rather than as members of their own avoids further pyproject proliferation for cross-cutting code that has small, shared third-party deps and is referenced by every context anyway. Apps land as members because each app is a distinct deployable unit with its own dependency profile (FastAPI for `apps/api/`, Vite for the future UI app, etc.).
  - Alternatives considered: Each cross-cutting concern (`zephyr/config`, `zephyr/security`, `zephyr/observability`, `zephyr/events`) as its own workspace member (rejected: forces pyproject proliferation without dependency-scoping benefit, since zephyr/ runtime deps are small and uniformly shared by every context). Only a root pyproject with no members and dependency-groups instead (rejected: defeats the per-context dependency-scoping commitment, leaves boundary enforcement only at the import level). `apps/api/` as a non-packaged consumer outside the workspace (rejected: loses uv's editable-install benefits for dev iteration on the app while still depending on workspace members).

- **D31: Package-level archive document at every package close from P2 forward** (Package P2, retrospective)
  - Choice: Every package from P2 onward produces an archive document at package close, written to `docs/archive/packages/pN.md`. The archive contains the package goal, sessions shipped, architectural commitments landed, stack state at close, data surfaced, drift surfaced, durable lessons, what the package leaves to the next, and convention changes. P1 retains no archive (the audit-time-only convention applied at P1 close, before this convention was settled). The cost calibration of the per-package archive convention is revisited at the Phase 1 close audit; if archive documents prove ceremonial in P3 through P5, the convention is reviewed.
  - Reasoning: Mid-phase package retrospectives produce synthesis with standalone value. P1 was structurally light enough that the absence of an archive has not bitten; P2 produced 16 D-entries, two AST tests, fourteen import-linter contracts, one rebrand, three durable lessons, and four drift candidates, which is enough material that the synthesis has audit value beyond the session log entries. Locating the synthesis across S4 through S8 session entries every time someone asks is reconstruction work the operator pays repeatedly. The archive document is the cheapest way to make that work payable once. The wording in `principles.md` ("Old content moves to archive at audit time, never deletes") becomes more permissive: "audit time" now includes package close from P2 forward. The principles wording itself is reviewed at phase audit if the convention sticks.
  - Alternatives considered: Defer all archives to phase audit (rejected: P2's material has standalone value that erodes if locked behind a phase audit twelve sessions away). Archive only at certain packages chosen ad hoc (rejected: ceremony question gets re-asked every package; better to settle the convention and revisit at phase audit). Treat the session log as the archive (rejected: session log entries are session-shaped, not package-shaped, and force per-audit reconstruction).

- **D32: Per-tenant Postgres instance topology — separate instances, two at P3 open for the test set, instance creation deferred until production deployment context** (Package P3, Session 9)
  - Choice: Each tenant has its own Postgres instance. P3 opens with two instances (`postgres-tenant-a`, `postgres-tenant-b`) seeded as tenants in the registry, joining a dedicated `postgres-control-plane` instance per D33. The provisioning workflow (registry insert, instance connection, control-plane row creation, schema migration) is exercised against these existing instances rather than against instance creation. Adding tenants beyond the two in Phase 1 requires editing Compose; instance creation as an automated step lands when production deployment context arrives and infrastructure-as-code is real.
  - Reasoning: D1 commits to database-per-tenant; the topology question (single instance with database-per-tenant logical separation versus separate instances) was open. The operator chose separate instances at the P2 retrospective on enterprise-grade learning grounds: running multiple Postgres instances locally exercises the routing layer under realistic conditions and makes the database-per-tenant claim concrete rather than theoretical. The cost is one more Postgres instance per tenant in the local Compose stack and a more substantial routing layer (per-tenant connection details in the registry, credential encryption per D21). Two test tenants at P3 open is sufficient to exercise the routing, isolation, and migration paths without committing to a dynamic-Compose pattern that has limited production analogue.
  - Alternatives considered: Single Postgres instance with logical database-per-tenant separation (rejected: lower local cost but does not exercise the routing layer or the credential-decryption path under realistic conditions; the architectural commitment to enterprise grade favours the more substantial routing). One instance at P3 open with provisioning workflow creating instances dynamically (rejected: dynamic-Compose pattern in dev does not match production posture, where instances are created by infrastructure-as-code; the local-versus-production gap is harder to absorb than the current Option A breach of D13 which is recoverable when production deployment lands).

- **D33: Control-plane database lives on a dedicated Postgres instance, separate from tenant data planes** (Package P3, Session 9)

- **D34: Credential encryption integration shape and three-control leak prevention** (Package P3, Session 10)
  - Choice: The tenant registry adapter integrates envelope encryption from `zephyr/security/crypto.py` (D21) on the credential write and read paths. Plaintext `TenantConnectionConfig` enters the adapter as input to `register_tenant`, is wrapped via `encrypt_field(plaintext_bytes, context={"tenant_id": ..., "purpose": "tenant.credentials.v1"})` before any I/O, and only the encrypted bytes touch Postgres. Read-back reverses the path: rows return `EncryptedCredentials`; the use case at the application layer unwraps to `TenantConnectionConfig` only when an operator-context caller invokes `reveal_connection_config`. Plaintext lives only in function-local variables, never in instance state, never in logs. The frozen-aggregate-plus-Core pattern is the right shape for hexagonal: the adapter owns the impedance mismatch, the domain stays pure, no ORM identity map tax, and decryption happens in Python after the row is fetched (asyncpg's prepared-statement cache returns bytea as `bytes` regardless of cache state, so caching is irrelevant to decryption correctness).

The AST test makes future plaintext-in-state regressions a CI failure, not a review comment. The AAD binding is what makes envelope encryption tenant-safe rather than merely cryptographically sound: without AAD binding, a stolen wrapped DEK from tenant A's row could decrypt tenant A's ciphertext if reattached to tenant B's row; with AAD binding to tenant_id and purpose, the InvalidTag boundary catches the misuse.   - Alternatives considered: Plaintext credentials in Postgres with disk-level encryption only (rejected: D21 commits to field-level for credentials specifically; disk encryption does not protect against DB credential compromise). Separate `AuditOperatorPort` for control-plane mutations (rejected: doubles audit surface for no architectural gain; one port with adapter-level routing is sufficient). - **D37: Audit adapter shape with hash-chain concurrency control and cache deferred** (Package P3, Session 12)
  - Choice: The audit Postgres adapter implements `AuditPort` against per-destination Postgres tables.   - Alternatives considered: Cache the last-written hash in adapter memory (rejected: trades correctness for unmeasured performance; deferred until measurement justifies). Serialisable isolation level on the audit transaction (rejected: heavier than needed; SELECT FOR UPDATE on the chain-tail row is sufficient). Advisory locks for concurrency control (rejected: more complex than row-level locking and adds a second mechanism alongside the existing transaction model). Omit `tenant_id` from per-tenant rows (rejected: cross-database queries need it; denormalisation cost is zero). Drop the cross-destination CHECK constraints (rejected: schema-layer defense complements the routing if-statement at zero runtime cost).

- **D66: Hybrid composition architecture — agent-runtime-executed composition with layered strategy selection and a three-strategy starter catalogue** (Data-retrieval design session, between-packages strategic block, 2026-05-07)
  - Choice: Hybrid composition is executed by the agent runtime based on agent configuration, not embedded in agent code. Three coupled commitments. First, location and execution model: agent code does not call ``search_vector`` and ``traverse_graph`` directly to compose results; the agent declares its retrieval strategy in configuration, and the agent runtime invokes the configured strategy through a strategy registry. The agent's view of retrieval is a single ``retrieve(query, filter, top_k, min_score, strategy_override=None)`` call; composition mechanics are runtime-internal. The ``RetrievalClient`` port from D65 stays at two methods (``search_vector``, ``traverse_graph``); the strategy registry sits above the port at the agent runtime layer per D5's "hybrid composition belongs at the agent layer" framing. Second, strategy selection is layered: each agent has a default strategy declared in configuration (sourced from methodology defaults at agent creation time per the methodology-embedded principle), and per-query override is allowed via the optional ``strategy_override`` argument. Override use is observable as span attributes (``padhanam.retrieval.strategy`` plus ``padhanam.retrieval.strategy_overridden = true`` when the override path was taken) so the optimisation layer can spot when an agent overrides the methodology default more often than expected. Third, the starter catalogue at P8 contains three strategies: ``vector_only`` (calls ``search_vector``, returns chunks); ``graph_only`` (calls ``traverse_graph``, resolves entities back to chunks via ``source_chunk_ids`` references, returns chunks); ``parallel_rrf`` (runs both stores in parallel, merges results by Reciprocal Rank Fusion across the two ranked chunk lists, returns the merged ranked chunks). The unit of composition is chunks across all three strategies; subgraph-shaped output is deferred until an agent type genuinely needs it (likely the analytics agent, already deferred). The query input is a free-text string for all strategies; strategies needing seed entities (``graph_only``, future cascade variants) extract them internally either via named-entity recognition or a vector pre-step, hidden from the agent.
  - Reasoning: D5 commits hybrid composition to the agent layer. The methodology-embedded-not-gated principle in ``charter/principles.md`` requires methodology defaults to be encoded as defaults rather than as workflow steps the user must traverse. The combination forces the runtime-executed-with-config-default shape: if methodology defaults sit in agent code rather than agent config, every agent re-implements its default and changing the default for "PM agent with LVT methodology" requires editing every PM agent, which is the gated-workflow shape the principle rejects. Agent-config defaults attached to methodology selection at agent creation match the principle's spirit. Layered strategy selection follows the principle's explicit second clause that overrides at decision points are cheap and non-punitive; per-agent default only would block within-agent strategy variation and contradict that clause; per-query selection only would push strategy choice back to agent code, undermining the methodology-embedded benefit. - **D67: Filter expression architecture — typed Boolean tree with bounded leaf operator vocabulary, scope-pre-composition / cut-off-post-composition pipeline split, and a six-operator starter set** (Data-retrieval design session, between-packages strategic block, 2026-05-07)
  - Choice: Filter expressions are typed objects in agent config and at the runtime port boundary, composed into a Boolean tree with arbitrary nesting depth. Three coupled commitments. First, the pipeline split: scope filters push pre-composition into each store as native predicates (SQLAlchemy expression for the pgvector adapter's source-and-chunk JOIN; Cypher WHERE clauses against the entity-and-source set in the Neo4j adapter); cut-off filters (``top_k`` and ``min_score``) apply post-composition at the merge step where the orchestrator can see the merged ranked result. ``top_k`` and ``min_score`` live as separate fields on the retrieval call rather than as predicates inside the filter tree, because cut-off has nothing to push down to the stores and mixing the two complicates translation. Second, the filter expression shape: each filter is a discriminated-union node, ``Predicate(field, op, value)``, ``And(children)``, ``Or(children)``, or ``Not(child)``. The leaf operators are drawn from a closed vocabulary of six entries: ``eq``, ``in``, ``gt``, ``gte``, ``lt``, ``lte``. Field references use dotted-path notation: ``source.id``, ``source.jurisdiction``, ``source.file_type``, ``source.created_at``, ``chunk.source_id``, ``chunk.jurisdiction``, ``chunk.chunk_index``, ``chunk.structural_metadata.<path>`` (scalar paths in the jsonb column). The Pydantic shape sits in agent config; the frozen-dataclass shape sits at the runtime port boundary, translated from the Pydantic shape per the existing port-domain pattern. The full retrieval spec at P8 is a typed object with five fields: a free-text ``query`` string, an optional ``strategy_override`` (default comes from agent config per D66), an optional ``filter`` tree (None means no scope filter), an optional ``top_k`` integer, and an optional ``min_score`` float. Third, structural surfaces remain non-user-filterable: ``tenant_id`` is enforced architecturally (D32 for Postgres-per-tenant, D63 for Neo4j property-scoped via ``TenantScopedNeo4jSession``); the readiness predicate ``state = 'indexed'`` remains structurally pre-applied per D65, not user-specifiable. Filters layer on top of these guards. Filter expressions are observable as a structured trace attribute (``padhanam.retrieval.filter``), letting the optimisation layer spot filter-shape patterns later.
  - Reasoning: The two filter purposes (scope and cut-off) apply at different points in the pipeline. Scope filters are cheap to push down because each store can apply them efficiently before returning. Cut-off needs the merged view (top-K across the merged ranked list, not 2*K from each store separately). Splitting the two by purpose is the structurally honest shape; making cut-off live in the filter tree complicates translation because cut-off has no per-store predicate, while making scope post-composition is wasteful because stores would return more than needed. The typed Boolean tree shape balances expressiveness against bounded translation surface: bounded leaf operators mean each operator maps to a finite set of per-store predicate generators (Postgres expression and Cypher predicate), while AND, OR, NOT composers map directly to native Boolean operators in both store query languages. The earlier framing of conjunctive-predicates-only as start-simple was misapplied: the start-simple-versus-structural-completeness distinction surfaced at the design session. Start-simple applies to scope (which fields and operators are available) but not to structural completeness of foundational contracts (composition expressiveness). Conjunctive-only would force agents to express OR and NOT in code, the same anti-pattern the methodology-embedded principle rejects at the strategy-selection layer; PM agent queries naturally include disjunctions ("decisions from Q3 OR Q4", "sources tagged X OR Y") and negations ("items NOT in the deferred bucket") that have to live in agent config, not agent code, for methodology defaults to encode them. The six-operator starter vocabulary covers equality, list membership, and comparison-against-numerics-and-timestamps, which together cover the bulk of PM agent filter shapes; ``contains``, ``exists``/``is_null``, ``regex``/``like`` defer with explicit triggers. ``contains`` activates when a schema extension introduces array fields. The others activate when a consumer needs them. The field set covers the source and chunk columns the substrate exposes today; ``state`` filtering remains structurally enforced per D65; ``created_by_user_id`` filtering defers with the personalization concern from the Ask David capture; tag-style fields defer until a schema extension introduces tagging.
  - Alternatives considered: Equality-dict filter shape with implicit AND across keys (rejected: hits the wall fast on real PM queries that need ``in`` for multiple sources or jurisdictions and range comparisons for date windows; lacks OR and NOT). Conjunctive-only typed object without Boolean composers (rejected after operator pushback: the start-simple framing was misapplied to expressiveness; PM workflows have inherent disjunctions and negations that have to live in config not code; v1-without-OR-NOT means v2 is a breaking change to add them, contradicting procurement-defensibility). Predicate AST with arbitrary leaf operators (rejected: open-ended leaf operators expand the per-store translation surface without consumer evidence; bounded leaf operators give the same expressiveness without the translation cost). SQL-like string with parser (rejected: parser complexity, audit difficulty, SQL-flavour leaking into the agent layer despite SQL being technically standard; contradicts the no-vendor-SDKs-in-domain-code spirit). Eval-style Python expression (rejected: security exposure from sandbox-escape risks, no audit boundary, no type safety). All filters apply pre-composition (rejected: breaks cut-off semantics because pre-composition top_k means each store returns its own top_k and the merged set has up to 2*top_k candidates we have to re-trim, so the agent's stated top_k is not preserved). All filters apply post-composition (rejected: scope filters that the stores could have applied themselves run on already-large result sets; performance penalty grows with corpus size). Per-strategy filter routing (rejected: strategies in the starter catalogue all benefit from the same filter behaviour; per-strategy variance has no consumer at P8). Cut-off filters as predicates inside the filter tree (rejected: cut-off has nothing to push down to the stores; mixing scope and cut-off complicates translation). Including ``contains`` for jsonb array elements at P8 (rejected: schema today does not expose array fields to filtering; structural_metadata is parser-emitted scalar paths). Including ``exists``/``is_null`` and ``regex``/``like`` at P8 (rejected: no consumer evidence; either can be added later without breaking the existing operator set).
  - Kano: must-have on the architectural commitments (pipeline split, Boolean tree with bounded leaf operators, the six-operator starter vocabulary, the cut-off-as-separate-fields shape — all gate P7's agent config schema and P8's runtime filter translator). Performance on the specific field set (start-simple floor for Phase 1; expands per-trigger as schema extends).

## D69: Prompt injection threat model and agent-runtime defences

**Decision.** At P8 framing, the agent runtime ships with named prompt-injection defences as architectural commitments. Four commitments: (1) source provenance carried through retrieval into LLM context such that injected instructions in retrieved content are distinguishable from operator-authored prompts at the prompt-construction boundary; (2) tool-call output filtering at the runtime boundary preventing unconstrained data egress through tool responses, with per-tenant egress allowlists activated alongside the production deployment context; (3) instruction hierarchy in system prompts enforcing operator instructions over retrieved content, mirroring the OpenAI and Anthropic instruction-hierarchy patterns; (4) red-team-shaped contract tests at `tests/contract/agent_runtime/` exercising indirect injection via retrieved sources, jailbreak-shaped prompts, and tool-call manipulation, with the same red-team posture as `tests/contract/tenant_isolation/` per D24. Specific implementation lands at P8.

**Reasoning.** Without this commitment at framing time, the agent runtime ships without a coherent threat model and absorbs prompt-injection failures as build-time discoveries rather than design constraints. Indirect injection via retrieved content is the highest-stakes vector for an agentic platform that couples retrieval to LLM completion calls per D66 and D67. The architectural floor required by the bet's enterprise-readiness claim cannot stand without it.

**Alternatives considered.** (a) Defer to P8 framing without architectural commitment now; rejected on the same logic as D24's tenant isolation commitment, where the threat model belongs at framing not at adapter authoring. (b) Treat prompt injection as an operational concern handled per-deployment; rejected because per-deployment posture would require every tenant to author their own prompt-injection defences, which contradicts the platform-as-substrate claim. (c) Commit to a specific prompt-injection-resistant model (e.g. Anthropic's harmlessness training); rejected because LLM-provider-agnostic per the LiteLLM commitment requires defences that work across model providers.

**Kano.** Must-have. Without this in the platform, the load-bearing claim about enterprise readiness fails procurement review at the first agentic-platform security questionnaire.

## D70: Cryptographic erasure for right-to-erasure under append-only audit chains

**Decision.** Tenant data-subject erasure requirements (GDPR Article 17, UK GDPR equivalent, jurisdiction-specific data-subject rights) are operationalised via cryptographic erasure rather than physical deletion. The per-tenant DEK structure from D21 enables this: erasing a tenant's KEK-wrapped DEK plus the KEK reference renders all tenant-encrypted data including audit-chain `before_state` and `after_state` JSONB unrecoverable. The audit-chain hash structure remains intact; chain integrity per D26 and D35 is preserved; the readable content becomes unreadable. Implementation lands as a `forget_tenant` use case at the tenancy context plus a tenant lifecycle state extension where `erased` joins `active`, `suspended`, `deprovisioned` per the existing CHECK constraint in `tenant_registry`. The erasure operation emits an audit event recording the chain hash before erasure as evidence of the operation's correctness. Activates at the package that frames data-subject rights operationally, likely Phase 2 production deployment context.

**Reasoning.** Physical deletion of audit-chain rows would break tamper-evidence per D26's commitment, which is itself a load-bearing architectural property. Cryptographic erasure resolves the apparent tension between append-only audit and right-to-erasure by separating the chain integrity (preserved) from the protected payload (rendered unrecoverable). Conservative regulatory interpretation under GDPR Article 17 accepts cryptographic erasure as satisfying the erasure requirement when the erased keys are themselves unrecoverable; the per-tenant DEK structure plus production KMS-backed KEK provides this guarantee.

**Alternatives considered.** (a) Physical deletion of audit-chain rows scoped to a tenant; rejected because it breaks tamper-evidence for the residual chain. (b) Maintaining a separate erasure-audit chain that records "this row was erased" without removing the original; rejected because the original payload would still exist, failing the regulatory requirement. (c) Treating audit-chain content as outside the scope of right-to-erasure under the legitimate-interest legal basis; rejected because legitimate-interest claims do not survive Article 17 scrutiny when alternative architectural solutions exist.

**Kano.** Must-have for any GDPR-jurisdiction tenant. Performance for non-GDPR jurisdictions where right-to-erasure is not directly required but the architectural property is procurement-readable.

## D71: Tool execution sandboxing

**Decision.** Tools registered through the tool registry (deferred from P7 per D68 to P8) execute in per-tenant sandboxes isolated from the platform process. Sandbox mechanism is a layered choice driven by tool category. (a) HTTP-based tools (the typical case at P8) sandbox via the network boundary plus per-tenant egress allowlists enforced at the platform proxy layer; the platform's own egress is the controlled boundary. (b) Code-execution tools (extensions per the architectural principle's residual-cases clause) sandbox via gVisor or Firecracker isolation per-tenant, with no shared state between tools or tenants. The default tool category at P8 is HTTP-based; code-execution tools defer until concrete use cases demand them. The egress allowlist activates with the production deployment context.

**Reasoning.** Tool execution is the highest-stakes security surface in agentic platforms because tools are tenant-controlled extensions with platform-level execution privilege. Without explicit sandbox commitment, the platform inherits whatever security properties tool authors happen to ship with, which is unbounded risk and procurement-visible at the first security review.

**Alternatives considered.** (a) No sandbox commitment, treating tool security as a tenant-supplied artefact concern; rejected because the platform-as-substrate claim collapses when tool execution can compromise the platform. (b) Container-per-tool isolation as the default; rejected at this commitment level as too heavyweight for the HTTP-based tools that constitute the typical case; deferred to code-execution tools where it earns its cost. (c) WASM-based isolation; rejected as immature for general tool-execution workloads in 2026; revisitable if WASM tooling matures by Phase 2.

**Kano.** Must-have. The procurement question "how is tool execution isolated" is asked in every agentic-platform security review.

## D72: Image signing and SLSA build-provenance attestation

**Decision.** Container images shipped to production are signed via cosign (Sigstore) and ship with SLSA provenance attestations at level 3 or higher. Image signing replaces digest-pinning as the primary integrity mechanism; digest-pinning continues as defence-in-depth at the compose layer per D25. Cosign verification gates deployment via admission policy at the production runtime. SLSA provenance attests to source repository, build environment, build steps, and inputs. The CI pipeline produces both signature and attestation; deployment infrastructure verifies both before pulling images. Activates at the production deployment context per the deferred-decisions production-onboarding entry; Phase 1 dev posture continues to use digest-pinning alone.

**Reasoning.** Digest-pinned images plus SBOM is the floor; signed images plus provenance attestation is the procurement-grade ask. AI Labs procurement reviews on supply-chain hardening expect at least signed images by 2026, and federal-adjacent buyers (FedRAMP-shaped) require attestation. The architectural commitment now ensures the production deployment work does not retrofit a signing pipeline against an unprepared codebase.

**Alternatives considered.** (a) Notation/Notary v2 instead of cosign; rejected because cosign has the larger ecosystem in 2026 and Sigstore's keyless signing reduces operational overhead. (b) SLSA level 2 instead of level 3; rejected because level 3 is the procurement-grade ask and the additional commitment (hosted build environment, isolated build) is achievable with standard CI tooling. (c) Defer entirely until production deployment context; rejected because the CI pipeline shape needs to land in Phase 1 close work for the production-deployment package to consume; an unprepared CI pipeline would force retrofit of signing across the existing Dockerfile set.

**Kano.** Performance for AI Labs procurement at 2026 maturity; must-have for federal-adjacent and FedRAMP-shaped buyers; the asymmetric Kano category mirrors D69's pattern across audiences.

## D73: Post-quantum cryptography readiness

**Decision.** PQ readiness commits to four boundary commitments and one schema forward-affordance.

(1) Production TLS posture (Caddy edge, mTLS internal) requires hybrid PQ key exchange (X25519MLKEM768 or NIST-approved successor) at the production deployment context, extending D20. Go's `crypto/tls` ships hybrid KEX in default ciphersuites by 2026; Caddy inherits automatically; the commitment is documentation, not implementation work.

(2) Production KMS selection criterion (Phase 2, replacing the `SecretManagerSource` no-op stub) names PQ-aware key encapsulation supporting ML-KEM or successor at the vendor boundary. AWS KMS HSMv2, Azure Key Vault Premium, GCP Cloud HSM all have ML-KEM roadmaps by 2026; the selection criterion ensures the chosen KMS aligns.

(3) Identity federation per D52 names PQ posture as a Phase 2 revisit at activation moment, gated by ecosystem maturity. Pure ML-DSA in IdP stacks is not broadly deployed in 2026; hybrid ES256+ML-DSA is implementation-available but not standardised. Commitment is to revisit at Phase 2 framing, not now.

(4) Outbound TLS to LLM providers via LiteLLM tracks vendor PQ posture under the existing `ops/scheduled_checks.yaml` cadence per D41's monthly-review pattern. Padhanam cannot force PQ on outbound calls; the commitment is to track vendor adoption.

(5) Schema forward-affordance: `padhanam/security/crypto.py` remains the single point of cipher choice with `key_version` versioning KEK rotation. A `cipher_id` schema column is reserved as forward-affordance for future cipher swap; added to `tenant_registry` when the first non-AES-GCM cipher arrives per the established forward-affordance pattern from D41 cost-ceiling columns.

Symmetric primitives in current use (AES-256-GCM via D21, HMAC-SHA-256 via the HS256 dev auth, SHA-256 in the audit hash chain per D26 and D35) remain PQ-safe under conservative guidance and require no immediate change.

**Reasoning.** HNDL (harvest-now-decrypt-later) threats are credible for any platform handling regulated data with long-term sensitivity; tenant credentials in the registry plus audit-chain content represent multi-year sensitivity windows. The architectural surfaces vulnerable to quantum attack are concentrated at TLS boundaries and asymmetric KMS operations; symmetric primitives dominating data-at-rest and audit-chain integrity are already PQ-safe by accident of the SOC 2 Type II posture choices. The commitment closes procurement questions without forcing immediate implementation work.

**Alternatives considered.** (a) Full PQ migration at Phase 1 including all symmetric primitives swapped for PQ-conservative variants (AES-256-GCM-SIV, SHA-384); rejected because conservative PQ guidance accepts the current symmetric primitives at 128-bit post-quantum margin. (b) No PQ commitment until vendor pressure demands it; rejected because the production deployment context will demand it for federal-adjacent buyers; ahead-of-demand commitment is the cheaper position. (c) Commit to specific cipher migration timeline; rejected because the cipher landscape evolves through 2026-2030 and premature timeline commitment is paper architecture.

**Kano.** Delighter for AI Labs procurement at 2026 maturity. Must-have for federal-adjacent buyers in 2026. Performance for the broad market by 2028.

## D74: Methodology aggregate shape, hash-chain content surface, repository interface, and CLI shape

**Decision.** The methodology bounded context ships at S23 with the following architectural commitments.

**Aggregate shape.** Two frozen-dataclass aggregates following D31's revision-shape precedent. `MethodologyTemplate` carries the human-stable identity (id, name, description, created_by_user_id, created_at, archived_at). `MethodologyRevision` carries the per-revision content (methodology_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at) plus the hash-chain fields (previous_revision_hash, this_revision_hash). Revisions are immutable per D31; updates create new revision rows. Retirement marks the parent template's archived_at, leaving revisions intact for existing-clone-references per D68.

**Persistence shape.** JSONB columns for the structured fields. `source_ids` jsonb (array of UUID strings; typically empty for templates per D68); `tool_allowlist` jsonb (array of opaque strings; opaque per D68 with no registry at P7); `retrieval_strategy` jsonb (per D66's strategy-name-plus-params shape; e.g. `{"strategy": "vector_only", "params": {}}`); `filter_tree` jsonb (per D67's typed-Boolean-tree shape; defaults to the empty-tree sentinel). Scalar fields (top_k integer, min_score numeric, model_selection text, system_prompt text) as native columns. The JSONB-as-configuration pattern matches `scoring_sheet_criteria.levels` per D55 and avoids cross-context relational coupling between methodology and the retrieval/filter abstractions.

**Hash-chain content surface.** SHA-256 over canonical JSON of a payload comprising the revision content fields plus `previous_revision_hash` as a key inside the payload, mirroring the audit-chain pattern at `contexts/audit/domain/events.py:67-81` per D26. Canonical JSON: sorted keys, no whitespace separators (`json.dumps(payload, sort_keys=True, separators=(",", ":"))`), UTF-8 encoded. Numeric fields stored as Postgres `numeric` type round-trip through `Decimal` in SQLAlchemy; for canonical-JSON determinism plus operator-readable audit-dump form, the canonical encoder converts `Decimal` values via `format(value.normalize(), "f")`, which produces canonical fixed-point lexical form regardless of magnitude (e.g. `Decimal("0.50")` and `Decimal("0.5")` both serialise to `"0.5"`; `Decimal("100")` serialises to `"100"` rather than the `str(...)`-form `"1E+2"`). At S23, `min_score` is the only Decimal-shaped field; future Decimal fields (cost ceilings, retrieval-tuning numerics, percentage thresholds) inherit the same handling via the central encoder. The audit precedent at `contexts/audit/domain/events.py:67-81` does not exercise this path; the methodology context extends the precedent additively rather than diverging from it. The hash spans: name (denormalised onto the revision for chain-self-containment), description, system_prompt, source_ids (with internal sort), tool_allowlist (with internal sort), retrieval_strategy, filter_tree, top_k, min_score, model_selection, plus `previous_revision_hash` as the chain-binding key. The hash does not span: methodology_template_id, version, created_by_user_id, created_at, this_revision_hash. Reasoning: the chain-binding mechanism is inclusion of the previous hash inside the canonical-JSON payload, which is the audit precedent under D26. The chain structure that does not appear in the hash (template_id, version, timestamps, this_revision_hash itself) is what makes the chain queryable as relational data; the content fields plus the chain-binding previous hash are what the integrity check actually verifies.

**Repository interface.** `MethodologyRepositoryPort` Protocol with no `TenantContext` parameter on any method. Methodology data is control-plane-scoped per D33; mutation auth flows through the use case layer (operator-context enforcement) mirroring `register_tenant`/`update_tenant_status`/`reveal_connection_config` per D34. Methods: `create_template(template, initial_revision) -> MethodologyTemplate`, `get_template(template_id, version=None) -> tuple[MethodologyTemplate, MethodologyRevision]`, `list_templates() -> list[MethodologyTemplate]`, `add_revision(template_id, revision) -> MethodologyRevision`, `archive_template(template_id) -> MethodologyTemplate`. Tenant-context callers reading methodology templates do so without policy gating because templates are platform-managed and visible across tenants by design (the inverse of agent isolation per the P7 epic note).

**Operator-context enforcement at use case layer.** All five use cases inherit the operator-context pattern from D34. `create_methodology_template`, `update_methodology_template`, `retire_methodology_template` require operator-context and reject tenant-context callers including own-tenant callers. `get_methodology_template` and `list_methodology_templates` accept any authenticated context (operator or tenant) per the platform-managed-templates-visible-across-tenants principle. `AuthorizationError` from `padhanam/security/policy.py` raised on rejection, mirroring `reveal_connection_config`'s rejection path. Per pre-build review, the `OPERATOR_ROLE` constant and `is_operator` predicate currently at `contexts/tenancy/application/use_cases.py` promote to `padhanam/security/policy.py` at this session's commit 8 alongside the methodology use cases, with the tenancy use cases updated to import from the new location. The promotion treats operator-context as a platform-level security primitive consistent with where `AuthorizationError` and `check` already live; the alternatives (cross-context application-to-application import forbidden by D17's independence contracts; duplication fragmenting the predicate definition) were both worse on structural-honesty grounds.

**CLI shape.** Five commands at `padhanam methodology` namespace.
- `padhanam methodology create --config <path>` reads a YAML or JSON file containing the full template-plus-revision-1 payload (name, description, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection); produces a new template with revision 1; prints the new template_id and revision_id.
- `padhanam methodology get <template-id> [--version N] [--json]` retrieves the template plus the named or latest revision; default human-readable, --json for machine-readable.
- `padhanam methodology list [--json]` lists all non-archived templates.
- `padhanam methodology update <template-id> --config <path>` reads the same config shape minus the name (which is immutable per the template aggregate); produces a new revision; prints the new revision_id and version number.
- `padhanam methodology retire <template-id>` marks the template's archived_at; existing clones unaffected per D68.

The --config file shape is YAML or JSON (auto-detected by extension; .yaml/.yml or .json). The CLI parses, validates against the methodology config schema, and constructs the domain aggregate at the use case boundary. Operator-context resolution at `apps/cli/_runtime.py` mirrors the P5 dev-shape pattern: short label 'operator' resolves to the operator role; the production CLI tenant resolution carryover from P5 close applies symmetrically here for Phase 2.

**Alternatives considered.** Nine rejected alternatives weighed.

(a) Single methodology-template aggregate without revision split; rejected because D31's revision-shape precedent provides the immutable-content-with-evolving-versions discipline that audit posture requires.

(b) Normalised tables for retrieval_strategy and filter_tree (separate strategy-row, separate predicate-tree-rows); rejected because the configuration is consumed atomically per agent invocation and never queried at the field level; relational normalisation buys join cost without analytical benefit.

(c) Single config jsonb collapsing all structured fields into one column; rejected because separate jsonb columns preserve the architectural distinction between retrieval (D66 concern), filter (D67 concern), source attachment, and tool allowlist; the cleaner schema also supports future analytical queries without column-pruning the jsonb.

(d) MethodologyRepositoryPort with TenantContext parameter for read uniformity across contexts; rejected because methodology data is structurally control-plane-scoped and pretending otherwise creates the same architectural confusion the tenancy-context-without-tenant-context pattern would create. Read-side filtering by tenant happens at the agent context (tenant-scoped), not at the methodology context (platform-scoped).

(e) Hash-chain over the entire revision row including chain metadata; rejected because chain metadata is the chain structure itself; including it makes the hash non-deterministic against the canonical content shape.

(f) Hash-chain over the methodology template plus all revisions ever; rejected because that is the audit-chain pattern (event chain), not the revision-chain pattern; methodology revisions chain forward per template, mirroring the `scoring_sheet_revisions` per-sheet revision pattern.

(g) Tenant-admin role distinct from operator role for methodology mutations; rejected because at Phase 1 the operator-context-or-tenant-context distinction from D34 covers the platform-admin case; tenant-admin role lands when tenant-facing methodology authoring UI surfaces (Phase 2 per the P7 epic note's out-of-scope).

(h) CLI flag-per-field shape rather than --config-file shape; rejected because the field set has nine substantive fields including two structured (retrieval_strategy, filter_tree) and two list-shaped (source_ids, tool_allowlist); flag-per-field would produce 9-12 flags including file references for the structured fields and would lose the schema-validatable-at-parse-time property that --config gains.

(i) Leaving `OPERATOR_ROLE` and `is_operator` at `contexts/tenancy/application/use_cases.py` and importing cross-context from methodology; rejected because cross-context application-to-application imports violate D17's independence contracts and would require new import-linter exemptions; promoting to `padhanam/security/policy.py` is the structural-honesty resolution and lifts a primitive that was always platform-level to its proper home.

**Kano.** Performance. The aggregate shape and persistence choices preserve the architectural discipline (revision shape per D31, hash-chain per D26, control-plane scope per D33, operator-context auth per D34) that future packages consume; alternative shapes would force retrofit at S24 (agent context) or P8 (agent runtime). The CLI shape is delighter on operator ergonomics; the structural-honesty contribution sits at the architectural commitments above.

## D75: Agent aggregate shape, methodology lineage, hash-chain helper promotion, repository interface, auth posture, and CLI shape

**Decision.** The agent bounded context ships at S24 with the following architectural commitments.

**Aggregate shape.** Two frozen-dataclass aggregates following D31's revision-shape precedent and inheriting D74's structural pattern. `AgentTemplate` carries the human-stable identity plus methodology lineage: id, name, description, source_methodology_template_id (UUID, nullable for blank-created agents, immutable after construction), source_methodology_template_version (integer, nullable for blank-created agents, immutable after construction), created_by_user_id, created_at, archived_at. Description lives on AgentTemplate only and is immutable after creation; treating description as part of revision content would conflate metadata-stable identity with revision-evolving content. `AgentRevision` carries the per-revision content (agent_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at) plus the hash-chain fields (previous_revision_hash, this_revision_hash). Revisions are immutable per D31; updates create new revision rows. Archive marks the parent template's archived_at.

The paired-NULL invariant on AgentTemplate's lineage fields (both NULL or both populated; never one without the other) is enforced at the domain layer via `__post_init__` validation on the frozen dataclass: instantiation with exactly one of the two fields populated raises `ValueError`. The same invariant is enforced at the schema layer via the CHECK constraint named in the schema update; the two-layer enforcement matches the audit-context precedent of domain-layer validation backed by schema-layer constraint.

**Methodology lineage placement.** The lineage fields (source_methodology_template_id, source_methodology_template_version) live on AgentTemplate, not on AgentRevision. Reasoning: lineage is template-level identity (origin), not revision-level content (what changes between versions). Placement on the template structurally enforces D68's "set immutably on revision 1, preserved across all later revisions" because the template never changes after creation; the lineage cannot drift across revisions because it does not exist on the revision. The fields are nullable to accommodate blank-created agents per D68.

**Persistence shape.** Same JSONB-for-structured-fields and scalar-for-primitives pattern as D74. `source_ids` jsonb, `tool_allowlist` jsonb, `retrieval_strategy` jsonb, `filter_tree` jsonb on AgentRevision; `top_k` integer, `min_score` numeric, `model_selection` text, `system_prompt` text on AgentRevision. The AgentRevision row contains: agent_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at, previous_revision_hash, this_revision_hash. Name is read from the parent AgentTemplate at hash-compute time and not persisted on the revision row, mirroring S23's actual implementation pattern. AgentTemplate carries `id` uuid, `name` text, `description` text nullable, `source_methodology_template_id` uuid nullable, `source_methodology_template_version` integer nullable, `created_by_user_id` text, `created_at` timestamptz, `archived_at` timestamptz nullable.

**Hash-chain content surface.** Same shape as D74's audit-mirror per D26. SHA-256 over canonical JSON of a payload comprising the revision content fields plus `previous_revision_hash` as a key inside the payload. Format-f Decimal canonical encoder inherited unchanged. The hash spans: name (read from parent template at compute time), description (read from parent template at compute time), system_prompt, source_ids (sorted), tool_allowlist (sorted), retrieval_strategy, filter_tree, top_k, min_score, model_selection, plus previous_revision_hash. Excluded: agent_template_id, version, created_by_user_id, created_at, this_revision_hash. Methodology lineage fields are template-level and explicitly outside the revision hash because they are not part of revision content.

Name is read from the parent AgentTemplate at hash-compute time and included in the canonical-JSON payload as the `name` key, mirroring the methodology context's conceptual-denormalisation pattern from S23's actual implementation. Name is not persisted as a column on agent_revisions; the architectural argument for chain-self-containment is satisfied by the payload-key inclusion at compute time without the redundancy of a persisted denormalised column. If a future session demands stricter chain self-containment (e.g., S25's cross-context flow surfacing a real consumer need), the migration to a persisted column lands then with a real architectural reason.

Description is read from the parent AgentTemplate at hash-compute time and included in the canonical-JSON payload as the `description` key (with `""` as the deterministic value when description is NULL), mirroring the methodology context's actual implementation from S23. Description is template-level and immutable post-creation, so its inclusion in the revision hash is deterministic and stable across the chain; the earlier argument that inclusion would force new revisions on description updates does not apply because description does not update post-creation.

**Hash-chain helper promotion.** The hash-chain primitives currently at `contexts/methodology/domain/hash_chain.py` promote to `padhanam/security/hash_chain.py` at this session's commit 8 alongside the agent use cases. The promoted helper exports field-set-agnostic primitives only: `compute_revision_hash(content_payload: dict, previous_hash: str) -> str`, `canonical_json(payload: dict) -> bytes`, `_CanonicalJSONEncoder(json.JSONEncoder)`, `GENESIS_REVISION_HASH = "0" * 64`. Methodology-specific bits in the current helper (the `CONTENT_FIELDS` frozenset, the `_normalise_list_fields` function, the unused `filter_content_fields` defensive whitelist) do not promote; list-sort responsibility for list-shaped fields moves to the use case layer in both contexts. Each use case knows which of its fields are list-shaped and sorts them before constructing the content payload it passes to `compute_revision_hash`. The promotion treats hash-chain as a platform-level security primitive consistent with where AuthorizationError, check, OPERATOR_ROLE, and crypto.py live; the API shape is field-set-agnostic so future revision-shaped contexts inherit the primitive without re-cleaning the helper's field-name coupling. Cross-context import from contexts.methodology.domain into contexts.agent violates D17's independence contracts; the promotion is the structurally honest resolution. This is the second instance of the second-consumer-promotes pattern after S23's OPERATOR_ROLE promotion; the pattern is a Patterns-observed candidate at the next phase audit if a third instance fires (potentially at S25's cross-context flow or at a future revision-shaped context).

**Repository interface.** `AgentRepositoryPort` Protocol with `TenantContext` parameter on every method. Agent data is per-tenant per D32; routing flows through TenantContext per D50, mirroring the existing per-tenant adapters at `contexts/audit/`, `contexts/evaluation/`, `contexts/ingestion/`. Methods: `create_template(template, initial_revision, tenant_context) -> AgentTemplate`, `get_template(template_id, tenant_context, version=None) -> tuple[AgentTemplate, AgentRevision]`, `list_templates(tenant_context, include_archived=False) -> list[AgentTemplate]`, `add_revision(template_id, revision, tenant_context) -> AgentRevision`, `archive_template(template_id, tenant_context) -> AgentTemplate`. Cross-tenant access fails at the tenant-isolation contract test layer and at the data-layer predicate.

**Auth posture.** Agent CRUD use cases accept either tenant-context or operator-context as valid authentication; both produce authorised access. Reasoning: agents are tenant-user-owned per the P7 epic note's audience definition; tenant users CRUD their own agents through the tenant-context route. The CLI in operator-context per the dev-shape pattern from `apps/cli/_runtime.py` also CRUDs agents on behalf of a tenant; this is operator-as-platform-administrator, not operator-as-tenant-impersonator. AuthorizationError raised on unauthenticated callers (no role at all). The cross-context create-from-methodology flow at S25 inherits the same auth posture.

**CLI shape.** Five commands at `padhanam agent` namespace.
- `padhanam agent create --tenant <label> --config <path>` reads YAML or JSON config containing the full template-plus-revision-1 payload (name, description, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection); produces a new template with revision 1 (and source_methodology_template_id / source_methodology_template_version both NULL because this is blank-created); prints the new template_id and revision_id.
- `padhanam agent get --tenant <label> <template-id> [--version N] [--json]` retrieves the template plus the named or latest revision.
- `padhanam agent list --tenant <label> [--include-archived] [--json]` lists templates (default excludes archived).
- `padhanam agent update --tenant <label> <template-id> --config <path>` reads the same config shape minus the name; produces a new revision; prints the new revision_id and version number.
- `padhanam agent archive --tenant <label> <template-id>` marks the template's archived_at; revisions remain intact for audit.

The `create-from-methodology` subcommand is excluded from S24; lands at S25 alongside the cross-context flow it consumes.

**Alternatives considered.** Eight rejected alternatives weighed.

(a) Methodology lineage fields on AgentRevision rather than AgentTemplate; rejected because revision-level placement creates the enforcement burden that template-level placement avoids structurally; the fields would be repeated identically across every revision and a malicious or buggy update path could drift them.

(b) Hash-chain helper duplication in contexts/agent/domain/ rather than promotion; rejected on the same drift-cost argument that justified S23's OPERATOR_ROLE promotion. Two definitions of canonical-JSON encoding is exactly the failure mode the S23 review caught at pre-build; the structural-honesty resolution is the same shape applied to the same recurrence.

(c) Cross-context import of hash_chain from contexts.methodology.domain into contexts.agent; rejected because it violates D17's independence contracts and would require new import-linter exemptions.

(d) Repository without TenantContext parameter, with tenant routing at the use case layer; rejected because it inverts the per-tenant pattern the rest of the codebase follows (audit, evaluation, ingestion all carry TenantContext through the port chain) and would require a parallel routing mechanism for one context only.

(e) Operator-context required for all agent CRUD (mirroring D34 / D74 methodology pattern); rejected because agents are tenant-user-owned per the P7 epic note's audience definition; requiring operator-context would force every tenant user interaction through an operator role, which is wrong at the architectural level.

(f) Tenant-context required only (no operator-context override); rejected because the CLI runs in operator-context per the dev-shape pattern, and agent CRUD via the CLI is a real workflow at Phase 1; rejecting operator-context would force the CLI into a tenant-impersonation pattern that does not match its actual role.

(g) Single combined AgentTemplate + AgentRevision aggregate without revision split; rejected for the same reason D74 rejected the equivalent for methodology — D31's revision-shape precedent provides immutable-content-with-evolving-versions discipline that audit posture requires.

(h) As-is promotion of the existing methodology helper including `_normalise_list_fields` and `CONTENT_FIELDS`, with field-name coupling documented in the new module's docstring; rejected because the second-consumer moment is the cheapest moment to settle the helper's API shape. List-sort responsibility on the helper bakes in field-name assumptions that the next revision-shaped context would have to refactor or work around; moving the responsibility to the use case layer now makes the helper field-set-agnostic and avoids a third-time-around cleanup. The cost is small (each context's use case adds a `_sort_list_fields` call before constructing the content payload); the structural-honesty benefit is a clean primitive at `padhanam/security/`.

**Kano.** Performance. Aggregate shape and persistence choices preserve the architectural discipline (revision shape per D31, hash-chain per D26, per-tenant scope per D32, lineage as template-level immutable per D68) that S25's cross-context flow consumes and P8's agent runtime executes against. Hash-chain helper promotion is structural-honesty rather than feature work; the alternative (cross-context import or duplication) would degrade the architecture. CLI shape is delighter on operator ergonomics; the structural-honesty contribution sits at the architectural commitments above.

## D79: Cross-context create_agent_from_methodology flow shape — agent-owned cloning via callable api-facade ports, MethodologyView and SourceLookup as consumer-side abstractions (P7 S25, 2026-05-10)

**Decision.** The `create_agent_from_methodology` use case lives in `contexts/agent/application/use_cases.py`. Agent context contains zero imports from `contexts.methodology` or `contexts.ingestion` at the domain or application layer; verified by extending the existing cross-context independence import-linter contracts to cover the new cross-context relationships. Lineage records on the new `AgentTemplate` populate `source_methodology_template_id` and `source_methodology_template_version` (the resolved version, not the request's version=None) per D75's paired-NULL invariant. The cloned `AgentRevision` version 1 inherits content fields from the `MethodologyView`: system_prompt, retrieval_strategy, filter_tree, top_k, min_score, model_selection, tool_allowlist all copy verbatim; description copies from the methodology template envelope; source_ids come from the request payload after existence validation, not from the methodology (methodology templates do not carry tenant-scoped source_ids). The cloned agent is independent per D68: subsequent edits to the methodology template do not propagate to the agent, and subsequent edits to the agent do not propagate back to the methodology. Auth posture: agent write requires tenant-context-or-operator-context per D75; methodology read uses any-authenticated-context per D34's get/list pattern; source existence check uses tenant-context (or operator-context routed through the tenant) per D32. CLI surface: `padhanam agent create-from-methodology --tenant <label> --config <path>` with config shape accepting `methodology_template_id`, optional `methodology_version` (defaults to latest), `name`, `source_ids`; the use case resolves version=None to the latest version at clone time and records the resolved integer in lineage.

**Reasoning.** The api-facade-via-callable pattern is the established cross-context convention per D17; the S17b precedent (evaluation→inference) demonstrated callable-injection-at-construction as the structurally-honest cross-context shape. Wrapping each producer's use cases in a callable port avoids type imports at the consumer's domain or application layer while letting the wiring layer translate producer aggregates to consumer-shaped DTOs. Agent-context ownership of the cloning logic respects D68's independent-clones commitment: methodology is the read-only producer, agent is the write-side consumer that records lineage and persists the clone. Source existence validation at the use case boundary fails fast on bad source_ids rather than after AgentTemplate construction, which would leave orphan-reference revisions if persistence ran first; the validation also surfaces tenant-routing errors (source belongs to a different tenant) at the boundary rather than at retrieval time. The MethodologyView DTO defined in the consumer's application layer rather than as a re-export of MethodologyTemplate is the structurally-honest cross-context type pattern: shared types create coupling that the hexagonal seam exists to prevent. Tenant-context-or-operator-context auth for agent write inherits D75; methodology read inherits D34's get/list pattern; source check uses tenant-context per D32 because source data is tenant-scoped per D32 (source rows live on per-tenant Postgres).

**Alternatives considered.** Seven rejected alternatives weighed.

(a) Methodology context owns cloning via a `clone_to_agent` use case at `contexts/methodology/application/use_cases.py`. Rejected because methodology has no business knowing about agents per D17; the consumer-knows-mapping pattern fits agent-side ownership; methodology is platform-managed and audience-shifting it to know about tenant agents inverts the audience boundary D16's bounded contexts split establishes.

(b) Apps-layer orchestration service at `apps/cli/_clone_orchestrator.py` owning the cross-context flow and calling both contexts' use cases. Rejected because business logic belongs in the consumer's use case layer per the hexagonal pattern; an apps-layer orchestrator would replicate the architectural mistake the hexagonal seam exists to prevent (business logic in the wiring layer is unowned by any context's discipline).

(c) Direct cross-context import from `contexts.methodology.domain` into `contexts.agent.application`. Rejected because it violates D17's independence contracts; the import-linter contracts would break; the same shape as the S24 hash-chain helper promotion rationale (cross-context type imports always promote to a higher-altitude shared module or get abstracted via consumer-side ports).

(d) MethodologyView as a re-export of `MethodologyTemplate` plus `MethodologyRevision`. Rejected because cross-context type sharing creates the coupling D17 forbids and the consumer would inherit the producer's invariants (paired-NULL lineage on methodology, hash-chain semantics) that the agent context has no business asserting. A consumer-shaped DTO at the consumer's application layer is the structurally-honest shape and matches how evaluation handles inference results per S17b.

(e) Source attachment as a follow-on update step rather than at create-time. Rejected because the e2e demonstration value is weaker (two-step create-then-attach reads as architectural drag in the demo flow), the at-create-time validation surfaces source-not-found errors earlier in the user flow, and the at-create-time path matches how the existing blank-create with `--source-ids` works (inherits the same UX shape rather than diverging).

(f) CLI command without `--config` (all parameters as flags). Rejected because the existing agent CRUD pattern (S24's `create`, `update`) uses `--config` for the structured payload; create-from-methodology inherits the same shape for CLI surface uniformity; methodology_template_id and source_ids are awkward as flags (UUID arguments), comfortable as YAML.

(g) LVT system prompt drafted at build-time without preservation in the brief. Rejected because methodology IP benefits from operator review before paste, the system prompt is the methodology's primary content surface (not a default), and brief-preservation matches the framing-prompt-as-recommendation pattern's distinction between defaults (drafted at build-time) and substantive content (drafted at brief-time and reviewed before commit).

**Kano.** Performance for the cross-context architectural commitments (api-facade-via-callable shape, MethodologyView placement, lineage recording mechanics, source existence validation timing); delighter for CLI ergonomics (config-file-based create-from-methodology consistent with blank-create); must-have for the LVT template content surface because the bet's "one agent configured from a methodology template" demonstration depends on a real LVT system prompt rather than a placeholder.
