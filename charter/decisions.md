# Architectural Decisions

Append-only log. One entry per decision. Reviewed at phase audits.

Format:
- **Decision N: [name]** (Package P, Session S)
  - Choice: [what was decided]
  - Reasoning: [one or two sentences]
  - Alternatives considered: [if relevant]

## Phase 1 baseline decisions

These were made before Session 1 and form the starting architecture.

- **D1: Tenancy model is database-per-tenant.** Strongest isolation. V1 runs one tenant locally; architecture is forward-built for many.
- **D2: No sub-workspaces inside a tenant in V1.** Tenant is the unit of organization. Workspaces deferred to V2 if needed.
- **D3: Identity is Keycloak in V1 Docker Compose.** Reference open-source IdP, OIDC + SAML + SCIM. ~1GB RAM cost accepted.
- **D4: LLM access via LiteLLM gateway.** No vendor SDKs in domain code. Ollama default in dev.
- **D5: Retrieval is hybrid, configured per agent.** Vector via pgvector and graph via Neo4j, both behind `RetrievalClient`. Strategy fixed at agent config in V1; runtime selection deferred to V2.
- **D6: Orchestration is LangGraph behind `AgentOrchestrator` interface.** CrewAI or custom orchestrators swappable later.
- **D7: Trace store is self-hosted Langfuse 3, behind an interface.** OpenTelemetry GenAI conventions used throughout.
- **D8: V1 metric scope is bounded.** Cache hit rate, output token distribution, context length trajectory, tool call patterns, cost per successful task, latency components decomposed, model substitution similarity scores. New metrics require documented decisions they inform.
- **D9: Optimization output is recommendation-shaped.** Every dashboard view ties to a recommended action.
- **D10: Stack versions pinned.** Python 3.14, Node 24 LTS, Postgres 17 with pgvector, Neo4j 5 Community, Keycloak 26, Redis 7, Vite 6, React 19, React Router 7, FastAPI, SQLAlchemy 2.0 async, LangGraph current, LiteLLM current, Langfuse 3.

## Session decisions

- **D11: Scaffold grows incrementally** (Package P1, Session 1)
  - Choice: Each package adds the Compose services it requires. P1 ships repo structure, charter docs, and structural tooling. Compose at P1 close contains only services exercised by P1 or P2.
  - Reasoning: Big-bang scaffold front-loads complexity before any service has earned a use case, contradicting the learning-sprint framing of Phase 1. Incremental scaffold reaches agent work faster and prevents unused-service drift.
  - Alternatives considered: Big-bang scaffold (Postgres, Neo4j, Keycloak, Redis, LiteLLM, Langfuse all at P1 close). Rejected on learning-value and drift grounds.

- **D12: Jurisdiction is a first-class architectural attribute** (Pre-S2 charter edit)
  - Choice: Tenant context carries jurisdiction from P3 onward. Every component that touches customer data (databases, object storage, identity, trace store, LLM endpoints) is built to be regionally partitionable. Phase 1 deploys a single region; the architecture does not assume a single region anywhere in code.
  - Reasoning: Retrofitting jurisdiction across forty tables and every interface signature later is a quarter of work and a migration risk. Building it in from inception is free at the data-model layer and cheap at the interface layer. The discipline is "by construction, not by policy", which is the framing enterprise procurement and auditors require.
  - Alternatives considered: Treat jurisdiction as a Phase 2 concern and add it when the first non-default-region tenant arrives. Rejected on retrofit-cost grounds.

- **D13: Tenant onboarding is configuration, not deployment** (Pre-S2 charter edit)
  - Choice: Per-tenant decisions (jurisdiction, identity federation, classification policy, model endpoints, retention) live in the tenant registry as configuration. The application reads the registry; no code path hardcodes per-tenant behaviour. Adding a tenant to an existing regional stack is an idempotent provisioning workflow. Adding a region is a separate infrastructure event, scoped explicitly when a customer's residency requirement crosses an existing region boundary.
  - Reasoning: Onboarding through configuration scales; onboarding through deployment does not. The architectural commitment that adding a tenant requires no code changes is what makes the platform sellable to enterprise customers with custom IdP, jurisdiction, and classification requirements. Distinguishing tenant-add from region-add prevents over-claiming.
  - Alternatives considered: Conflate tenant and region provisioning into one workflow. Rejected because they have different actors, different lifecycles, and different cost profiles.

- **D14: Customer-specific behaviour is configuration; capability extensions are bounded** (Pre-S2 charter edit)
  - Choice: The platform exposes parameters, schemas, and tool integration points that cover the large majority of per-tenant requirements. Tools (external services called by the platform on the tenant's behalf) are the primary mechanism for customer-supplied logic and are configuration, not code. Extension points exist for the residual cases where logic must run inside the platform with access to internal state; extensions are versioned, sandboxed, and isolated per tenant, and are bounded to a small named set of interfaces (RetrievalClient, scorer, pre-processor). Forking the platform codebase for customer-specific logic is forbidden.
  - Reasoning: Configuration-only positions cannot survive contact with enterprise customers; codebase-forking destroys the platform. The middle path (configuration first, tool calls for most customer logic, sandboxed extensions for the residue) is the position every mature platform vendor converges on. Setting the boundary now prevents the rot.
  - Alternatives considered: Pure configuration with no extension surface (insufficient for enterprise). Open extension surface with arbitrary plugin points (becomes a fork farm). Rejected.

- **D15: Default development model is Qwen 2.5 7B** (Package P2, pre-S6)
  - Choice: Qwen 2.5 7B served via Ollama is the default model for development and the eval harness baseline.
  - Reasoning: Tool-calling fidelity matters once the agent surface lands, and Qwen 2.5's tool-call behaviour is more reliable than Llama 3.1 at comparable memory cost. Reversible if the eval harness surfaces problems.
  - Alternatives considered: Llama 3.1 8B (conservative default, weaker tool calling). Rejected on tool-call grounds.

- **D16: Codebase structure is bounded contexts on hexagonal, with platform / contexts / shared_kernel separation and import-linter enforcement** (Package P2, pre-S7)
  - Choice: The codebase organizes around bounded contexts at the top level (`contexts/`), with cross-cutting platform concerns (`platform/`), a strictly bounded `shared_kernel/`, and deployable units (`apps/`) that compose contexts and adapters into runnables. Each context internally follows hexagonal layers (`domain/`, `application/`, `ports/`, `adapters/inbound/`, `adapters/outbound/`). Boundaries are enforced by `import-linter` contracts in CI, not by convention. The `shared_kernel/` contains only types that must be referentially equal across contexts (TenantId, Jurisdiction) and forbids Pydantic imports to prevent framework version coupling. Packaging uses uv workspaces, with per-context `pyproject.toml` files added when a context first acquires a third-party dependency that should not bleed across boundaries. The observability split (`platform/observability/` is mechanism, `contexts/observability/` is intelligence) is deliberate: span emission is infrastructure every context uses; trace analysis and recommendation generation are a product feature with their own domain model.
  - Reasoning: Enterprise architecture review requires the answer to "where does retrieval live" to be a single folder, "how is multi-tenancy enforced" to be a build-time invariant, and "how do we swap a vendor" to be a port contract. Organizing by technical layer at the top level fails all three; organizing by bounded context with hexagonal layers within each passes all three. The platform / contexts / shared_kernel split keeps the import graph a DAG. Import-linter turns the architectural rules into CI failures rather than review comments.
  - Alternatives considered: Top-level layered structure (`domain/`, `application/`, `adapters/` at the root). Rejected: scatters each business concern across four directories and produces the modular-monolith-becomes-hairball failure mode. Top-level `ports/` directory. Rejected: ports are owned by the domain that needs them, not global. Pure flat package. Rejected: structurally indefensible at enterprise audit.

- **D17: Contexts communicate via published query APIs for reads and a domain event bus for state changes** (Package P2, pre-S7)
  - Choice: Each bounded context exposes a single `api.py` module at its root containing read-only query methods other contexts may call. State-changing interactions flow through a domain event bus in `platform/events/`: contexts publish events from their domain or application layer, other contexts subscribe through wiring in `apps/`. No context imports another context's internals. The bus is synchronous in-process in Phase 1; the interface is broker-ready so Phase 2 can swap to a real event broker without changing context code. `import-linter` enforces the rule that `contexts/X/*` may import only `contexts/Y/api`, never `contexts/Y/domain` or `contexts/Y/adapters`.
  - Reasoning: "Contexts communicate through ports or shared_kernel" is too vague to defend at audit. The hybrid (queries direct, commands eventful) is the pattern mature platform vendors converge on after the fact and is cheap to adopt now. It reflects Quorum's actual data flow: observability queries trace state on the hot path (read-shaped, latency-sensitive) and reacts to inference completions for recommendation generation (event-shaped, decoupled). Forcing reads through events adds latency without benefit; forcing writes through direct calls couples contexts that should stay separable.
  - Alternatives considered: Direct synchronous calls only (modular monolith, couples deployment). Events for everything (latency on the hot path, no benefit). Rejected on the trade-offs above.

- **D18: Redis is shared between Quorum application use and Langfuse ingestion in development; production Redis topology is deferred** (Package P2, Session 4)
  - Choice: A single Redis instance serves both Quorum application caching and queueing (DB 0) and Langfuse ingestion queueing (DB 1) in the local Compose stack. The configuration interface (per `platform/config/`, landing in S5) is structured so production deployments can resolve Quorum Redis and Langfuse Redis to either the same instance or separate instances by configuration, without code change.
  - Reasoning: Local development cost favours sharing; production posture depends on factors (queue depth, eviction policy compatibility, security boundary requirements) that are not yet known. Forcing a production decision now would commit on missing information. The architecture commits to the configuration interface that defers the decision cleanly.
  - Alternatives considered: Separate Redis instance for Langfuse from inception. Rejected: doubles development cost without benefit at this stage. Shared instance hardcoded with no config swap path. Rejected: forces production into a posture that may not fit.

- **D19: Configuration is read through `platform/config/` exclusively, no direct `os.getenv` or `.env` reads** (Package P2, Session 5)
  - Choice: A single `platform/config/` module is the only place secrets and environment-derived configuration enter the application. Pydantic Settings is the dev-time implementation, reading from `.env`. Production reads from a secret manager via the same `Settings` interface. `import-linter` contract forbids `os.getenv` outside `platform/config/`. Settings classes are per-concern (`InferenceSettings`, `ObservabilitySettings`, etc.), not god-objects.
  - Reasoning: "Secrets in `.env`" without an enforcement mechanism is a development convenience that pretends to be a security posture. The unified config interface is what makes "production swap is configuration not refactor" true on the secrets path. Pydantic Settings is chosen because it composes source priorities (env vars, dotenv, secret-manager-shaped backends) through a stable interface and is well-understood at audit.
  - Alternatives considered: Direct `os.getenv` calls (no enforcement, retrofits expensively). Per-context config modules (fragments the audit surface). Custom secrets layer (reinvents Pydantic Settings poorly).

- **D20: TLS configuration is read through `platform/config/`, dev profile defaults to plaintext for Compose-internal traffic, prod profile defaults to mTLS with no plaintext escape hatch** (Package P2, Session 5)
  - Choice: Every adapter that opens a network connection reads its TLS configuration through `platform/config/`. The dev profile resolves to plaintext for Compose-internal traffic (mkcert TLS at the Caddy edge stays in place). The production profile resolves to mTLS with private CA bundles. There is no code path that bypasses TLS in production; the production profile has no plaintext option.
  - Reasoning: The internal/external network distinction does not survive defence-in-depth review. ISO 27001 Annex A 8.20 explicitly requires controls on internal networks. Forcing TLS configuration through the unified config interface means the dev and production postures are profile selection, not code change.
  - Alternatives considered: Plaintext internal in production (rejected: fails Annex A 8.20). Per-adapter TLS configuration (rejected: fragments the audit surface). Service mesh (deferred: appropriate for production but premature in Phase 1).

- **D21: Field-level encryption uses envelope encryption via `platform/security/crypto.py`** (Package P2, Session 5)
  - Choice: Field-level encryption is implemented in `platform/security/crypto.py` using envelope encryption: a Key Encryption Key (KEK) wraps per-row Data Encryption Keys (DEKs); only DEKs touch field data. Field categories requiring crypto: per-tenant credentials, customer PII, audit log integrity hashes. The dev profile uses a fixed KEK from `platform/config/`. The production profile resolves the KEK to a KMS-managed key. The KMS vendor is deferred until production deployment context exists. Production crypto design is a candidate for explicit external review when production deployment context lands.
  - Reasoning: Disk-level encryption (platform-provided in production) protects against disk theft. Field-level encryption protects against database compromise where the attacker has DB credentials but not application crypto state. SOC 2 confidentiality, ISO 27001 Annex A 8.24, and sector frameworks like HIPAA all require field-level for sensitive categories. Envelope encryption is the standard pattern because it confines KEK use to the wrapping operation, allowing per-row key rotation without rewrapping the entire dataset.
  - Alternatives considered: Direct field encryption with a single key (rejected: no per-row rotation, larger blast radius). Application-transparent encryption via the database (rejected: couples to specific DB vendor and does not protect against DB credential compromise).

- **D22: Audit logging is a bounded context (`contexts/audit/`) with hash-chained append-only storage** (Package P2, Session 5)
  - Choice: Audit is a bounded context, not platform plumbing. `contexts/audit/` contains the domain model (AuditEvent value object, hash-chaining logic), the port (`AuditPort` for emitting events), and adapters. P2 ships with a no-op adapter for use in S6/S7. The real adapter (writing to a tenant-scoped append-only Postgres table with hash chaining) lands in P3 when the tenant registry exists. Schema: actor (user or system), tenant_id, jurisdiction, timestamp, action_verb, resource_type, resource_id, before_state (JSONB), after_state (JSONB), correlation_id, previous_event_hash, this_event_hash. Hash chain provides tamper-evidence: any insertion or modification breaks the chain at and after the affected entry, detectable by chain verification.
  - Reasoning: Audit data is tenant-scoped and has its own domain logic (querying, integrity verification, retention enforcement); it is a bounded context by the same criteria that make observability one. Hash chaining is the lowest-cost tamper-evidence mechanism that provides real audit value; full append-only storage with cryptographic signatures is overkill at this stage and can be added later by extending the chain logic. SOC 2 CC7.2, ISO 27001 Annex A 8.15, and sector framework per-record requirements all converge on this shape.
  - Alternatives considered: Audit as platform plumbing (rejected: tenant-scoping makes it a context). External audit service (rejected: introduces a dependency that does not earn its keep at Quorum's stage). No tamper-evidence (rejected: insufficient for SOC 2 and ISO 27001).

- **D23: Authentication and authorization are platform concerns; no endpoint ships without auth middleware** (Package P2, Session 5)
  - Choice: `platform/security/auth.py` provides the authentication interface. `platform/security/policy.py` provides the authorization interface. Both have dev backends (signed-token AuthN, single-tenant-single-role policy) and Keycloak-shaped production backends stubbed. The FastAPI surface in S7 ships with authentication middleware in front of every endpoint from the first commit. Policy checks gate every tenant-scoped operation. Privileged actions (admin operations, cross-tenant access) emit security events in addition to audit events.
  - Reasoning: Endpoints without authentication middleware ship in development and stay in production. The architectural rule is that the middleware is non-removable, enforced by an integration test that fails if any FastAPI route is reachable without it. Policy-as-code (rather than role-baked-into-handlers) is what makes per-tenant authorization tenable at scale.
  - Alternatives considered: Auth as middleware on a per-router basis (rejected: opt-in security is no security). Authorization in handlers (rejected: scatters the policy surface, fails audit). External authorization service (deferred: appropriate at scale, premature in Phase 1).

- **D24: Tenant isolation is verified by `tests/contract/tenant_isolation/` against every adapter touching tenant-scoped data** (Package P2, Session 5)
  - Choice: Cross-tenant access tests live in `tests/contract/tenant_isolation/`. They are red-team shaped: each test attempts unauthorized cross-tenant access and asserts the access fails. The harness is scaffolded in S5 with one example test against the no-op audit adapter. Every adapter that touches tenant-scoped data must have isolation tests in this directory. CI fails if a tenant-scoped adapter ships without corresponding isolation tests, enforced by a coverage rule (any module under `contexts/*/adapters/` referencing tenant_id must have a test under `tests/contract/tenant_isolation/`).
  - Reasoning: Tenant isolation by assertion is tenant isolation by hope. SOC 2 confidentiality, ISO 27001 Annex A 8.3, and the database-per-tenant principle (D1) all require verification, not declaration. Red-team shaped tests catch the failure mode the architecture is most exposed to: unintended cross-tenant data flow through poorly-scoped queries.
  - Alternatives considered: Manual review only (rejected: not durable). Property-based isolation testing (deferred: complementary, not replacement, and premature at Phase 1).

- **D25: Supply chain hardening: image digest pins, dependency lockfiles, vulnerability scanning, SBOM, scheduled monitoring of high-velocity dependencies** (Package P2, Session 5)
  - Choice: Container images pin to SHA256 digests in `compose.yaml` and any production manifests. Python dependencies pin via uv lockfile (lands in S7 with the FastAPI skeleton). Vulnerability scanning runs via `make scan`: Trivy against pulled images, `pip-audit` against Python deps. CI fails on critical CVEs (severity threshold configurable, default critical-only). SBOM generation is scaffolded as a Make target in S5 and emits real SBOMs from S7 onward. Scheduled dependency monitoring for high-velocity dependencies is part of supply chain hygiene; the first instance is monthly Langfuse patch checking, established at S4 close. Scheduled checks open digest-bump PRs with changelog excerpts and breaking-change flags; the operator reviews and merges; no auto-merge. Local CI runs via `make scan`; remote CI deferred to first remote deployment.
  - Reasoning: ISO 27001 Annex A 8.30 (outsourced development), 8.8 (vulnerability management), and SOC 2 CC8.1 (change management) all converge on supply chain controls. Digest pinning prevents image-tag mutation attacks and forces explicit upgrades. SBOMs are increasingly expected by enterprise procurement. Scheduled monitoring catches version drift before it becomes a CVE response.
  - Alternatives considered: Tag pinning only (rejected: tags mutate). External SCA service (deferred: appropriate at scale, premature now). No SBOM (rejected: enterprise procurement increasingly requires). Auto-merging dependency updates (rejected: removes operator judgment from a security-relevant change).

- **D26: Security events log separately from application logs via `platform/observability/security_events.py`** (Package P2, Session 5)
  - Choice: `platform/observability/security_events.py` provides a `SecurityEventLogger` interface. Event categories: auth_failure, authz_denial, config_change, tenant_scope_violation, privileged_action. Local backend writes structured JSON to `logs/security.jsonl` (separate from application log path, gitignored). Production backend ships to a SIEM, vendor deferred. Every auth middleware execution, every policy check, every audit log write also emits a security event for the corresponding category when applicable.
  - Reasoning: Application logs and security events have different lifecycles (application logs rotate, security events retain), different consumers (operators vs. security analysts vs. auditors), and different requirements (verbose vs. structured-and-filtered). Conflating them produces logs that are too verbose for SIEM and too sparse for debugging. SOC 2 CC7.2/CC7.3 and ISO 27001 Annex A 8.16 both require dedicated security monitoring.
  - Alternatives considered: Single log stream with severity tagging (rejected: SIEMs do not consume well, retention policies conflict). External security event service (deferred: appropriate at scale).

- **D27: OTel is the observability portability boundary; vendor-specific observability code is confined to adapters** (Package P2, Session 5)
  - Choice: All observability emission in `platform/observability/` and in `contexts/*/` uses OpenTelemetry APIs with GenAI semantic conventions. Langfuse-specific code is confined to `contexts/observability/adapters/outbound/langfuse/` and contains only the OTLP exporter configuration and the trace-query adapter for the read path. The OTLP collector endpoint is read through `platform/config/`. Switching to a different OTel-consuming observability tool is a configuration change plus a trace-query adapter rewrite.
  - Reasoning: D7 commits to self-hosted Langfuse 3 with OTel GenAI conventions. The portability claim that follows from that commitment needs to be explicit and architecturally enforced, or it decays into vendor lock-in by accretion. OTel as the wire protocol is the portability mechanism; the adapter pattern is the structural enforcement. OTel has consolidated as the cross-vendor observability standard, meeting the optionality principle's threshold for committed adoption.
  - Alternatives considered: Langfuse SDK directly in domain code (rejected: vendor lock-in by import). OTel emission with no architectural constraint on Langfuse-specific code (rejected: Langfuse-specific code spreads, swap cost rises).

- **D28: Python package is named `zephyr` to decouple implementation namespace from product name and resolve stdlib collision** (Package P2, pre-S6)
  - Choice: The top-level Python package is named `zephyr` (Esperanto for "north," continuing the navigation-theme lineage of the Quorum project name). The product name "Quorum" remains in user-facing surfaces, charter strategic framing, and external references; the package name `zephyr` is the implementation namespace. From this commit forward, charter decisions and working docs refer to `zephyr/config/`, `zephyr/security/`, `zephyr/observability/` as the file-path locations of the cross-cutting layer. Historical D-entries (D16, D19–D27) retain their original `platform/` wording as append-only record; the architectural concept they describe is unchanged.
  - Reasoning: The original `platform/` package name collides with Python's stdlib `platform` module, requiring a `conftest.py` shim as workaround. Trademark uncertainty around "Quorum" makes a package name tied to the product name a future-rebranding risk. Decoupling the package name from the product name protects against both: stdlib collision goes away with the rename, and a future product rename does not require touching every Python file.
  - Alternatives considered: `core_platform` (still contains the colliding word, generic, weak). `quorum` (couples package to potentially-changing product name). Other navigation-theme names (`compass`, `bearing`) lack the personal resonance and language-specific distinctiveness.

- **D29: Product name changes from Quorum to Zephyr** (Package P2, post-S6)
  - Choice: The product name is Zephyr from this commit forward. The package name was already `zephyr` per D28; the product and package names now align. User-facing surfaces (README, charter strategic framing, future UI copy, customer-facing communications) refer to Zephyr. Historical D-entries and session log reflections retain their original "Quorum" wording per the append-only principle in `principles.md`. The original D28 text, which committed to Quorum as the user-facing product name, stands as written.
  - Reasoning: The trademark uncertainty around "Quorum" cited in D28's reasoning has resolved, and the package-name decoupling D28 introduced means the product rename touches user-facing surfaces, charter narrative, operational defaults, and one config class name, but not the import namespace. "Zephyr" (Esperanto for "north") carries personal resonance for the operator and continues the navigation-theme of the package name. The decision is recorded as a charter D-entry rather than absorbed silently because future audits need a single locatable explanation for why the product name changes between commits visible in git history.
  - Alternatives considered: In-place edits to historical D-entries and session reflections (rejected: violates the append-only principle in `principles.md`, destroys audit-trail value, and the "one-time exception" framing is precisely how append-only erodes). Carrying forward both names in user-facing surfaces during a transition period (rejected: the project is pre-customer, no external surface depends on either name, clean break is cheaper than dual-naming).

- **D30: uv workspace topology — root pyproject is the cross-cutting platform package; bounded contexts and apps are workspace members** (Package P2, Session 7)
  - Choice: The repo-root `pyproject.toml` represents the `zephyr` cross-cutting platform package: it carries the runtime dependencies for `zephyr/config/`, `zephyr/security/`, `zephyr/observability/`, `zephyr/events/`, and `shared_kernel/`. Bounded contexts (`contexts/inference`, `contexts/observability`, `contexts/audit`) and deployable apps (`apps/api`) are uv workspace members declared in `[tool.uv.workspace]`, each with its own `pyproject.toml` declaring only the third-party dependencies that context or app uses. Members use `[tool.uv] package = false` so they are dependency-tracked but not built as wheels in dev — Python imports continue to resolve through `pythonpath = ["."]` in the root pytest config, which keeps the import-linter root packages and the AST enforcement walkers unchanged. Cross-context imports continue to be policed by import-linter (D16, D17) regardless of workspace topology; the workspace topology adds the second layer of enforcement at the dependency-manifest level.
  - Reasoning: The bounded-context boundary (D16) is enforced at the import level by import-linter; the workspace topology adds a second, complementary layer of enforcement at the dependency level. Declaring `litellm` only in `contexts/inference/pyproject.toml` and `langfuse` only in `contexts/observability/pyproject.toml` makes a vendor SDK leaking into another context a manifest-resolution failure, not just an import-linter failure. Keeping `zephyr/` (and `shared_kernel/`) at the workspace root rather than as members of their own avoids further pyproject proliferation for cross-cutting code that has small, shared third-party deps and is referenced by every context anyway. Apps land as members because each app is a distinct deployable unit with its own dependency profile (FastAPI for `apps/api/`, Vite for the future UI app, etc.).
  - Alternatives considered: Each cross-cutting concern (`zephyr/config`, `zephyr/security`, `zephyr/observability`, `zephyr/events`) as its own workspace member (rejected: forces pyproject proliferation without dependency-scoping benefit, since zephyr/ runtime deps are small and uniformly shared by every context). Only a root pyproject with no members and dependency-groups instead (rejected: defeats the per-context dependency-scoping commitment, leaves boundary enforcement only at the import level). `apps/api/` as a non-packaged consumer outside the workspace (rejected: loses uv's editable-install benefits for dev iteration on the app while still depending on workspace members).

- **D31: Package-level archive document at every package close from P2 forward** (Package P2, retrospective)
  - Choice: Every package from P2 onward produces an archive document at package close, written to `docs/archive/packages/pN.md`. The archive contains the package goal, sessions shipped, architectural commitments landed, stack state at close, data surfaced, drift surfaced, durable lessons, what the package leaves to the next, and convention changes. P1 retains no archive (the audit-time-only convention applied at P1 close, before this convention was settled). The cost calibration of the per-package archive convention is revisited at the Phase 1 close audit; if archive documents prove ceremonial in P3 through P5, the convention is reviewed.
  - Reasoning: Mid-phase package retrospectives produce synthesis with standalone value. P1 was structurally light enough that the absence of an archive has not bitten; P2 produced 16 D-entries, two AST tests, fourteen import-linter contracts, one rebrand, three durable lessons, and four drift candidates, which is enough material that the synthesis has audit value beyond the session log entries. Locating the synthesis across S4 through S8 session entries every time someone asks is reconstruction work the operator pays repeatedly. The archive document is the cheapest way to make that work payable once. The wording in `principles.md` ("Old content moves to archive at audit time, never deletes") becomes more permissive: "audit time" now includes package close from P2 forward. The principles wording itself is reviewed at phase audit if the convention sticks.
  - Alternatives considered: Defer all archives to phase audit (rejected: P2's material has standalone value that erodes if locked behind a phase audit twelve sessions away). Archive only at certain packages chosen ad hoc (rejected: ceremony question gets re-asked every package; better to settle the convention and revisit at phase audit). Treat the session log as the archive (rejected: session log entries are session-shaped, not package-shaped, and force per-audit reconstruction).

- **D32: Per-tenant Postgres instance topology — separate instances, two at P3 open for the test set, instance creation deferred until production deployment context** (Package P3, Session 9)
  - Choice: Each tenant has its own Postgres instance. P3 opens with two instances (`postgres-tenant-a`, `postgres-tenant-b`) seeded as tenants in the registry, joining a dedicated `postgres-control-plane` instance per D33. The provisioning workflow (registry insert, instance connection, control-plane row creation, schema migration) is exercised against these existing instances rather than against instance creation. Adding tenants beyond the two in Phase 1 requires editing Compose; instance creation as an automated step lands when production deployment context arrives and infrastructure-as-code is real.
  - Reasoning: D1 commits to database-per-tenant; the topology question (single instance with database-per-tenant logical separation versus separate instances) was open. The operator chose separate instances at the P2 retrospective on enterprise-grade learning grounds: running multiple Postgres instances locally exercises the routing layer under realistic conditions and makes the database-per-tenant claim concrete rather than theoretical. The cost is one more Postgres instance per tenant in the local Compose stack and a more substantial routing layer (per-tenant connection details in the registry, credential encryption per D21). Two test tenants at P3 open is sufficient to exercise the routing, isolation, and migration paths without committing to a dynamic-Compose pattern that has limited production analogue.
  - Alternatives considered: Single Postgres instance with logical database-per-tenant separation (rejected: lower local cost but does not exercise the routing layer or the credential-decryption path under realistic conditions; the architectural commitment to enterprise grade favours the more substantial routing). One instance at P3 open with provisioning workflow creating instances dynamically (rejected: dynamic-Compose pattern in dev does not match production posture, where instances are created by infrastructure-as-code; the local-versus-production gap is harder to absorb than the current Option A breach of D13 which is recoverable when production deployment lands).

- **D33: Control-plane database lives on a dedicated Postgres instance, separate from tenant data planes** (Package P3, Session 9)

- **D34: Credential encryption integration shape and three-control leak prevention** (Package P3, Session 10)
  - Choice: The tenant registry adapter integrates envelope encryption from `zephyr/security/crypto.py` (D21) on the credential write and read paths. Plaintext `TenantConnectionConfig` enters the adapter as input to `register_tenant`, is wrapped via `encrypt_field(plaintext_bytes, context={"tenant_id": ..., "purpose": "tenant.credentials.v1"})` before any I/O, and only the encrypted bytes touch Postgres. Read-back reverses the path: rows return `EncryptedCredentials`; the use case at the application layer unwraps to `TenantConnectionConfig` only when an operator-context caller invokes `reveal_connection_config`. Plaintext lives only in function-local variables, never in instance state, never in logs. The frozen-aggregate-plus-Core pattern is the right shape for hexagonal: the adapter owns the impedance mismatch, the domain stays pure, no ORM identity map tax, and decryption happens in Python after the row is fetched (asyncpg's prepared-statement cache returns bytea as `bytes` regardless of cache state, so caching is irrelevant to decryption correctness).

The AST test makes future plaintext-in-state regressions a CI failure, not a review comment. The AAD binding is what makes envelope encryption tenant-safe rather than merely cryptographically sound: without AAD binding, a stolen wrapped DEK from tenant A's row could decrypt tenant A's ciphertext if reattached to tenant B's row; with AAD binding to tenant_id and purpose, the InvalidTag boundary catches the misuse.   - Alternatives considered: Plaintext credentials in Postgres with disk-level encryption only (rejected: D21 commits to field-level for credentials specifically; disk encryption does not protect against DB credential compromise). Separate `AuditOperatorPort` for control-plane mutations (rejected: doubles audit surface for no architectural gain; one port with adapter-level routing is sufficient). - **D37: Audit adapter shape with hash-chain concurrency control and cache deferred** (Package P3, Session 12)
  - Choice: The audit Postgres adapter implements `AuditPort` against per-destination Postgres tables.   - Alternatives considered: Cache the last-written hash in adapter memory (rejected: trades correctness for unmeasured performance; deferred until measurement justifies). Serialisable isolation level on the audit transaction (rejected: heavier than needed; SELECT FOR UPDATE on the chain-tail row is sufficient). Advisory locks for concurrency control (rejected: more complex than row-level locking and adds a second mechanism alongside the existing transaction model). Omit `tenant_id` from per-tenant rows (rejected: cross-database queries need it; denormalisation cost is zero). Drop the cross-destination CHECK constraints (rejected: schema-layer defense complements the routing if-statement at zero runtime cost).

- **D54: Applier port shape — single polymorphic async ApplierPort with applier_type dispatch in the adapter** (Package P5, Session 16, 2026-05-06)
  - Choice: ``ApplierPort`` is a single async Protocol with the signature ``async def apply(*, interaction: Interaction, output: str, criterion: Criterion, applier_config: ApplierConfig) -> str | None``. A single polymorphic adapter (``ExactMatchApplier`` at ``contexts/evaluation/adapters/outbound/exact_match_applier.py``) implements the port and dispatches on ``applier_config.applier_type``: deterministic resolves the function name against the deterministic-library registry at ``contexts/evaluation/adapters/outbound/deterministic_library.py`` and invokes it; prompt and human raise ``NotImplementedError`` at S16 (prompt lands at S17 LLM-as-judge per D53; human is data-substrate-only per D53's Reading-C posture and never invokes the port). The use case at ``contexts/evaluation/application/apply_scoring_sheet.py`` is indifferent to applier mechanism — it asks "score this output against this criterion," receives a score string, and constructs the ``RubricApplication`` from that plus the context it already holds (interaction, criterion, applier id, revision id). Build-time deviation from S16 framing: the framing's recommended return type was ``RubricApplication``; we landed ``str | None`` because the applier should not own record assembly (the persistence-layer fields ``id`` and ``created_at``, plus context fields like ``interaction_id`` the applier has no opinion about, leak into the port if the port assembles the record). The use case is the structural authority on RubricApplication construction; the applier is the structural authority on scoring. The honest split lives at the score type, not at the record type.
  - Reasoning: D53 frames appliers-as-data; the use case is indifferent to applier mechanism, so a single polymorphic port matches that indifference. Two typed sub-ports (``DeterministicApplierPort`` sync + ``PromptApplierPort`` async) would push dispatch knowledge up the stack — the use case would route on ``applier_type`` itself, which is the kind of detail the port exists to hide. Async at the port level is forward-compatible with the LLM-as-judge applier landing at S17. The build experience supports the choice: at one concrete deterministic adapter (S16's ``exact_match``), the dispatch logic in ``ExactMatchApplier.apply`` stayed mechanical — a simple ``if/elif`` over the three ``ApplierType`` values, with the deterministic branch resolving against the small registry and the other branches raising. No domain-shaped knowledge leaked into the dispatch; the choice of executable behaviour was data, exactly as D53 framed it. Dispatch-mechanical contingency carried over from framing: if at S17's prompt-applier addition the switch logic begins encoding domain knowledge (e.g. needing criterion shape to pick a function, or needing tenant context to pick a judge model), this commits revisits at S17 framing. At S16 the contingency does not bite. Return-shape choice (``str | None`` rather than ``RubricApplication``) is the structurally honest split between scoring (the applier's responsibility) and record assembly (the use case's responsibility); ``None`` is reserved for the human-applier mode that never invokes the port at S16 but may return null automated_score in future flows where the applier explicitly defers to human review.
  - Alternatives considered: Two typed sub-ports — DeterministicApplierPort (sync) + PromptApplierPort (async) (rejected: pushes dispatch into the use case for no test-level benefit; the use case's indifference to applier mechanism is a feature of the appliers-as-data framing, and routing on applier_type at the use-case layer would invert that). Single sync port with the adapter wrapping LLM calls in run_in_executor (rejected: blocking adapter pattern is anti-FastAPI-async; LLM calls dominate runtime at S17 onward and forcing them through a sync-bridge is paper architecture). Return type ``RubricApplication`` per the framing prompt (rejected at build per the reasoning above; the structural split between scoring and record assembly is cleaner at the score type, and the port stays free of persistence-layer concerns the applier does not own). Adapter-per-applier-type (one adapter for deterministic, one for prompt, one for human; rejected: the use case would need to know which adapter to dispatch to, which is the appliers-as-data framing inverted; a single polymorphic adapter with internal dispatch is the structurally honest shape for "the executable behaviour is data the adapter reads"). Static dispatch on applier_type via match statement instead of if/elif (acceptable shape variant; current if/elif chosen for trivial readability difference at three values).
  - Kano: performance.

- **D55: Score representation on rubric_applications — text with criterion-level interpretation** (Package P5, Session 16, 2026-05-06)
  - Choice: ``automated_score`` and ``human_score`` on ``rubric_applications`` are TEXT columns. Score interpretation is criterion-level: each criterion's ``levels`` jsonb encodes the level definitions (label-plus-definition pairs), which downstream consumers (cost-per-successful-task at S17, regression report at S18, recommendation surface at P11) read to determine pass/fail, threshold breaches, or aggregations. SQL aggregation across rubric_applications requires explicit casting plus criterion-level filtering; direct ``AVG(automated_score)`` is foreclosed and is not the intended access pattern. The criterion is the architectural authority on what its scores mean, and the harness's downstream metric implementations read the criterion's level definitions to determine "successful," "threshold breach," or "aggregation method" rather than relying on a generic numeric default.
  - Reasoning: Rubric heterogeneity is real. Production scoring sheets use numeric scales (1–5 Likert), categorical labels (pass/fail, yes/no/partial), and continuous similarity scores (0.0–1.0). The text representation preserves all three shapes at one column cost — no schema split, no NULL columns for scoring shapes a particular criterion does not use, no implicit numeric default that pretends pass/fail rubrics are just "1 or 0." The foreclosure of direct SQL aggregation is the trade-off accepted: criterion-level interpretation lives where the criterion is defined, which is the right architectural authority on what its scores mean. S17's cost-per-successful-task implementation reads the criterion's level definitions to determine "successful," and S18's regression report reads them to determine threshold breaches; this is more honest than a numeric default that pretends every rubric is comparable on a uniform scale. Locking the choice in at S16 prevents a quality-foreclosing default leaking into the schema; superseding D55 later would require a migration on every rubric_applications row, which is the kind of avoidable retrofit D41 named explicitly as a learning failure when the case study commits to its audit posture.
  - Alternatives considered: Numeric column plus text label (rejected: two columns where one suffices when criterion encodes interpretation; categorical-only criteria still need the text path; the column split implies a runtime split that is paper architecture). Jsonb discriminated type (e.g. ``{"kind": "numeric", "value": 4}`` vs ``{"kind": "categorical", "value": "pass"}``) (rejected: opaque to SQL beyond extraction, query cost compounds at the optimization-recommendation layer, flexibility unused at any concrete criterion shape since each criterion already declares its level shape via ``levels``). Numeric only (rejected: forecloses categorical and binary scoring without ad-hoc encoding; pass/fail rubrics are common in procurement-grade evaluation where the binary outcome is exactly what matters). Numeric with criterion-level scaling map at write time (rejected: pushes coercion into criterion authoring; criterion writers should describe levels with definitions, not encode them onto a numeric scale chosen for SQL convenience). Enum types via Postgres ``CREATE TYPE`` (rejected: cross-criterion enum sharing forces every criterion's level set into a single global enum, which collapses the criterion-as-authority framing; per-criterion enum types proliferate type definitions without benefit).
  - Kano: must-have. The choice constrains every downstream consumer of rubric_applications; locking in at S16 prevents a quality-foreclosing default leaking into the schema, and the foreclosure of direct SQL aggregation is the structural trade-off the case study commits to in exchange for honest cross-rubric scoring.

  - Choice: The regression report compares two runs (baseline revision vs candidate revision) of a scoring sheet against the same interaction set. ``RegressionReport`` carries ``baseline_revision_id``, ``candidate_revision_id``, ``interaction_set_id``, a tuple of per-criterion deltas, aggregate metrics, and a ``generated_at`` timestamp. ``CriterionDelta`` carries ``criterion_name`` (the join key across revisions; criterion ids differ because each revision creates fresh criterion rows), per-side success rates, the rate delta, and per-side application counts so consumers can distinguish "no data" from "all failures". ``AggregateMetrics`` carries the overall counts, success-rate, and cost-per-task on each side plus the cost-per-task delta. The asymmetric-criteria handling — a criterion that exists only in baseline or only in candidate produces a ``CriterionDelta`` with zero on the missing side and the per-side counts to interpret it — is honest about the structural absence rather than fabricating a delta that hides the renaming. Build-time field-name and field-set refinements from the brief land per the methodology's framing-prompt-as-recommendation pattern: brief specifics name an option space and the strongest recommendation; build commits to the choice with whatever refinements the actual code surfaces; the D-entry records both. JSON-only output (rejected: text rendering for the CLI operator is load-bearing for case-study posture; the harness should be operable without programmatic tooling). Text-only output (rejected: programmatic consumers at P11 need the structured shape; rendering JSON from text is parse-error-prone). Joining criteria by id rather than name across revisions (rejected: ids change across revisions per D53's immutability commitment; the join would always produce zero per-criterion deltas with both ids present in the union, making the report useless). - **D59: Langfuse trace-ingestion asynchrony — polling-with-timeout at the cost-query path** (Package P5, Session S18, 2026-05-06)
  - Choice: Cost queries that may target recently-emitted traces wait for trace availability via polling. ``LangfuseHTTPTraceQueryAdapter.wait_for_trace_availability(trace_id, tenant_context, *, timeout_seconds=30.0, poll_interval_seconds=1.0)`` polls ``get_trace`` (which applies the tenant.id span-attribute filter per D50) until the trace becomes queryable or the timeout elapses; returns True on availability, False on timeout. The CLI runner at S18 invokes this helper between OTel force-flush and the first cost query, once per unique trace_id produced by the replay flow. The 30-second default is conservative for CLI flows; programmatic consumers can tune via parameters. Polling uses ``get_trace`` (not the lower-level ``_fetch_trace``) so cross-tenant probes time out without leaking existence information — a deliberate trade-off that costs one round-trip more per legitimate poll relative to a bare existence check, but preserves D24's tenant-isolation discipline at the polling surface.
  - Reasoning: Langfuse trace ingestion is asynchronous from OTel emission. The OTLP receiver writes to ClickHouse and a worker pipeline materialises the queryable trace on a separate cadence. Consumers that emit a trace and immediately query for its cost (the CLI runner's replay → cost-aggregate flow) hit a race window between OTel export and Langfuse ingestion. S17b worked around this with an 8s force-flush-and-sleep that is brittle: insufficient under variable load (peak ingestion lag can exceed 8s and produce false-empty cost results that the operator misreads as "qwen at zero rates" rather than "trace not yet ingested"); wasteful when ingestion is fast (the 8s sleep is paid even when the trace is queryable in 1s). Polling-with-timeout is honest: it waits exactly as long as needed for fast ingestion and surfaces a clear False return that the caller can treat as a clear failure. The 30-second default reflects the upper bound of the dev-environment ingestion window observed across the S17b-S18 development arc; production tenants with higher ingestion volume tune up, batch-mode programmatic consumers tune down. The two-phase rendering alternative (immediate report with cost-pending sections, follow-up render when costs land) was rejected for CLI flows because the CLI is a one-shot operation; the operator wants a complete report or a clear error, not a partial result they have to re-query. The two-phase shape makes sense for streaming UI surfaces at P11 but not at S18. The webhook/push alternative (Langfuse pushes "trace ready" events to Padhanam) was rejected because it requires Langfuse-side configuration not in the case study's control, and breaks D27's vendor-portability posture (any backend swap would need to re-implement the push).
  - Alternatives considered: Sync wait at a fixed sleep duration (rejected: brittle under variable Langfuse load; 8s might not be enough at peak ingestion lag and is wasteful at quiet times; this is exactly the S17b shape that surfaced the asynchrony problem and motivated D59). Two-phase rendering with cost-pending sections (rejected: complicates the CLI surface; one-shot CLI operations want complete results; the two-phase shape makes sense for streaming UI surfaces at P11 but not at S18). Webhook/push from Langfuse (rejected: requires Langfuse-side configuration not in the case study's control; breaks D27's vendor-portability posture; would force re-implementation on every backend swap). Polling without tenant filter (rejected: cross-tenant probes would leak existence information through the polling-availability response; the tenant.id filter on ``get_trace`` keeps the polling consistent with the cost-query path's tenant-isolation discipline). Polling at the application-layer use case rather than the adapter (rejected: the polling shape is vendor-quirk-specific to Langfuse's async-ingestion behaviour; a backend that materialises traces synchronously needs no polling. Adapter-level placement keeps the vendor knowledge confined per D27). Adding ``wait_for_trace_availability`` to the ``TraceQueryPort`` Protocol (rejected at S18: only the Langfuse adapter needs it at one consumer; promoting to the port for one consumer is paper architecture, and the recommendation engine at P11 will likely need a different shape — recently-traces-since-checkpoint or watch-for-new-trace — that warrants its own port method when the consumer arrives. If a second polling consumer arrives without a different shape, port promotion lands at that session's framing).
  - Kano: must-have. Without a documented asynchrony handling, every cost-query consumer reinvents the pattern, and the case study posture cannot honestly claim "cost-aware optimization recommendations" at P11 if cost-query results are race-condition-prone. The S17b 8s force-flush-and-sleep already exposed the fragility; D59 commits the architectural shape that consumers from S18 forward inherit. The structural-promotion threshold from the methodology applies asymmetrically here: this is a corrective discipline-addition (S17b's brittle workaround surfaced a real failure mode), so it lands on first observation rather than waiting for recurrence — same shape as the methodology's Failure-modes entries that land on single instance per the discipline-vs-pattern asymmetry.
