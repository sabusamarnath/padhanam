**D126: ActorContext shared-kernel value object, authorisation decorator at the use-case boundary, and ActorReference retention as persisted authoring identity.** Bundled D-entry covering the Phase 2-A actor-identity and authorisation substrate per the Decision 7 forward-compat substrate-depth classification. The framing-time bundle was a two-sub-commitment shape (ActorContext plus decorator); S44a pre-write reconciliation reshaped it to three sub-commitments after finding that ActorReference cannot cleanly be superseded by ActorContext at the persisted `authored_by` field. *Sub-commitment 1 — ActorContext.* ActorContext is a frozen dataclass at `shared_kernel/actor_context.py` composing the existing TenantContext as a field plus three fields: `actor_id` (`str`, non-empty — UUID-shaped when derived from the Principal at the HTTP path, a label at the CLI path), `role_list` (`frozenset[str]`, non-empty — Phase 2-A populates `{"operator"}`), and `authorisation_set` (`frozenset[str]` — Phase 2-A populates from the hardcoded role-to-authorisation lookup; may be empty for an actor with no permissions). The compose shape — ActorContext wraps TenantContext rather than subsuming it — preserves single-concern value objects per the hexagonal posture and keeps adapter signatures unchanged: a use case extracts `actor.tenant_context` before adapter calls. ActorContext is the request-scoped value object that flows into every portfolio use case from S44a onward; `__post_init__` enforces the invariants. Pydantic is forbidden in `shared_kernel/` per the `shared-kernel-policed` import-linter contract (D16), so the frozen-dataclass shape is structurally pre-empted, consistent with TenantContext. *Sub-commitment 2 — authorisation decorator.* `requires_authorisation(permission: str)` at `shared_kernel/authorisation.py` wraps a use-case async function whose keyword arguments include `actor: ActorContext`; it checks the required permission string against `actor.authorisation_set` and raises `AuthorisationDenied` (a typed exception in the same module carrying the required permission and the actor_id) when the check fails. The HTTP layer translates `AuthorisationDenied` to a 403 response with the existing `ErrorResponse` shape per D98, registered with the auth-cross-cutting handlers at `apps/api/_auth_errors.py` per D104 — the decorator's exception is auth-cross-cutting (raised by the shared decorator, not by any one router), so it belongs with the D104 auth-cross-cutting error module, not the per-router `apps/api/_errors.py`. The Phase 2-A authorisation policy is hardcoded in `shared_kernel/authorisation.py`: five portfolio permission strings (`portfolio.case.create`, `portfolio.data_point.create`, `portfolio.data_point.revise`, `portfolio.case.list`, `portfolio.case.get`) named once as module constants, and a single-role lookup `{"operator": <the five>}` resolved through an `authorisations_for_roles` function. The lookup lives in `shared_kernel/authorisation.py` rather than at the auth middleware so the decorator applications, the HTTP `get_actor_context` dependency, and the CLI's ActorContext synthesis all reference one source — the CLI synthesises ActorContext without passing through HTTP middleware, so a middleware-local lookup would force the permission set into two places. The richer per-tenant or registry-backed lookup activates at the role-hierarchy deferred-decisions trigger. *Sub-commitment 3 — ActorReference retention as persisted authoring identity.* ActorReference (the minimal `{user_id}` frozen value object at `shared_kernel/actor_reference.py`) is retained unchanged — not deleted, not renamed, not extended — as the *persisted* authoring-identity value object stamped onto `DataPoint.authored_by` and `Assertion.authored_by` and round-tripped through the `authored_by_user_id` column. A use case receives ActorContext and derives `ActorReference(user_id=actor.actor_id)` when stamping authorship on a domain entity or an audit-event draft. ActorReference (persisted identity) and ActorContext (request-scoped capability) are distinct value objects with distinct concerns; the name pair is self-documenting — a *reference* is a minimal identity stamp, a *context* is a rich request envelope. *Supersedes D124's forward commitment on `authored_by` becoming ActorContext.* D124 committed that ActorReference "is superseded at S44 by the full ActorContext per D116 ... the supersession extends shape and home without renaming," covering both the Revisable Protocol's `actor` parameter and the `authored_by` field. S44a pre-write reconciliation found that commitment structurally unsound. The `data_points` and `assertions` tables persist authoring identity as a single `authored_by_user_id` text column; an ActorContext cannot be reconstructed from it — there is no stored `role_list` or `authorisation_set`, the non-empty `role_list` invariant could not be satisfied on read, and a fabricated set would assert a request-time authorisation snapshot that was never recorded. Persisted authoring identity and request-scoped capability are different concerns: freezing `authorisation_set` onto a permanent record would produce a snapshot stale on every subsequent read and would semantically misrepresent identity as capability. D126 therefore supersedes D124's `authored_by` forward commitment — `authored_by` stays ActorReference. The Revisable Protocol's `actor` parameter (D125) likewise stays ActorReference: authorisation is enforced at the use-case decorator before `revise` runs, so the shared-kernel revision-history contract needs only identity, not the authorisation substrate; coupling it to ActorContext would be a layering smell. D124's other commitments stand; only the `authored_by`-and-`actor`-parameter forward commitment is superseded. This is the first instance of a D-entry superseding a forward commitment carried by an earlier D-entry; the supersession is recorded here and D124 is not rewritten, preserving the audit trail. *Alternatives considered.* (a) Subsume ActorContext into a flat envelope replacing TenantContext: rejected — single-concern value objects is the hexagonal posture; the refactor footprint touches every adapter; downcasting at the call seam makes the structural boundary visible. (b) Skip ActorContext entirely, keep ActorReference permanently, place authorisation at HTTP middleware: rejected — HTTP middleware cannot see method-specific permission requirements, and the CLI surface does not pass through HTTP middleware. (c) Inline authorisation checks in each use-case body: rejected — inline checks scatter policy across the application layer, defeating the trivial-check-at-one-boundary commitment from Decision 7. (d) Split into separate D-entries for ActorContext, the decorator, and AuthorisationDenied: rejected on the architectural-bundling test — the decorator cannot ship without the ActorContext fields it consumes, and the exception is structurally inseparable from the decorator. **D153: Threshold-briefing architecture — refresh-then-evaluate scheduled trigger, evaluator over the calendar state store, a narrow calendar must-have set, restraint against the reverse Kano category.** *Mechanism.* ThresholdEvaluator and threshold-briefing are both BroadcastFlow implementers (D142). A scheduled trigger (the `SCHEDULED_EVALUATION` trigger type, added additively to `BroadcastTriggerType` per D142's extension clause) runs refresh-then-evaluate: it syncs the active-rule substrates via consumer ports (the D146 composition pattern, no direct substrate import — the threshold context never imports `sync_calendar`), then ThresholdEvaluator **evaluates over the calendar state store** via a consumer reader port; on a match it emits `THRESHOLD_CROSSED` through a consumer emitter port wired to the D147 FireTrigger flow (fired_triggers idempotency), and threshold-briefing fires on `THRESHOLD_CROSSED`, composing and dispatching the briefing. *Why evaluate over state, not the audit chain (the S57 reconciliation correction).* The epic and the S57 brief both asserted the evaluator polls the *audit chain* for state-change matches. The reconciliation gate falsified that: `sync_calendar` writes only to the meetings store (upsert/tombstone) and emits **no** audit events, so calendar cancellations/moves are not in the audit chain (the only calendar audit events are the `meeting_citation` snapshots the conversation cell emits on a user turn). More fundamentally, **conflict/double-booking was never a state-*change* event** — it is a standing condition over the current meeting set, a query, not an emission. A single coherent model (the evaluator reads current state; both rules are state queries) beats a hybrid that makes cancel/move into audit events but still has to special-case conflict as a store query — and the hybrid would also pull an `AuditPort` + emission logic into the calendar substrate at the exact moment P15 closes against a live-verified foundation. So the evaluator reads the calendar state store; the audit chain records the *outcome* (the BROADCAST_INITIATED + THRESHOLD_CROSSED fire), not the input. *Traceability preserved.* Procurement traceability holds: the `THRESHOLD_CROSSED` crossing carries `rule_id`, `google_event_id`, `cancelled_at`, and the trigger timestamp into its metadata, and the BROADCAST_INITIATED audit event's after_state records that metadata, so the briefing remains traceable to exactly why it fired — only the *input source* moved from chain to store, not the audit record of the crossing. The `THRESHOLD_CROSSED` idempotency key is therefore the crossing's derived-state identity (a cancellation: `rule_id` + `google_event_id`; a conflict: `rule_id` + the unordered event pair), not a matched-audit-event id — same one-brief-per-crossing guarantee, different identity source. *Live-smoke refinement (S57).* The cancellation identity **excludes `cancelled_at`**, and the cancellation scan-window match is **lower-bound only** (`cancelled_at >= window_start`, no upper bound). **D163 — The whole-life goal taxonomy** (the typed model the daily driver's causal graph is built on).

Every goal is placed on three axes. The engine is cadence (repetition) or sequence (a dependency chain). The target either maintains a level (homeostatic), advances a level (progressive, with a ratcheting target), or reaches a point once (terminal). Control says whether the actor's levers determine the outcome, or the actor only influences it while another party determines it.

Three core shapes follow from engine crossed with target. Homeostatic cadence repeats to hold a level: behind means drift, the remedy is to re-establish the rhythm. Progressive cadence repeats to raise a level: behind means not advancing, the remedy is to adjust the target. Sequence releases tasks toward a terminal: behind means blocked, the remedy is to unblock or drop. Real goals are hybrids of these.

Two boundaries bound the model. Below it, the atomic one-off is too small for an outcome and is a tick with no machinery; a multi-step errand stays a tick unless a seam between its steps can stall, and is promoted to a tracked chain on the stall, not on the decomposition. Before it, the exploratory phase has no defined outcome yet, so the work is to converge on the outcome, not advance toward it; the causal graph begins only once the outcome is named.

One variant of homeostatic is the avoidance goal, maintained by not acting and measured in streaks and lapses, where behind is a discrete lapse rather than drift. One higher layer sits above all goals: balance, the allocation across competing outcomes. Balance is a property of the whole set and the daily driver's morning decision, not a goal-shape.

Three mechanics ride on top. The adjustable target makes progressive cadence a live expected-versus-observed loop: the target is the expectation, progress is the observed, the gap moves the target. It is qualitative, not numeric; quantitative inference stays deferred per D156. Remedies must read the shape, because the wrong remedy deletes the wrong things: the S61 drop-if-quiet nudge is a sequence remedy and must not fire on a cadence goal. The subject, self or other, usually decides the control axis.

The model is a graph, not a list. A goal can be a lever toward a higher goal, so the higher layer has two faces: the vertical, goals laddering to life aims, held natively by the graph, and the horizontal, balance across the top nodes.

S62 instances only progressive cadence, self-control, self-subject, through German. All other values are schema-present but uninstanced.

*Step 0 reconciliation (against live code, the S4 safeguard).* The "existing graph interface" is `GraphRepositoryPort` + the `TenantScopedNeo4jSession` wrapper, the single Cypher surface confined to `contexts/ingestion/adapters/outbound/neo4j/` by the `neo4j-confined` import-linter contract and the AST enforcement test (Neo4j 5 Community, no APOC; every node and edge carries `tenant_id` + `jurisdiction`; property-based isolation per D63/D64). The existing `Entity`/`Relationship` value objects cannot carry the lever edge's `mode` + level ladder + current target (a `Relationship` holds only `relationship_type` + `source_chunk_id`; an `Entity` is keyed by `source_chunk_ids` a goal lacks), so the Outcome node and lever-to-outcome edge are a **new typed graph capability added to the same wrapper** (the only legal Cypher home), not a reuse of Entity/Relationship. Commitments live **only in Postgres** (no graph node through S61), so the edge attaches to the commitment by reference: a thin `:Lever {commitment_id}` node — a reference, not a duplicate of the Postgres row — connected to the `:Outcome`, the edge carrying `mode` and (for progressive) the ladder + current target. daily_driver cannot import neo4j (AST/contract) nor ingestion (D17 independence), so it consumes the graph through a daily-driver `GoalGraphPort` + an apps-composition-root bridge to ingestion's new outcome-graph methods — the calendar/email `MeetingGraphIndexPort` + `MeetingGraphIndexBridge` precedent. The goal is a graph node, the lever reuses the `commitments` table, so **no new Alembic migration**; the graph schema lands as a new `migrations/neo4j/0002_outcome_goal.cypher` via the `ops/migrate_neo4j` mechanism.

*Architectural commitments.* New `:Outcome` and `:Lever` node labels and a `LEVER_FOR` edge in the shared graph, all tenant- and jurisdiction-scoped through the existing wrapper; an ingestion-side `OutcomeGraphPort` on the Neo4j adapter; a daily-driver `GoalGraphPort` consumer port + `Goal` domain (the `GoalMode` / `ControlAxis` / `Subject` enums and the `LevelLadder`), all values defined but only progressive/self/self instanced; new `DAILY_DRIVER_GOAL_READ` and `DAILY_DRIVER_GOAL_RAISE_TARGET` permissions on the operator role (the use-case-boundary authorisation pattern, D126). No new import-linter context boundary — the daily-driver consumer-port + apps-bridge seam reuses the D17 pattern. The raise-or-hold recommendation is recommendation-shaped (D9): displayed, applied only on an explicit raise action, never automatically (the no-auto-modification invariant). Quantitative target inference and companion/health data ingestion remain deferred per D156.

*Deferred together.* Every other mode (homeostatic re-establish, sequence unblock-or-drop), the control-and-influence probabilistic-gap semantics, the avoidance variant, the balance layer, and the exploratory phase are schema-present and uninstanced; their remedies arrive at the session that instances a goal of that shape. The strongest second-instance candidate is a sequence goal (unblock-or-drop) or an influence goal (the probabilistic gap); M's Esperanto is the obvious influence candidate but is subject-other.

**D166 — The plan-side work-unit model.** A unit of work is one thing seen from up to four facets: a message that requested it (origin), a task that tracks it (tracking), a calendar block that times it (time), and a goal it serves (purpose). The first three are ingested read-only from the user's tools; the fourth is Padhanam-native. Padhanam's plan-side job is to correlate the facets into one unit and, where a facet is missing, assess whether it should exist and suggest it, recommendation-shaped, never writing to the user's tools.

*Correlation.* The sources share no identifier, so a link is proposed by title and time proximity and must be high-precision and confirm-rather-than-assume, because a wrong link that tracks two unrelated things as one is worse than no link. The link is a Padhanam-native edge, not written back to either tool.

*Suggestions are conditional, not universal.* A task with no time earns a block suggestion only when it is substantial; an atomic one-off does not, because that is the reverse-Kano nag. An event with no task earns a suggestion for the satellite work it implies, the preparation before and the actions after, not a duplicate of the event, which already tracks itself by happening. A unit present in both sources is linked.

*The differentiating assessments.* The two reads that separate Padhanam from a time-blocker are the ones only the goal facet makes: orphan work, a correlated unit that points at no named goal, and the neglected goal, an outcome the user says matters that nothing in the plan points at.

*The plan is a constrained graph of units, not a bag of complete units.* Beyond the single unit the model carries: dependency between units (the sequence engine at plan altitude, crossing goal boundaries); the deadline as a constraint distinct from the block (the dated-terminal shape); capacity as the whole-plan feasibility check (the balance layer made concrete, assessed through the goal so the work that gives when over capacity is the orphan and low-goal work); recurrence (the cadence engine at plan altitude); and waiting-on-others (the influence axis at plan altitude, units owned by another party that can be nudged but not scheduled). Effort, fixed-versus-movable, and priority are properties feeding capacity, not separate facets. Purpose is broader than goal-advancement: maintenance work and owed work serve a real purpose, so the orphan-work read must not flag homeostatic or owed work as purposeless.

*Build sequencing is gated on the Phase 2-A dogfooding week.* The week determines which of dependency, deadline, capacity, recurrence, and waiting-on-others actually bite in real use, and those build first. The model is recorded now; the build follows the week.

*References.* D148, D151, D155 (external-cache ingestion); D17 (cross-context read seam); D156 through D165 (the goal taxonomy the purpose facet draws on); the assess-not-replace principle. *Kano category:* the decision spans two tiers and must not be collapsed to one. Facet correlation and the time-blocking suggestions (the block-for-a-task and satellite-work-for-an-event reads) are **performance-or-parity** — the time-blockers already ship them, so their absence reads as a gap to anyone comparing. The two goal-aligned assessments, orphan work and the neglected goal, are the **delighter** — the thing no tool does, and the reason Padhanam is not a rebuilt Motion. Collapsing the whole decision to performance is the exact move that lets the moat get built as an afterthought to the commodity correlation (the rebuilt-Wingtip Scheduling failure wearing a Kano label instead of a roadmap one); the split directs prioritisation to invest in the half only Padhanam can build. (P16, charter, 2026-06-08)

**D171 — Coverage honesty — the moat reports uncovered, not neglected, outside the linked boundary** (refines D169; **supersedes D169's bare "neglected goal = a goal nothing points at" and "orphan = a unit pointing at no goal" framing**) — an assess-not-replace platform reads only part of the user's world by definition, so its assessment is **valid only inside the boundary of what is ingested and linked**. **D187 — Goal status taxonomy: on-track, behind, stalled, done.** Each goal reads exactly one status, computed in the read/projection layer from its commitments' cadence adherence and its confirmed-edge activity — a read recomputed from the moat each time, never a stored verdict. *The status family is set by the goal's mode (Step-0 reconciled).* The prompt framed cadence vs cadence-less as "a commitment with a rhythm" vs "rhythm-less," but every live goal carries commitments, so the split is by **`GoalMode`**, which matches the intent exactly: a **homeostatic** goal (repeats to *hold* a level — the rhythm *is* the goal) is a **cadence goal**; a **progressive** goal (repeats to *raise* a level, e.g. a language — D187's own cadence-less example is progressive) is **cadence-less**; a **sequence** goal reads **done** when its terminal is reached, else by activity. *Cadence goal → on-track / behind / stalled.* On-track when its lever commitments are within cadence; behind when a lever has missed recent beats but fewer than K in a row; stalled at K consecutive missed beats. A goal with several levers takes the **worst status** (a goal with one dead habit is at-risk, the honest read). Missed beats are computed from the lever's `expected_interval_days` and last completion (`overdue_by_days // interval`), reusing the existing staleness math; on-track when not overdue, stalled when `missed ≥ K`, behind in between. *Cadence-less goal → active / stalled (no behind).* It cannot be behind, having no rhythm to slip; it reads **active** with confirmed-edge activity inside the no-activity window and **stalled** with none for that window — reading by edge-activity recency, **not** by its commitments' cadence (a progressive goal's never-completed daily lever does not drag it to behind). *Sequence goal → done / active / stalled.* Done when the terminal is reached; otherwise read by activity like a cadence-less goal. *The stalled tier is the point.* It is the deliberate addition over S89's recency-only "active" — the at-risk read — and it exists so a rhythm-less goal that quietly stopped surfaces instead of hiding in the healthy collapse, the case "behind" cannot produce for a cadence-less goal. *Static this session.* The K values and the no-activity window are static config; learning K per goal from operator overrides is the post-week adaptive loop, not built here. The default thresholds are tunable config, not part of this decision. *Live-surface verification (the just-minted principle).* The taxonomy is verified on the real corpus and the operator sanity-checks that the verdicts read true (a goal that stopped reads stalled; a goal met at cadence reads on-track), not on fakes. *Kano.* Performance tending to must-have — the moat's verdict is the legibility surface the gate week reads; without the stalled tier a rhythm-less goal that died reads healthy, the assess-not-replace promise broken at the verdict. *References.* D169/S83 (the goal-grouped moat read this status field extends), D157/D162 (the commitment cadence + `staleness` math reused), D163 (the goal modes — homeostatic / progressive / sequence — that set the status family), D177 (a goal's multiple lever commitments, aggregated worst-wins), D171 (coverage honesty — a stalled read is honest at-risk, distinct from uncovered), S89 (the recency-only "active" this generalises), the live-surface verification principle (charter/principles.md), roadmap **v12** (the legibility block this opens). **D188 — Progressive goals feel their practice-commitment cadence: the asleep state.** D187 made progressive goals cadence-less, reading active or stalled by edge activity alone. The live read (S92) exposed this as too coarse: a progressive goal whose practice commitment is being missed still read **active** off an incidental recent edge — German, a few lessons then a week of nothing, reading active while the operator had actually paused it — hiding exactly the quiet lapse the stalled tier was built to surface. D188 refines D187's progressive rule with a third status, **asleep**, between active and stalled. A progressive goal now reads, in precedence order: **stalled** when it has no confirmed activity in the 14-day window; else **asleep** when it has recent activity but its practice commitment has **lapsed** (missed at or past the threshold — daily K=3, weekly K=2 consecutive beats, reusing the homeostatic missed-beat logic, not a new mechanism); else **active**. That flatness is why the surface could not distinguish one live opportunity past the HR call from hundreds of cold items, and why an inbound recruiter contact (an external) read as if it were the user's own application lever. Pratt's guest post resolves the collision by keeping the process map and the CDD as cross-linked layers (her DIOps framing), with the process decision points acting as portals into per-decision CDDs; the platform adopts that boundary rather than flattening process into the CDD. The schema already half-embeds the process layer (a sequence goal carries `step_order` and `step_state` per D163), and design-language §4 already commits the Map-and-Flow split, so this entry names the conceptual boundary the deferred build will implement, not new build. *Alternatives.* (a) Treat a stage as a lever: rejected, a stage is a position reached, not a controllable action, and treating it as a lever makes the CDD un-simulatable, since you cannot pull a stage. (b) Flatten process into the CDD with one lever per pipeline: rejected, it merges inbound externals with user levers and destroys the stage-level read the differentiator depends on. (c) Build the Flow and intermediary layer now: deferred to D162's activation (the post-week verdict plus the gap-analysis substrate); this entry settles the model, not the build. *Kano.* Performance. The stage-level causal read is where assess-not-replace becomes concrete for process-shaped goals; without the boundary the Map reverts to a flat tracker, which is the reverse-Kano failure the daily driver exists to avoid. *References.* D156 (the whole-life causal daily driver and the CDD), D162 (the deferred causal depth this boundary will be built into; intermediaries and the cross-goal ripple), D163 (the sequence `step_order`/`step_state`, the embedded process layer), D9 (recommendation-shaped output), design-language §4 (Map and Flow over one graph) and §10, the `product-methodology.md` goal taxonomy and CDD stack, and the Pratt "How to Integrate Process Models with Decision Intelligence" guest post held in project knowledge. **D200 — The CDD is authored per goal as the context layer, edited as the learning signal, and co-evolves through a bidirectional human-proof gate; intermediaries and externals move from deferred depth to foundational defined context.** *Choice.* The platform builds each goal's causal structure top-down before mapping signal into it. The LLM drafts the goal's levers, intermediaries, externals, and expected outcomes; the user proofs and edits. That authored CDD is the semantic context layer. Ingested work then maps into named elements ("this email is evidence for the response-rate intermediary"), not a generic edge to the goal, and the user's edits and unlinks are the signal the LLM learns from. The model is not authored once. It co-evolves through one human-proof gate: the user authors and corrects, and the system proposes new elements or relationships when emergent signal does not fit the current structure, with both directions passing through the user's proof. Each element carries a provenance origin, LLM-drafted, user-authored, or system-suggested-from-signal, and that origin history is itself optimization signal. *Reasoning.* The S101 dogfood (the finding above) showed that a generic, auto-derived, read-only CDD has decreasing value, because the relationships carry no per-goal meaning and the user cannot correct them, so the model cannot learn, which guts the optimization differentiator. On a subjective personal-goal domain the only source of ground truth is the user, so authoring and correction are not conveniences; they are the precondition for the optimization layer. Authoring the CDD goal by goal also pressure-tests the CDD abstraction itself: a goal that cannot be sensibly drafted as levers, intermediaries, externals, and outcomes is evidence the frame does not fit that goal-type. So the one mechanism both corrects the model and tests whether the model belongs. The suggestion loop is an extension of machinery that already exists (D170's missing-element suggestions, D196's gated suggestion flow), generalized from "attach this unlinked work" to "this emergent cluster does not fit your CDD, should it be a new element." *Alternatives.* (a) Improve the matcher alone, no authoring: rejected, automated derivation cannot capture user intent in a subjective domain and cannot learn from correction it does not collect. (b) Build D162's deferred depth next as planned, auto-derived intermediaries: rejected, depth on an uneditable, often-wrong CDD compounds the error. (c) Full manual authoring, no LLM draft: rejected, friction too high; the draft-and-proof split keeps the user as authority while removing the burden. (d) Freeze the authored CDD, no suggestion loop: rejected, the model goes stale as the life changes. *Kano.* The define-and-correct capability is a must-have, table stakes for meaningful causal assessment, which the first slice wrongly modeled as deferred depth, the reverse-Kano miss that made a working render feel like loss. The LLM-draft-and-proof flow and the emergent-suggestion loop are the delighter execution of that must-have. Must-have drove the recommendation. *Scope and altitude.* This settles the shape only. Deferred to the build sessions: the concrete schema (node labels, edge types, properties), the authoring surface, the emergence-detection method, the suggestion threshold (governed by D171 coverage-honesty and D196 gating to avoid the nagging-wallpaper failure), and the matcher's rewrite from goal-linking to element-evidence. *References.* D156 (the daily driver and the CDD), D162 (the deferred depth this reorders; see the cross-reference at D162), D163 (the goal taxonomy and the sequence `step_state` the authored levers build on), D170 and D196 (the suggestion machinery this generalizes), D171 (coverage-honesty governing suggestion restraint), D198 (the process-versus-CDD boundary the authored levers and intermediaries instantiate), D199 (the read-only Map slice whose dogfood surfaced this), the assess-not-replace, observability-is-foundation, and optimization-is-recommendation-shaped principles, design-language §4. *Kano category:* must-have. (S101 dogfood reflection, strategic, 2026-06-18) *Dual-nature addendum (externals are knowable as category, emergent as instance; promoted from the S103a authoring pass).* Hand-authoring externals at S103a surfaced that an external has two altitudes. Its **category** is often knowable from the goal description alone — a job search always has a market-conditions slot and an inbound-interest slot — while its **specific instance** only becomes knowable from an event that arrives: a hiring freeze this quarter, a recruiter on Tuesday. The S102 draft producing zero externals across all eight goals is therefore a uniform draft-prompt weakness at the category altitude, not eight separate emergent surprises. This refines D200's draft-and-proof: the draft should enumerate external **category slots** per goal-type (a draft-prompt strengthening, deferred and off the dogfood critical path since the live goals' slots are hand-authored), while the **emergent loop fills the instances** as signal arrives (S104). Strengthening the draft and routing to the emergent loop are not alternatives — they are two altitudes of the same mechanism, and the unbound queue (D202) plus the user's corrections are what feed the instance altitude. **D202 — Signal binds to authored elements, not goals: the element-evidence matcher.** *Choice.* The matcher writes **element-level evidence** as the primary write: a unit of work matches the nearest authored element *within* its goal — a lever, intermediary, external, or the outcome — via **lexical and alias recall applied to per-element targets** (the per-element extension of the goal-level recall the matcher already does). A unit may evidence **more than one element** (multi-attach); it writes an evidence edge to each element it matches. **Goal-level evidence is derived on read** from element evidence (rolling each unit→element edge up to the goal via the element's `outcome_id`), **replacing the goal-level `SERVES` write** so the goal view and the element view cannot drift apart. A unit matching **no element parks in a visible unbound bucket**, neither dropped nor silently goal-linked, as the queue the emergent loop (S104) consumes. *Reasoning.* D200 made the CDD authored per goal so signal could attach to per-goal *meaning*; binding a unit to the goal-as-a-whole throws that meaning away the moment it lands ("this email is evidence for the response-rate intermediary," not "this email serves Get-a-job"). Element binding is the mechanism that makes the authored model load-bearing, and the user's relink/unlink corrections against it (captured at S103c) are the ground-truth the optimisation layer learns from. Deriving the goal level on read rather than writing it twice is the D155 derived-state discipline applied to the two altitudes: one write, one source of truth, no drift. The unbound bucket is parked rather than dropped because it is precisely the input the emergent loop needs — work the model has no element for is the signal that the model is missing an element. *Deferred and named.* (i) An **embedding recall tier**: the live matcher is lexical-and-alias only and the email-embedding corpus is empty (S100), so per-element embedding recall is named here as later work, not built — and a high unbound rate must be diagnosed against this (under-described element, an authoring problem, versus too-crude lexical recall, which would pull the embedding tier forward). (ii) **Direction** — the lever-versus-external orientation from email sender/recipient and calendar organiser/attendee — needs a user-identity reference the system does not yet store, and its only consumer is the emergent loop, so it lands in **S104** with its configured-account-identity decision (D203, reserved there); a signal lands where it informs a decision, and in this session direction informs none. *Alternatives.* (a) Single-assignment (a unit serves one element): rejected — discards real multi-element signal (a recruiter's email is both an inbound and moves the interview-invitations intermediary). (b) Dual goal-and-element writes: rejected — two writes drift; derive the goal level instead. (c) Hard `SERVES` replacement that rewrites the three goal-level readers: rejected for risk — deriving at the `list_goal_edges` boundary keeps the readers (`group_units_by_goal`, `goal_status`, coverage) byte-for-byte unchanged. (d) Drop unmatched units: rejected — they are the emergent loop's queue. *Kano category:* performance — binding precision is the platform's core differentiator; a goal-whole link is the reverse-Kano flatness D198/D200 exist to avoid. *References.* D197 (the tiered recall this extends per-element, embedding tier deferred), D198 (the lever/intermediary/external/outcome element taxonomy bound against), D200 and its dual-nature addendum (the authored model this binds to and the externals altitudes), D162 (the expected-vs-observed loop the element evidence sharpens), D155 (derived state — the derive-on-read discipline), D169 (the goal-facet/coverage read re-sourced), D185/D186 (the matcher-quality and policy hooks measuring the rewritten matcher), the graph-is-authored and observability-is-foundation principles. (P2B/S103b, build, 2026-06-18)

**D201 — Reclassifying an authored CDD element across the lever/intermediary/external boundary preserves the node and its stable identity, flips its provenance origin to `user_authored`, and flags any now-invalid incident edge for the user to resolve rather than silently dropping it.** *Choice.* When the user moves an element from one type to another (a draft mis-typed a recruiter's inbound as a lever; it is really an external), the reclassify keeps the **same node** — its stable id value, its `outcome_id`, its `label`, its `tenant_id`/`jurisdiction`/`created_at` all survive; only the type-label changes (and the id moves between the kind's id property, `lever_id` for a lever, `element_id` for an intermediary/external, since the live whitelist keys each kind by its own property — Step 0). The reclassify is a **correction**, so it flips `provenance_origin` to `user_authored` (the D200 ground-truth signal), exactly as an in-place label edit does. A type change can make an element's incident authored edges ungrammatical: a lever `FEEDS`, an external `INFLUENCES`, so a lever reclassified to an external should not keep its `FEEDS` edge. The platform **flags** each such now-invalid edge (a `needs_review` marker the proof read surfaces) for the user to resolve, and does **not** delete it. *Reasoning.* Silent deletion of an authored edge would erase structure the user authored without their say, which the "graph's meaning is authored" principle (D200) forbids and which the no-auto-deletion platform invariant (D82, dimension reversibility/integrity) targets directly: the platform may not auto-delete user-authored content, and an authored edge is user-authored content once proofed. Preserving node identity rather than delete-and-recreate matters because identity is what the S103b matcher's learning signal attaches to: a reclassify that drops and re-mints the node would read as "old element deleted, new element appeared" instead of "this element was the same thing, re-typed," losing the correction's meaning. So reclassify is modelled as identity-preserving correction with edge-grammar flagging, the same recommend-surface-don't-mutate posture the rest of the proof loop carries. *Alternatives.* (a) Silent drop of now-invalid edges on reclassify: rejected — erases authored structure without consent, violates D200 and the no-auto-deletion invariant. (b) Auto-re-point the invalid edge to a grammatical shape (e.g. retype `FEEDS` to `INFLUENCES`): rejected for S103a — the platform cannot know the user's intent for the edge (the external may influence the outcome or an intermediary), so guessing manufactures structure the user did not author; surfacing the flag and letting the user resolve is the honest move. The auto-suggest-a-fix path is the emergent-suggestion loop's territory (S104), gated through the same proof. (c) Delete-and-recreate the node under the new type: rejected — breaks identity continuity the S103b learning signal needs and needlessly cascades edge deletion. (d) Block reclassify when it would invalidate an edge: rejected — refusing the correction to protect a now-wrong edge inverts the priority; the correction is the point, the stale edge is the thing to flag. *Scope.* Reclassify is the three-way lever/intermediary/external boundary (D198); the outcome is the goal's single terminal node (D199) and is not reclassifiable. The edge-resolution affordance (re-pointing or clearing a flagged edge) is surfaced as a flag in S103a; the full edge-edit loop is S103b. No migration — the `needs_review` flag and the reclassify are schemaless graph operations on the S102 (`0005`) shapes. *Kano.* Performance — correcting a mis-typed element is the core act the authored-CDD differentiator depends on (a model you cannot correct cannot learn, D200); the flag-don't-drop discipline is what keeps the correction trustworthy rather than lossy. *References.* D200 (the authored-CDD pivot and the learning signal this correction feeds), D198 (the lever/intermediary/external boundary being crossed), D199 (the outcome-is-the-goal-node rule that excludes the outcome from reclassify), D82 and the no-auto-deletion platform invariant (reversibility/integrity), D126 (the `CDD_WRITE` use-case-boundary the reclassify routes through), the "graph's meaning is authored" and "optimization output is recommendation-shaped" principles. *Kano category:* performance. (P2B/S103a, build, 2026-06-18)
