**D126: ActorContext shared-kernel value object, authorisation decorator at the use-case boundary, and ActorReference retention as persisted authoring identity.** Bundled D-entry covering the Phase 2-A actor-identity and authorisation substrate per the Decision 7 forward-compat substrate-depth classification. The framing-time bundle was a two-sub-commitment shape (ActorContext plus decorator); S44a pre-write reconciliation reshaped it to three sub-commitments after finding that ActorReference cannot cleanly be superseded by ActorContext at the persisted `authored_by` field. *Sub-commitment 1 — ActorContext.* ActorContext is a frozen dataclass at `shared_kernel/actor_context.py` composing the existing TenantContext as a field plus three fields: `actor_id` (`str`, non-empty — UUID-shaped when derived from the Principal at the HTTP path, a label at the CLI path), `role_list` (`frozenset[str]`, non-empty — Phase 2-A populates `{"operator"}`), and `authorisation_set` (`frozenset[str]` — Phase 2-A populates from the hardcoded role-to-authorisation lookup; may be empty for an actor with no permissions). The compose shape — ActorContext wraps TenantContext rather than subsuming it — preserves single-concern value objects per the hexagonal posture and keeps adapter signatures unchanged: a use case extracts `actor.tenant_context` before adapter calls. ActorContext is the request-scoped value object that flows into every portfolio use case from S44a onward; `__post_init__` enforces the invariants. Pydantic is forbidden in `shared_kernel/` per the `shared-kernel-policed` import-linter contract (D16), so the frozen-dataclass shape is structurally pre-empted, consistent with TenantContext. *Sub-commitment 2 — authorisation decorator.* `requires_authorisation(permission: str)` at `shared_kernel/authorisation.py` wraps a use-case async function whose keyword arguments include `actor: ActorContext`; it checks the required permission string against `actor.authorisation_set` and raises `AuthorisationDenied` (a typed exception in the same module carrying the required permission and the actor_id) when the check fails. The HTTP layer translates `AuthorisationDenied` to a 403 response with the existing `ErrorResponse` shape per D98, registered with the auth-cross-cutting handlers at `apps/api/_auth_errors.py` per D104 — the decorator's exception is auth-cross-cutting (raised by the shared decorator, not by any one router), so it belongs with the D104 auth-cross-cutting error module, not the per-router `apps/api/_errors.py`. The Phase 2-A authorisation policy is hardcoded in `shared_kernel/authorisation.py`: five portfolio permission strings (`portfolio.case.create`, `portfolio.data_point.create`, `portfolio.data_point.revise`, `portfolio.case.list`, `portfolio.case.get`) named once as module constants, and a single-role lookup `{"operator": <the five>}` resolved through an `authorisations_for_roles` function. The lookup lives in `shared_kernel/authorisation.py` rather than at the auth middleware so the decorator applications, the HTTP `get_actor_context` dependency, and the CLI's ActorContext synthesis all reference one source — the CLI synthesises ActorContext without passing through HTTP middleware, so a middleware-local lookup would force the permission set into two places. The richer per-tenant or registry-backed lookup activates at the role-hierarchy deferred-decisions trigger. *Sub-commitment 3 — ActorReference retention as persisted authoring identity.* ActorReference (the minimal `{user_id}` frozen value object at `shared_kernel/actor_reference.py`) is retained unchanged — not deleted, not renamed, not extended — as the *persisted* authoring-identity value object stamped onto `DataPoint.authored_by` and `Assertion.authored_by` and round-tripped through the `authored_by_user_id` column. A use case receives ActorContext and derives `ActorReference(user_id=actor.actor_id)` when stamping authorship on a domain entity or an audit-event draft. ActorReference (persisted identity) and ActorContext (request-scoped capability) are distinct value objects with distinct concerns; the name pair is self-documenting — a *reference* is a minimal identity stamp, a *context* is a rich request envelope. *Supersedes D124's forward commitment on `authored_by` becoming ActorContext.* D124 committed that ActorReference "is superseded at S44 by the full ActorContext per D116 ... the supersession extends shape and home without renaming," covering both the Revisable Protocol's `actor` parameter and the `authored_by` field. S44a pre-write reconciliation found that commitment structurally unsound. The `data_points` and `assertions` tables persist authoring identity as a single `authored_by_user_id` text column; an ActorContext cannot be reconstructed from it — there is no stored `role_list` or `authorisation_set`, the non-empty `role_list` invariant could not be satisfied on read, and a fabricated set would assert a request-time authorisation snapshot that was never recorded. Persisted authoring identity and request-scoped capability are different concerns: freezing `authorisation_set` onto a permanent record would produce a snapshot stale on every subsequent read and would semantically misrepresent identity as capability. D126 therefore supersedes D124's `authored_by` forward commitment — `authored_by` stays ActorReference. The Revisable Protocol's `actor` parameter (D125) likewise stays ActorReference: authorisation is enforced at the use-case decorator before `revise` runs, so the shared-kernel revision-history contract needs only identity, not the authorisation substrate; coupling it to ActorContext would be a layering smell. D124's other commitments stand; only the `authored_by`-and-`actor`-parameter forward commitment is superseded. This is the first instance of a D-entry superseding a forward commitment carried by an earlier D-entry; the supersession is recorded here and D124 is not rewritten, preserving the audit trail. *Alternatives considered.* (a) Subsume ActorContext into a flat envelope replacing TenantContext: rejected — single-concern value objects is the hexagonal posture; the refactor footprint touches every adapter; downcasting at the call seam makes the structural boundary visible. (b) Skip ActorContext entirely, keep ActorReference permanently, place authorisation at HTTP middleware: rejected — HTTP middleware cannot see method-specific permission requirements, and the CLI surface does not pass through HTTP middleware. (c) Inline authorisation checks in each use-case body: rejected — inline checks scatter policy across the application layer, defeating the trivial-check-at-one-boundary commitment from Decision 7. (d) Split into separate D-entries for ActorContext, the decorator, and AuthorisationDenied: rejected on the architectural-bundling test — the decorator cannot ship without the ActorContext fields it consumes, and the exception is structurally inseparable from the decorator. (e) Replace ActorReference at the domain entities per D124's literal commitment, persisting `authorisation_set` with each authored record: rejected on the persisted-identity-versus-request-scoped-capability conflation — ActorReference is a minimal authoring-identity value object, ActorContext is a rich request-scoped envelope; persisting ActorContext into the `authored_by_user_id` column would freeze a request-time authorisation snapshot onto a permanent record, stale on every read and semantically misrepresenting persisted identity as request capability. The chosen position retains ActorReference unchanged for persisted authoring identity and introduces ActorContext as new for request-scoped capability. *Kano classification.* Must-have. The cost-now-versus-cost-later asymmetry is the structural driver: cost now is one shared-kernel value object plus one decorator plus signature changes at the five portfolio use cases plus the `get_actor_context` dependency; cost later is touching every use-case signature plus every authorisation-check site after the codebase grows through P14, P15, and P16 use cases. From the procurement-grade evaluator perspective at Phase 2 close, authorisation enforcement at the use-case boundary is the substrate commitment that makes a future SOC 2 or enterprise compliance audit pass cleanly — without the decorator as a single grep-able surface, an auditor cannot verify completeness of authorisation enforcement across the codebase. *References.* D98 (TenantContext shape and ErrorResponse), D104 (auth-cross-cutting error-handler module at `apps/api/_auth_errors.py`), D116 (three-tier consent-and-awareness framework; orthogonal substrate at the platform-initiation altitude rather than the actor-identity altitude addressed here), D121 (no-silent-operation principle; honoured by the decorator's explicit AuthorisationDenied surface), D124 (portfolio context substrate; D126 supersedes D124's forward commitment that `authored_by` and the Revisable `actor` parameter become ActorContext, retaining ActorReference as persisted authoring identity), D125 (Revisable Protocol; the `actor` parameter stays ActorReference per the layering reasoning above). *Deferred-decisions cross-references.* Role hierarchy with inheritance machinery (activation trigger: a second role beyond operator) — `authorisations_for_roles` already resolves a role-set union, so the hierarchy is a pure extension. Principal polymorphic shape, machine-actor variant (activation trigger: an API caller at Phase 2-B+) — the ActorContext `actor_id` slot supports the polymorphic shape as a pure extension.
