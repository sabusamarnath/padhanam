The posture is adversarial: confirmation that did not look hard enough is a failure of the audit.

## 1. Gestell (enframing)

**Concept.** Modern technology discloses the world as standing reserve: what is legible to the system becomes a calculable resource on call for optimisation; what is illegible disappears. The audit question is whether the optimisation code enframes agentic activity into calculable dimensions, and whether the pluggable seams that would make that enframing inspectable-and-replaceable are real in code or merely claimed in the charter and hardcoded at the composition root.

**Evidence.** The optimisation engine does enframe: `run_optimization` ([contexts/optimization/application/run_optimization.py:68](contexts/optimization/application/run_optimization.py#L68)) reduces agentic-system activity to four calculable recommendation categories (retrieval_strategy, cost_optimization, model_choice, prompt_revision) evaluated against numeric thresholds — `recall_at_k_delta_threshold=0.15`, `cost_per_successful_task_threshold_usd=0.10` ([contexts/optimization/application/rules/__init__.py:46-48](contexts/optimization/application/rules/__init__.py#L46)). This is standing-reserve disclosure in Ciborra's exact sense: agent behaviour becomes a resource on call for optimisation.

The seam that should make the enframing replaceable is the `RecommendationRule` Protocol. It is genuinely a seam: `run_optimization` takes `rules: Sequence[RecommendationRule]` as an injected parameter (line 72) and iterates whatever is passed (line 104). The engine hardcodes no rule. **But both composition roots inject the same hardcoded factory:** `rules=default_rules()` at [apps/cli/_optimization.py:228](apps/cli/_optimization.py#L228) and [apps/api/routers/optimization.py:257](apps/api/routers/optimization.py#L257). `default_rules()` ([contexts/optimization/application/rules/__init__.py:44](contexts/optimization/application/rules/__init__.py#L44)) returns a fixed four-tuple. No configuration selects the rule set; swapping rules is a code edit, not a config change.

The pattern repeats — more starkly — across every Phase-2-A port:
- `ChannelResolver` (D144): Protocol at [contexts/messaging/application/ports/channel_resolver.py:35](contexts/messaging/application/ports/channel_resolver.py#L35), one adapter (`StaticConfigChannelResolverAdapter`). The adapter's own docstring says it "returns the configured operator-default channel **regardless of input** (static-config adapter)" — it discards `user_id` and `message_intent`. The second adapter (`UserScopedChannelResolverAdapter`) is named in the docstring (line 18) but does not exist in the tree.
- `ConfidenceCalculator` (D134): one adapter, `confidence_self_reported.py`, headed "Phase 2-A **placeholder**" ([contexts/inference/adapters/confidence_self_reported.py:1](contexts/inference/adapters/confidence_self_reported.py#L1)); future logprob/multi-sample adapters are named (line 17) but unbuilt.
- `CellDispatch` (D133), `ThresholdResolver`, `BroadcastDispatch` (D143): same shape — Protocol plus exactly one adapter, the alternative ("Path B / out-of-process queue," "UserScoped...") named in comments only.

**Charter-claim vs code-reality.** The principles file commits "vendor swap is configuration or adapter replacement, never domain change" and "vendor lock-in is not architectural" ([principles.md:10](principles.md)). The PRFAQ surface (out of audit scope but named in the prompt) leans on "pluggable." Code reality: the seams are real *as Protocols* — inspectable, named, layered correctly — and the principle's "or adapter replacement" clause is technically satisfied. But at HEAD every load-bearing seam has exactly one adapter, several of them degenerate stubs that discard their own inputs, with the second implementation existing only as a docstring promise. "Pluggable" is doing procurement-grade rhetorical work that the single-adapter reality has not yet earned. The methodology's own "interface-versus-implementation discipline" ([methodology.md:381](methodology.md)) honestly describes and defends this — commit the interface, ship one adapter, swap later — so the code is not dishonest with itself; the gap is between the marketing register of "pluggable / no lock-in" and the as-built register of "one adapter, forward-compatible by construction."

**Verdict: partially aligned.** The enframing is real and the seams are real as interfaces, which is more than "claimed in charter and hardcoded." But the composition root does hardcode the single inhabitant of each seam, and the procurement-facing word "pluggable" oversells a reality that is, at HEAD, "designed for future pluggability, currently single-adapter." This is the largest charter-vs-code gap the audit found, and — because all these ports postdate P12's commit `afabe7a` — it is necessarily a tension P12 could not have surfaced.

## 2. Ready-to-hand versus present-at-hand (breakdown)

**Concept.** A working tool disappears into the task (ready-to-hand); only breakdown turns it into an object of scrutiny (present-at-hand). Breakdown moments are the analytically richest sites. The audit question: does the code make breakdown a first-class, deliberately surfaced state, or hide it behind silent fallbacks and swallowed exceptions?

**Evidence.** Breakdown is first-class, and in places structurally inescapable:

- `SubstrateGapError` ([contexts/optimization/domain/recommendation_rule.py:47](contexts/optimization/domain/recommendation_rule.py#L47)) is a deliberately surfaced breakdown state. When a rule cannot run because its input substrate is absent, it raises this carrying a structured `CategorySkipReason`; the engine catches it, records it on `OptimizationRun.skipped_categories`, and **emits it in the audit event** ([run_optimization.py:109-111, 149-157](contexts/optimization/application/run_optimization.py#L109)). Two of four shipped rules (model_choice, prompt_revision) raise it by design because their substrate is Phase 2 territory. The platform discloses its own incapacity as audited data rather than hiding it.
- The same use case's `except Exception` (line 163) does not swallow: it persists `failed` status, emits an `optimization.run.fail` audit event, and **re-raises** (line 189). Breakdown is disclosed *and* propagated.
- Chain verification fails loudly with location. `verify_chain` ([contexts/audit/domain/events.py:95](contexts/audit/domain/events.py#L95)) returns `ChainVerificationResult(is_intact=False, break_index=idx, ...)` — the exact index of the first break. The read-side `ChainIntegrityVerification` ([contexts/audit/domain/chain_integrity.py:38](contexts/audit/domain/chain_integrity.py#L38)) carries three states — `verified`, `broken_at_row`, and `partial` — and a `__post_init__` invariant (line 51) that *raises* if a `broken_at_row` status lacks its offending `broken_at_id`, "so consumers cannot read a status that the `broken_at_id` shape contradicts." The `partial` state is the honest "I cannot verify this deterministically" disclosure — the platform refusing to render a verification it cannot perform as a clean binary.
- Swallowing is near-absent. A scan of `contexts/`, `apps/`, `padhanam/` finds 185 `except` blocks and only two `except: ... pass` swallows, both at the CLI boundary in `apps/cli/_ingest.py:340,346` for `asyncio.TimeoutError` and `NotImplementedError` — expected, boundary-level tolerances, not domain-level concealment.

One nuance worth its honesty: the `ConfidenceCalculator` placeholder falls back to `0.5` when the model omits a confidence field ([confidence_self_reported.py:9-15](contexts/inference/adapters/confidence_self_reported.py#L9)). This is a fallback, but a disclosed one — the docstring frames missing confidence as "no signal," middle-of-range, configurable — rather than a silent default-to-high-confidence.

**Charter-claim vs code-reality.** The charter elevates breakdown disclosure implicitly through the "No silent operation" principle ([principles.md:88](principles.md)) and the audit-as-source-of-truth discipline. Code matches: breakdown states are typed, audited, and in the chain-integrity case enforced at construction. They agree, strongly.

**Verdict: aligned.** Breakdown is treated as the richest site, exactly as Ciborra would prescribe — `SubstrateGapError` and the `partial` integrity state are the platform making its own gaps present-at-hand on purpose.

## 3. Stimmung (mood / attunement)

**Concept.** Organisational technology decisions are saturated with mood — panic, fashion, anxiety, enthusiasm — dressed as rational deliberation. The audit question: what mood does the git history actually reveal in its cadence, message tone, and corrective patterns?

**Evidence.** The mood is sustained, dense cultivation, not punctuated panic:

- **Cadence.** 689 commits across 24 active days in one month (2026-04-29 → 2026-05-28), ~29 commits/active-day. Distribution is steady-high with peaks (62 on 05-15, 58 on 05-22, 58 on 04-30) and only one near-idle day (1 commit on 05-09). No multi-day gaps followed by frantic catch-up bursts — the signature of anxiety-driven work — appears.
- **Corrective signature.** `git log` shows **zero reverts** across the full history. 31 fix-class commits (~4.5% of total), and inspection shows them small and scoped (test-assertion updates, FK-boundary fixes, attribute-access corrections), typically landing in-session or the next session, e.g. `5cb4df9`, `051f09b`, `5c7a7f2`.
- **The one anxiety signature is early identity churn.** The product was renamed twice in quick succession — Quorum → Zephyr (D29) → padhanam (D38) — during P2–P3. Two renames in the opening weeks reads as the founding-mood instability (what is this thing called?) that then resolves into stability; no rename after D38.

A measurement tension worth surfacing: `grep -c "classification: corrective" log/sessions.md` returns **0**. No session in the entire log is tagged corrective, so the methodology's change-failure-rate metric ([methodology.md:248](methodology.md)) computes to 0%. Yet the Failure-modes-observed section documents real drift events (silently-deferred package drift, fabrication-class drift, single-currency assumption). The quantitative mood-signal (0% failure) is calmer than the qualitative record, because failures are recorded as narrative Failure-modes entries rather than via the corrective session classification. The mood is genuinely steady — but its steadiness is flattered slightly by where failure gets booked.

**Charter-claim vs code-reality.** The methodology projects "steady cultivation under measurement" and "honest reporting including poor periods" ([methodology.md:254](methodology.md)). Git confirms the cultivation; the reporting honesty is real in the Failure-modes prose but incompletely wired to the metric (0 corrective classifications).

**Verdict: aligned, with one measurement caveat.** The build's mood is enthusiasm and steady tending, evidenced by reverts-zero and dense even cadence. The early double-rename is the only anxiety trace, and it resolved.

## 4. Care / Sorge (cultivation)

**Concept.** You do not control a large infrastructure; you tend it, intervene selectively, and accept drift, then codify it. Cultivation, not control. The audit question: does git show tending (abstractions extracted only when forced; drift accepted then codified) or control (everything planned and installed upfront)?

**Evidence — cultivation.** The clearest tending artefact is in the code's own docstring. `padhanam/security/hash_chain.py` was not designed upfront as a platform primitive; it was grown. Its header ([hash_chain.py:5-11](padhanam/security/hash_chain.py#L5)) records: "Promoted from `contexts/methodology/domain/hash_chain.py` at S24 commit 8 ... This is the second instance of the second-consumer-promotes pattern after S23's OPERATOR_ROLE promotion." Commit `9bb7c03` confirms it was a move-and-prune triggered when the agent context became a second consumer — the abstraction was extracted *because a second instance forced it*, not in anticipation. The methodology codifies exactly this: "Start simple; refactor at the structural-promotion threshold" — "The first occurrence ... is implementation; the second is suspicion; the third is the lift to shared abstraction" ([methodology.md:516](methodology.md)).

The D3 → D52 identity reversal (developed in Authenticity below) is cultivation too: a planned package drifted, the drift was accepted, and it was codified into a deferral rather than forced back onto plan.

**Evidence — a shift toward control in Phase 2-A.** The cultivation doctrine itself drifted. Phase 1 extracted at the *third* instance. Phase 2-A introduced the "build-at-second-instance discipline" (D127) and, more tellingly, the "interface-versus-implementation discipline" ([methodology.md:381](methodology.md)), under which Phase-2-A ports (`CellDispatch`, `ChannelResolver`, `ConfidenceCalculator`, `BroadcastFlow`) are committed as Protocols *upfront* with only one adapter shipped and the second named in docstrings. That is anticipatory design — closer to control than to tend-when-forced. The hash_chain primitive was extracted reactively at a second consumer; the ChannelResolver port was installed proactively before any second channel exists. The build moved from cultivation toward anticipatory control as it entered Phase 2-A, and the methodology codified the move as a named discipline rather than registering it as a departure.

**Charter-claim vs code-reality.** The charter's stated mechanic is cultivation (structural-promotion threshold; refactor between sessions). Phase 1 git confirms it. Phase 2-A git shows the same project quietly running a more control-shaped pattern (interfaces-first, single adapters) under new discipline names — without the methodology naming the shift as a shift.

**Verdict: partially aligned.** Phase 1 is cultivation, evidenced in the very docstrings. Phase 2-A leans toward anticipatory control under the interface-versus-implementation discipline, and the codification of that lean as "discipline" rather than "drift in our own method" is itself the care-versus-control tension the section is meant to find.

## 5. Authenticity versus das Man (the They)

**Concept.** Inauthentic decisions adopt because others adopt; authentic decisions emerge from genuine reckoning with the specific situation and are by definition hard to copy. The audit question: do the architectural decisions bear marks of situated reckoning, or templated patterns lifted because they are what one does?

**Evidence — authenticity.** The decisions record carries genuine reckoning, including reversal under evidence:
- **D3 → D52.** D3 committed identity-as-Keycloak with OIDC/SAML/SCIM; P2 was named "Identity foundation." What shipped under P2 (S4–S8) was "First LLM call." The mismatch went uncaught for ~30 days until a status-snapshot pass surfaced it; D52 (commit `593dd00`, 2026-05-06) reversed D3, deferring identity to Phase 2 with the reasoning that "the bet's load-bearing claims do not turn on federated identity" ([methodology.md:456-462](methodology.md), Failure-modes entry). A planned package abandoned and reversed under situation-specific evidence is the opposite of das Man.
- Other explicit supersessions confirm the reckoning is habitual, not one-off: D14 → D76 (forking phrasing refined), D88 → D90 (sync → streaming executor), D45 → D51 → D93 (PRFAQ audience), D39 → D113 (methodology authorship framing). Each is preserved append-only with reasoning, not silently rewritten.

**Evidence — das Man tension (the hardest finding).** Four of the Phase-2 principles in [principles.md:115-154](principles.md) are not reckoned into being from Padhanam's situation — they are **transplanted from a prior product.** Each carries the identical provenance line "Origin: karma prior-art product specification §11.x, transplanted at P13 framing per Decision 6 option (c)": frontend/backend separation (§11.3), audit-trail-as-source-of-truth (§11.5), originals-never-erased (§11.5), authority-and-certainty-independent (§11.5). `grep -c "karma prior-art" principles.md` → 4. These are the most load-bearing Phase-2-A architectural principles, and their genesis is transplantation from what worked before, not situated reckoning. The transplant is *honestly labelled* — which is itself authentic practice — but transplantation-from-prior-art is structurally closer to das Man ("this is what one does, it worked in karma") than to the situated reckoning the bet's self-image claims. The private-assistant communication discipline ([principles.md:141](principles.md)) is similarly sourced from "the attentional-assistant product brief shared during P13 framing."

**Charter-claim vs code-reality.** The bet claims decisions "emerge from genuine reckoning with the specific situation" and are "hard to copy" ([bet.md], methodology Foundation). The Phase-1 decisions record bears this out strongly. The Phase-2-A principle imports complicate it: the platform's next-phase spine was, in material part, copied from a prior product — easy to copy precisely because it already had been.

**Verdict: partially aligned.** Phase-1 architecture bears deep marks of situated reckoning, including evidence-driven reversal (D52). Phase-2-A principles lean on honestly-labelled prior-art transplant, which is the das Man pole the bet's self-image is least comfortable acknowledging. P12 could not have seen this — the karma transplants landed at P13, after `afabe7a`.

## 6. Bricolage

**Concept.** The bricoleur builds with materials at hand, recombining fragments whose original purposes differed, improvising against constraints rather than designing from first principles. Improvisation is generative, not a failure mode. The audit question: find the bricolage in git, and cross-reference whether the methodology names these moments as bricolage or frames them as discipline lapses recovered.

**The headline cross-reference finding: the word "bricolage" appears zero times in the entire charter, archive, and log.** `grep -rin "bricolag\|improvis\|materials at hand\|recombin" charter/ docs/archive/ log/` returns nothing. The improvisation is everywhere in git; the vocabulary for it is absent. And — this is the part the prompt's binary did not anticipate — the methodology frames these moments neither as bricolage *nor* as "discipline lapses recovered." It frames them as **proactive, forward-binding engineering disciplines.** That is a third thing, and it is the most interesting result in this audit.

**Commit 1 — `9bb7c03` (S24), cross-referenced against the session log.** The hash_chain primitive was reused-and-recombined: a fragment built for the methodology context (`contexts/methodology/domain/hash_chain.py`) was promoted to the platform layer when the agent context needed it — materials at hand, recombined for a purpose differing from the original. The commit message names it "the second instance of the second-consumer-promotes pattern." Bricolage, framed as a named pattern.

**Commit 2 — the S39 mid-build reuse, cross-referenced against [log/sessions.md:1799](log/sessions.md).** This is textbook Lévi-Strauss bricolage captured in the operator's own prose. The S39 brief planned to *extract a new helper* (`compute_chained_payload_hash`, commit 2.5) inside the audit context. Mid-build, while reading migration 0010 *for an unrelated reason* (mirroring its recompute pattern for commit 2), the import `from padhanam.security.hash_chain import compute_revision_hash` surfaced — and "the field-set-agnostic primitive promoted at S24 ... already exposes exactly the ... mechanism D109's commit 2.5 would extract. The audit refactor was therefore unnecessary; commit 2.5 did not land." The gold-set "became the third consumer of `padhanam.security.hash_chain` ... strengthening D75's second-consumer-promotes pattern (now third-consumer-confirms)." The bricoleur reached for a tool mid-task, found a fragment to hand, and abandoned the planned new build. The session log names this **"mid-build pre-write reconciliation as a distinct sub-pattern"** — and it is promoted to a methodology Patterns-observed entry ([methodology.md:329-337](methodology.md)). The improvisation is real; the framing is "architectural discovery discipline."

**Beyond what the session log names.** The Phase-2-A single-adapter-behind-a-Protocol pattern (Gestell section) is itself bricolage-shaped: `StaticConfigChannelResolverAdapter` reuses `MessagingSettings.operator_default_channel` ([sessions.md:2057](log/sessions.md), S53 entry) as the channel source rather than building a channel-preference store — improvising a channel resolver from the configuration material already at hand, deferring the "real" `UserScopedChannelResolverAdapter`. The methodology frames this as the "interface-versus-implementation discipline," not as improvisation against constraints. This is a bricolage moment the methodology does not name *as bricolage* — evidence for the vocabulary-promotion candidate carried forward below.

**Charter-claim vs code-reality.** There is no charter claim *to* bricolage to test — the charter has no such vocabulary. The finding is the absence itself: Padhanam improvises generatively and continuously (reuse-of-fragment, mid-build recombination, improvising stubs from config-at-hand), and every instance is converted into a named, forward-binding discipline ("second-consumer-promotes," "third-consumer-confirms," "mid-build pre-write reconciliation," "interface-versus-implementation," "build-at-second-instance"). The codification of improvisation *is* the methodology's mechanism. Ciborra would call the moments bricolage; Padhanam calls them discipline.

**Verdict: aligned in practice, unnamed in vocabulary.** The git history is rich with bricolage and the methodology captures the moments faithfully — it simply lacks the word, and reframes generative improvisation as proactive discipline. Whether that reframing is a strength (improvisation made teachable and repeatable) or a self-image that hides how much of the architecture was improvised is the question the synthesis takes up.

## 7. Drift

**Concept.** Infrastructure mutates away from plans under use; drift is the normal condition, and the honest posture follows it rather than denying it. The audit question: diff load-bearing D-entries against what the code shipped, and distinguish build-layer drift (mature here) from operational-layer drift (untestable pre-Phase-2-production).

**Build-layer drift found:**
- **The twelve-context documentation note is stale at nineteen (R2).** P12 Entry 16 ([p12-audit-findings.md:235](p12-audit-findings.md)) recorded the count of twelve expressly so "future audit conversations inherit the documented count without rediscovery." Seven Phase-2-A contexts have since shipped (all D-authorised). The drift is benign at the code layer (every context is chartered) but the *audit artefact built to arrest rediscovery has itself drifted* — a small, self-referential drift the engineering lens would not flag because the contexts are authorised; the phenomenological lens flags it because it shows even the anti-drift instrument drifting under use.
- **`parallel_rrf` remains unimplemented from D66 through HEAD.** D66 catalogued three retrieval strategies; two ship; `parallel_rrf` is still "deferred" at [contexts/retrieval_evaluation/application/run_retrieval_evaluation.py:20](contexts/retrieval_evaluation/application/run_retrieval_evaluation.py#L20), [strategy_keys.py:15](contexts/retrieval_evaluation/application/strategy_keys.py#L15), and [domain/evaluation_run.py:7](contexts/retrieval_evaluation/domain/evaluation_run.py#L7). This is real D-entry-vs-code drift, but **P12 already surfaced it** (Finding T3, parked at D110 + deferred-decisions), so it is not a new finding — noted for completeness and to confirm the deferral held across the entire Phase-2-A arc rather than being quietly closed.
- **The cultivation doctrine drifted from three-instance to two-instance extraction** (Care section): D127's build-at-second-instance discipline supersedes the Phase-1 "third is the lift" rule for Phase-2-A, without the methodology naming the change to its own method as drift.

**Operational-layer drift: honestly absent, not invented.** No production deployment exists, so the entire operational layer is untestable. The DORA "deployment frequency" runs on a proxy (merged-to-main) by the methodology's own admission ([methodology.md:246](methodology.md)); the optimisation cost threshold ($0.10/task) is ~400x off any real production regime (P12 Entry 8); mTLS, KMS-at-rest, and SIEM routing are all "production swap" commitments not exercised in code. Per the prompt's instruction, these absences are noted, not dressed up as findings. There is no operational drift to follow yet because there is no operation to drift from.

**Charter-claim vs code-reality.** The charter treats drift as normal and to be codified (the living-document/append-only discipline). Build-layer drift is followed and codified maturely. The novel phenomenological finding is the stale anti-drift artefact (the twelve-context note) and the unacknowledged drift of the method's own extraction threshold.

**Verdict: partially aligned.** Build-layer drift is followed honestly and codified — mature, as the charter claims. Two drifts escaped the engineering lens: the audit artefact built to stop rediscovery has itself gone stale, and the cultivation threshold mutated without being named as a mutation. Operational-layer drift is correctly absent pending Phase-2 production.

## Synthesis: does the Ciborran self-image survive contact with the code?

Padhanam's implicit self-image — articulated nowhere as Ciborra but legible throughout the charter — is that the **build layer is Ciborran** (breakdown surfaced, drift followed, abstractions cultivated not installed) while the **product layer is Gestell** (it enframes agentic activity into calculable optimisation dimensions, deliberately, because that is the procurement-grade proposition). Bricolage is, on this reading, the codification mechanism: improvisation against materials at hand, converted into named disciplines.

That self-image largely survives, with two honest fractures:

**It survives where it matters most.** Breakdown is genuinely first-class — `SubstrateGapError` and the `partial` chain-integrity state are the platform making its own gaps present-at-hand on purpose, with construction-time invariants forbidding dishonest status. The mood is steady cultivation (zero reverts in 689 commits). The Phase-1 decisions bear deep marks of situated reckoning, including the evidence-driven D3→D52 reversal. And bricolage genuinely *is* the codification mechanism: the hash_chain promotion (`9bb7c03`) and the S39 mid-build reuse ([sessions.md:1799](log/sessions.md)) show improvisation converted, in real time, into forward-binding disciplines.

**It fractures at two seams the engineering lens missed.** First, **Gestell has crept from the product layer into the seams meant to contain it.** Every Phase-2-A port ships with exactly one adapter, several of them degenerate stubs that discard their own inputs (`ChannelResolver` ignores `user_id` and `message_intent`), with the alternative existing only as a docstring. "Pluggable / no vendor lock-in" is the procurement promise; "one adapter, forward-compatible by construction" is the code. The seams are real as interfaces but single-inhabited in fact, and the word "pluggable" enframes a future that the present has not built. Second, **the build layer is drifting toward control under cultivation's name.** Phase 1 extracted abstractions only when a second consumer forced it; Phase 2-A installs interfaces upfront and ships one adapter, and the methodology codifies this anticipatory design as the "interface-versus-implementation discipline" — control reframed as cultivation, without the method naming the shift to itself.

The deepest finding is reflexive: Padhanam's signature move is to convert every improvisation into a named discipline. That is genuinely powerful — it is what makes the methodology teachable, the proprietary insight the bet is built to sell. But it is also the mechanism by which the project's own bricolage and its own creep-toward-control become invisible *to the project*, because once improvisation is renamed "discipline" it stops looking like improvisation. The Ciborran self-image survives contact with the code; what the code reveals is that the self-image is, in part, produced *by* the very codification habit it describes. An audit looking only through the engineering lens reads the named disciplines as evidence of rigour. The phenomenological lens reads the same disciplines as the place where the project's improvisation and its drift toward control are most successfully hidden from view — not dishonestly, but by the ordinary working of a method whose core move is to make the contingent look principled.

The honest closing verdict: build-layer Ciborran (confirmed), product-layer Gestell (confirmed and, at the Phase-2-A seams, over-reaching its layer), bricolage-as-codification (confirmed, and more load-bearing than the charter admits, because it is also the project's blind spot).
