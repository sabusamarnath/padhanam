### Cross-context shared-transaction unit-of-work

The S44b intake-canonical orchestrations write across two bounded contexts — intake and portfolio — whose Postgres adapters each open their own per-method `session.begin()` transaction. D128 settled S44b on two-transaction intake-first ordering: the IntakeRecord writes first, and on downstream failure persists as the honest canonical record-of-attempt. A genuine single shared transaction spanning both contexts' writes would need a unit-of-work refactor — the adapter methods accepting an externally-managed session so the orchestration can open one transaction across both. The two tables live in the same per-tenant database, so atomicity is physically possible; the deferral is about the adapter-signature change. The Phase 2-A close question is whether the orphaned-intake-on-failure semantics are acceptable as the permanent shape, or whether the unit-of-work refactor lands. Architecture scope, not single-session hygiene. Surfaced at S44b pre-write reconciliation Finding 3.
