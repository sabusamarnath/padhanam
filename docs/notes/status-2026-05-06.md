## The bet (one line)

A senior product leader can direct the end-to-end implementation of an enterprise-grade agentic platform through Claude Code without writing code. The platform is the artefact; the methodology is the proprietary insight.

## Phase 1 success criteria (verbatim from `bet.md`)

1. A single tenant runs locally with the full stack.
2. One agent can be configured, run, audited, and optimised through the platform's own tooling.
3. The evaluation harness produces meaningful quality signals.
4. The trace capture layer surfaces optimisation recommendations, not just data.
5. The operator can explain every architectural decision and why it was made.
6. The methodology document captures the architect-implementer pattern with enough specificity that another senior product leader could read it and adopt the discipline.

## Ambiguities to resolve

These are gaps between the charter and the as-built reality. Calling them out so the next strategic-mode conversation can decide.

### 1. P2 scope drift: "Identity foundation" never shipped under that name

[charter/packages.md](../../charter/packages.md) line 8 still says **"P2: Identity foundation. Keycloak realm, OIDC integration, SAML SP, SCIM 2.0 endpoint, session management."** [charter/roadmap.md](../../charter/roadmap.md) RICE table still lists P2 as "Identity foundation."

What actually closed as P2 ([archive/p2.md](../archive/packages/p2.md)) is **"First LLM call"**: Langfuse, security baseline, Ollama+LiteLLM, FastAPI skeleton, rebrand. No Keycloak service is in the 14-service stack at P3/P4 close. No SAML SP, no SCIM endpoint exists. D3 ("Identity is Keycloak in V1 Docker Compose") is in the decisions log, but no D-entry rescoped or deferred it.

What does exist on the auth axis: D23 auth middleware on every endpoint with a dev signed-token backend and a "Keycloak-shaped production backend stubbed."

**Interpretation:** the identity-foundation work has been deferred without a recorded decision. The `packages.md` list and the RICE row need to be reconciled with reality. Either (a) Phase 1 will still ship Keycloak/OIDC/SAML/SCIM as a future package (in which case the package list needs a thirteenth slot or P2 needs to be renumbered/renamed), or (b) identity is deferred to Phase 2 as part of production-deployment context (in which case `packages.md`, the RICE row, and `phase-1-prd.md` scope all need an explicit edit + D-entry).

This matters because Phase 1 success criterion 5 ("the operator can explain every architectural decision and why it was made, in terms of the enterprise constraints that motivate it") is harder to defend if a major procurement-relevant constraint — federated identity — is silently absent.

### 2. `packages.md` is stale relative to reality

[charter/packages.md](../../charter/packages.md) line 10 describes P4 as "LiteLLM-backed clients, trace capture middleware, OpenTelemetry GenAI conventions, self-hosted Langfuse wired up. Cost capture from traces lands here per D41." Most of that shipped at P2 (S6/S7). The actual P4 epic note ([p4-epic.md](../../charter/packages/p4-epic.md) line 22) acknowledges this: "Most of what `charter/packages.md` attributes to P4 ... shipped across S6 through S12."

`packages.md` is a static reference and is updated at phase boundaries; the v2 roadmap took over as the living artefact. Worth noting that any stakeholder reading `packages.md` first will mis-map the package boundaries.
