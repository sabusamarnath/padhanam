- Reflection (provisioning reconciliation, prompt 1): Tenants are **dedicated Postgres containers** (`postgres-tenant-{a,b}`) on the database-per-tenant topology (D32), each with its own volume and `POSTGRES_TENANT_<LABEL>_*` env creds; the api container passes those through so ops scripts can build plaintext `TenantConnectionConfig`s at registration time. Registration is `ops/seed_tenants.py` calling `register_tenant(...)`, which stores the connection config **encrypted** in the control-plane registry (D34); `TenantPostgresSettings.for_tenant(label)` is **generic** (env prefix `POSTGRES_TENANT_<LABEL>_`, host default `postgres-tenant-<label>`), so a `personal` label needs no code change. Migration is `ops/migrate.py`, which **iterates every registered tenant** from the registry — so once the personal tenant is registered, `make migrate` migrates it through `0028`. The personal tenant therefore needed **a little new tooling, not much**: the compose service/volume/env passthrough (infra config), and a minimal `ops/dogfood_provision.py` (registration), kept separate from `seed_tenants.py` so the deterministic a/b test set stays clean. Two build-time wrinkles the live run surfaced: the running api predated the env passthrough (recreated it to pick up `POSTGRES_TENANT_PERSONAL_*`), and `make sync-code` does not copy `ops/` (copied it explicitly so the container saw the new provision script) — both ops-iteration artefacts, not design issues.

- Reflection (wipe today vs later, prompt 2): The wipe is a **single clean database drop today** — `DROP DATABASE` + `CREATE DATABASE` inside the `postgres-tenant-personal` container, then re-migrate. Verified live: the personal tenant went from 1 item to 0 while tenant_a stayed at 12 and the three daily-driver tables were re-created. Because the daily driver is **Postgres-only**, that single drop *is* a complete wipe right now. It will **not** stay complete: once personal data reaches Neo4j (the causal-decision-graph slice — a shared instance scoped by `tenant_id` property per D63, **not** a per-tenant database) a complete wipe also needs a **delete-by-tenant-property** Cypher, and once conversational cells capture prompts it needs a **Langfuse trace clear**. Both are named out of scope here and written into the deferred-decisions entry and the runbook, so the later slices inherit the requirement rather than rediscovering it. This is the wipe-completeness argument *for* resolving the personal-graph isolation decision toward a per-tenant/separate graph store: clean-wipeability is structurally harder to guarantee on a shared property-scoped store than on a database you can drop.

- Reflection (synthetic-seed-only boundary, prompt 3): The rule held without strain. All creds are synthetic (`tenant_personal`), the tenant id is a neutral deterministic placeholder, the live-seeded commitment was literally named "SYNTHETIC personal dogfood commitment", and `.env` (which would hold any real values) is gitignored. The one place the rule was *at risk* is conceptual, not actual: the entire point of this tenant is to hold the operator's **real** personal data during dogfooding — so the boundary that matters is "real data lives only in the running `postgres-tenant-personal` volume on the operator's machine, never in the repo, the seeds, the docs, or the synthetic test fixtures." The wipe exists partly to honour that boundary (a clean exit for real data), and the guard exists so honouring it can never collateral-damage the test tenants. `git grep` over the new artefacts found only image digests and the pre-existing synthetic `admin@padhanam.local` — no real identity.

- The guard (load-bearing): three independent layers in `ops/dogfood_wipe.sh` — (1) the container boundary (every destructive statement runs inside `postgres-tenant-personal` via `compose exec`, structurally unable to reach another instance), (2) a hardcoded target (an argument may only re-confirm `personal`, never redirect), (3) a refuse-list (aborts if the resolved service/db match a/b/control names, defending a tampered `.env`). Minor, not promotion-worthy alone, but it rhymes with the live-substrate-verification-gate candidate: tooling that is never exercised against the real container lies about being wired. - Reflection (*stateless-per-turn over HTTP, prompt 1): **Substantive — this is the load-bearing architectural call.** `ConversationState` lives in the *client* between turns. The cell's `cell_payload`/drill-down (D141) did force a persist-vs-thread decision, and I chose **thread, not persist**: the cell takes `prior_focus` at construction and emits the serialised focus in `state.payload["cell_payload"]`; the web turn DTO carries that `cell_payload` to the client, the next `turn` request returns it, and `advance_conversation` reconstructs `prior_focus` via the cell's own `extract_focus_from_cell_payload`. So drill-down/parent/siblings work **statelessly, kept in scope** — no `messages` row, no migration, no new table (F6). The messaging path persists `cell_payload` on the outbound Message because WhatsApp turns are one-shot with no client to hold state; the web client *is* that holder, so reusing the messaging message-persistence would have been a second, redundant state store. The web adapter stayed free of a parallel state machine: it constructs the existing cell and threads its existing state shape; it invents no lifecycle. The one honest nuance is that the cell's **PendingClarification** (medium-confidence + resolution-ambiguity) still persists server-side in the messaging DB — but that is the *cell's* existing user-scoped mechanism (D134, deliberately cross-channel), reused unchanged, not state the *adapter* holds. The precise claim is: the adapter holds no conversation state; the cell keeps its own clarification discipline; the drill-down focus rides the client. That division is what makes "stateless per turn" true without scoping drill-down out.

- Reflection (*citation web render — D131 first web instance, prompt 2): **Substantive.** Citation ids resolve to labels at the **adapter** layer, through the *same* `mirror_portfolio_reader` the cell already reads from, so there is no second read path and no risk of the render disagreeing with the cell: a `case` citation → `get_case_detail(...).case.title`; a `data_point` citation → `get_data_point(...)` value-text. Each becomes `{type, label, ref}` where `ref` is an 8-char short-hex, never the raw UUID — the tests assert no full UUID appears in `reply`, `label`, or `ref` (the cell_payload *does* carry the focus artefact_id, but that is an opaque client-threaded token, not surfaced). The honest gap is exactly the one D138 names: `cited_audit_events` stays **empty** for mirror (the response composes from current portfolio state, and the audit chain is reached transitively through cited IntakeRecords per D128), so the chips today are `case`/`data_point` only; the resolver carries the intake/audit branches defensively (short-hex labels) for a future implementer that populates them. The resolution shape is the **first web instance** of D131 render — it does not yet recur (WhatsApp render is channel-text, not chips), so per the captures-promotion threshold I did **not** open a candidate; if a second chip-rendering surface lands (the dashboard, a Slack card), the `{type, label, ref}` resolver-at-the-adapter shape is the thing to watch for promotion at the Phase 2-A close audit.

No Commitment-focus gap forced a new cell — a Commitment-specific cell is named out (D158) until dogfooding shows a Commitment needs conversation; the Case cell carries this cut.
