- Reflection 1 — Shared substrate, or third separate instance? **Third separate instance, and it is the crystallise point — answered decisively, not just asked.** Calendar and email are parallel contexts (each its own `*_connections` table, cache table, source port, sync pipeline, and Nango-proxy adapter; the `connections` table is per-context, confirmed not shared), and tasks followed the template exactly. That makes three near-identical external-cache ingestion contexts, past the two-threshold point and squarely in the structural-duplication cluster the P13 baseline named. The duplication is concrete: the `Connection` value object (near-identical three times), the connection repository (save/get on a `*_connections` table), the Nango-proxy adapter shape (Bearer + Provider-Config-Key + Connection-Id headers, the 200/4xx-config/5xx-retryable `_handle_response`), the re-pullable encrypted store (enc_* content + upsert-on-conflict + tombstone + the read), and the sync skeleton (drain → upsert/tombstone → set-diff). The genuine per-provider variation is only the wire-parse and the cache's structural columns. **Disposition (in D167): extract the shared ingestion substrate — a generic Connection + ConnectionRepository + a Nango-proxy client + a re-pullable encrypted-cache base + a sync skeleton, with per-provider adapters supplying parse + column mapping — as a named slice *before Trello*, the fourth adapter.** Three is tolerable; four is not — the same do-not-let-known-debt-compound discipline as the S64 test-integrity slice.

- Reflection 2 — Did the D155 read-only re-pullable cache model hold, or did Google Tasks' shape strain it? **It held, cleanly.** `google_task_id` is a stable key, so upsert is idempotent, deleted tasks tombstone, and a set-diff against the stored ids tombstones any that vanished beyond the `showDeleted` window — the same complete-refresh guarantee email uses. The three shape questions the prompt named all resolved without strain: the **tasklists** are a two-call N+1 (drain lists, then each list's tasks) — a shape difference from calendar's single `events.list`, but identical to email's N+1, so an inherited pattern, not new strain; **completed-task semantics** fit as structural fields (`status=completed` + `completed_at`); and **recurring tasks** turned out to be a non-problem because **the Google Tasks API exposes no recurrence at all** — a recurring task surfaces as individual instances, each a normal cache row, so there is nothing to model. The one real micro-decision was preferring set-diff over relying on `showDeleted` alone (a long-ago-deleted task simply vanishes from the response), which is the email precedent. Net: tasks are the *easiest* of the three caches (no embedding, no chunk store, no incremental-sync token dance), which is itself evidence the D155 model generalises down as well as across.

- Reflection 3 — What does P18 need from this cache that is not yet there? P18 correlates tasks ↔ calendar ↔ email into units of work by title + time proximity (D166). From this cache it has what it needs to *read*: the title (encrypted — P18's matcher must decrypt to compare, so correlation runs server-side with crypto access, noted), the `due_at` time anchor for proximity matching against calendar blocks, and a stable identity (`google_task_id` / the row id) to attach an edge to; and `list_tasks(include_completed=False)` already lets P18 take only open tasks as correlation candidates (completed tasks are history, not work to correlate). What is **not** here, by design: a place to record the correlation edge — that is P18's to add as a **Padhanam-native edge**, never written back into the tasks cache (D166 "not written back"; D167 read-only) — and any link to the goal facet, which is P19. So the cache is correlation-ready as a read source; P18 adds the edge store and the title/time matcher, touching neither this cache's write path nor Google. The one thing P18 will likely want that is absent is a normalized title for matching (the raw title is all we store); whether to add a derived match-key here or compute it in P18's matcher is a P18 call, flagged now.
