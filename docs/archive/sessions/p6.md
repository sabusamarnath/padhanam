- Reflection: Reflection prompt 1 (parser-as-port shape) — The Parser Protocol held cleanly under both adapters with no leaky abstractions back into the use case. ParsedContent/ParsedChunk as the boundary type let MarkdownParser emit `{heading_text, heading_level}` and PlainTextParser emit `{paragraph_index}` through the same `Mapping[str, object]` shape, and parse_source treated both uniformly. Two architectural observations worth recording for the PDF and DOCX parsers when they land. (a) The structural_metadata shape is parser-defined and not validated by the use case; this is intentional (D61's open-ended Mapping leaves room for `{page_number, page_text}` from PDF or `{section_name, paragraph_in_section}` from DOCX without a domain-type extension), but downstream consumers (S22 retrieval, P11 recommendation) will need a discovery mechanism that does not depend on parser-specific knowledge. The likely shape is a structural_metadata schema versioning field alongside the chunk metadata; landing it pre-emptively at S19 would be paper architecture (only two parsers exist), but the discovery question is worth surfacing at S22 framing when retrieval becomes a real consumer. (b) ParserError as a single error class works for S19's two parsers because both failure modes are "content is structurally invalid for the format"; PDF's failure modes (encrypted pages, malformed cross-references, OCR failures on scanned pages) may need richer signal that distinguishes "we cannot parse this format at all" from "we parsed most of it but lost N pages". The ParserError signature does not foreclose this — the caller catches and writes parsing_error_text — but parsers may want a richer return shape (success-with-warnings) that needs framing at the PDF session.

  Reflection prompt 2 (SKIP LOCKED concurrency) — The SKIP LOCKED pattern survived under the threaded concurrent-workers test cleanly. Two `padhanam ingest worker` invocations launched ~50ms apart against a single registered source produced exactly one claim-and-process cycle and one immediate empty-claim return; the integration test asserts `sorted(processed_each) == [0, 1]`. The within-transaction state transition (the adapter does the SELECT FOR UPDATE SKIP LOCKED + UPDATE state='parsing' inside `session.begin()`) prevents the race-then-re-poll path that would have produced double-processing without it. One forward-affordance worth recording: the test exercises two workers in the same Python process via threads, which is enough to prove the asyncpg + SQLAlchemy 2.0 path delivers the locking guarantee, but does not exercise the multi-process or multi-machine pattern that production would have. The Postgres lock is held at the connection level and SKIP LOCKED is a server-side primitive, so the multi-process case is structurally identical, but the next session that adds horizontal worker scaling (production deployment context) should rerun the contention shape with two separate processes to confirm the locking contract holds across connection pools.

  Reflection prompt 3 (worker reentrancy and idempotency) — The reentrancy model needed no refinements during build for the success and cross-tenant cases. The idempotency case the brief named (re-running against an already-parsed source is a no-op) holds because the SKIP LOCKED query filters on `state = 'received'` and parsed sources are excluded; the test confirms `processed 0 source(s)` on re-run. The recovery story for a worker that died with state in `parsing` (the brief's specific concern) is the gap S19 leaves open: the current adapter has no recovery query that re-claims `parsing` rows after a worker process dies. The schema supports the recovery path (state CHECK includes `parsing`; UNIQUE(source_id, chunk_index) prevents duplicate writes on re-claim), but no use case exercises it. Two options surfaced at build for the recovery shape: (a) a separate `claim_stale_parsing_rows(stale_after=...)` method on the repository that finds rows in `parsing` whose updated_at is older than the threshold and re-claims them; (b) a heartbeat column on the source row that a long-running parse updates periodically, with the recovery query keying off heartbeat staleness rather than updated_at. Option (a) is simpler and likely sufficient at Phase 1 scale; option (b) is the production-ready shape. Neither lands at S19 because the failure mode it addresses (worker process dies mid-parse) does not yet have an observed instance, and the structural-promotion-threshold convention names the trigger for the recovery use case as "first observed worker mid-parse death" or "first session that cares about worker uptime guarantees" — both defer to production deployment context. Recorded as carryover in the active-P6 carryover list.

  Reflection prompt 4 (OTel helper promotion at fourth-caller threshold) — The lift was the right call and exposed a small follow-on issue worth recording. The lift mechanically removed the inline TracerProvider/OTLPSpanExporter/BatchSpanProcessor + set_tracer_provider stanza from four call sites, replaced each with `init_tracing("service-name")`, and shrank net code by ~80 lines while removing four ObservabilitySettings constructions and four exporter constructions. The follow-on: the lift dropped the `_provider = ...` local binding the e2e setup scripts later used for explicit `force_flush(timeout_millis=...)` calls. The integration tests caught it on first run (NameError on `_provider`); the fix reads the helper's return value into `_provider`, restoring the binding. Worth surfacing as a methodology observation: when lifting a multi-line block to a single helper call, the lift's mechanical correctness is verified by the import-linter and AST tests, but local-variable bindings the lifted block produced are brittle to the migration. The fix is one line per script (`_provider = init_tracing(...)`) and the helper's return-value contract was written for exactly this case, but the failure mode is silent at unit-test collection time and only surfaces when the e2e scripts execute as `python -c "..."` inside the container. The discipline candidate: when the lift target produces a return value, the migration touch-points should preserve any local binding by name unless explicitly named for removal, and integration tests that exercise the scripts should run as part of the lift commit's verification rather than after-the-fact (which is what happened: the fix landed in a separate commit because the failure surfaced after commit 7's full-pytest run). The AST enforcement test at `test_tracer_provider_setup.py` is the correct shape for fencing future drift — future bare-script drivers must import the helper rather than re-introducing inline setup, and the test catches drift at the syntax-tree level before lint-imports' allow_indirect_imports = false would.
