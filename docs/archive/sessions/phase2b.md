## S74 — D159 multi-calendar support: connection-scoped meetings, the professional-coverage unblock (D176) (build mode)
roles: architect (the collision-scoping vs age-out-sweep call, the connection-scoped calendar_id design, the forward-compat naming), engineer (the schema + migration + adapter threading + tests, the live Postgres verification), analyst (the Step 0 reconciliation — the shared-event-id finding, the no-sweep finding, the backfill-safety check), technical writer (D176, this entry)
mode: build session — Phase 2-B Epic E1 opener, the architectural unblock the gate audit's source dependency named. Schema migration on a populated core entity plus adapter; charter ahead of code; combined schema+adapter feat commit per the prompt's escape hatch.

S74 builds D159 multi-calendar support (D176) so a second calendar account can enter the corpus without aging out or colliding with the first — the unblock for professional coverage (roadmap v9's named source dependency). `Meeting` gains a connection-scoped `calendar_id`, the identity key extends to `(tenant_id, calendar_id, google_event_id)`, the connection unique key relaxes to permit a second account per tenant, the scoped full pull and every write-path operation scope by `calendar_id`, and migration 0031 backfills the existing 979 personal meetings by constant-fill. **This connects nothing and seeds nothing** — it makes connecting the work calendar safe.

- **Step 0 (against the live tree + running stack).** (1) **Meeting key needed extending — confirmed.** The single-column `(tenant_id, google_event_id)` is collision-prone *commonly*, not rarely: a meeting both accounts are invited to shares **one** Google event id across calendars (the organizer's id, propagated to attendees), so a second account's pull would overwrite the first's copy. Extended to `(tenant_id, calendar_id, google_event_id)`. (2) **Connection unique** relaxed from `(tenant_id, provider, provider_config_key)` to add `provider_connection_ref` (a distinct account = a distinct ref = a new row; same account re-connects upsert). (3) **Age-out is NOT account-wide** — `sync_calendar` has no set-diff sweep; it tombstones only per returned-cancelled event (`showDeleted`). So the load-bearing change is collision-scoping the write path, not scoping a sweep. (4) **979 personal meetings** (0 cancelled); **0 orphan meetings across all tenants** (every meeting maps to a `google_calendar` connection) → the connections-subquery backfill covers all, NOT NULL safe. Personal connection id `6c37a349-391c-4f5f-bcb3-9d70844db0e3`. (5) **Per-connection sync confirmed**; `calendar_id = str(connection_id)` stamped in the store loop. (6) **Vendor reconciliation:** `calendar_id` carries *our* connection id, not a Nango/Google identifier, so the column has no vendor dependency; the `"primary"` pull and the Nango connection-ref semantics are unchanged. Latest migration 0030 → 0031.
- **The build, one feat commit (`31fcad4`).** `Meeting.calendar_id` (default `""` for pure-domain test construction; the sync path sets it via `meeting_from_event`). `_tables.py`: the column + both unique-constraint swaps. `meeting_store`: the write path (upsert ON CONFLICT, tombstone, change-detection get, set_embedding) scoped by `calendar_id`; the read-path `get_by_event_id` takes an optional `calendar_id` (sync passes it for the exact row; the conversation cell omits it and resolves any calendar's copy of a shared event — fine for a display read). `sync_calendar` + `index_meeting` thread it. `connection_repository` upsert keys on the new constraint. Migration 0031: add column, constant-fill backfill, swap constraints, reversible downgrade.
- **Live verification against real Postgres (no real-table mutation; the running image is old so the full alembic apply + image rebuild + e2e smoke are the operator-gated close step).** AC3 backfill dry-run: **979 total, 979 resolve, 1 distinct calendar_id** — the constant-fill covers every row. AC1/AC4 key semantics (temp table): two calendars' copies of a shared event id **coexist (rows=2)** while a true triple-duplicate is **rejected**; the old single-column key would have rejected the second row. AC6 scoped tombstone (temp table): `WHERE calendar_id='cal-work'` cancels **only** the work copy (UPDATE 1), personal copy intact — a full pull of one calendar never touches another's.
- Produced: charter commit (`fbdd759`: D176 + the D159 resolution pointer per the supersession convention + current-package marker + ToC regen to 176 entries; the second-calendar deferral lived inside D159, not a standalone deferred-decisions entry, so none was closed there) ahead of the feat commit (`31fcad4`). +1 threading unit test; fakes updated for the new signatures (sync/index fakes take `calendar_id`; the cell fakes unchanged — the cell omits it). **Unit suite: 2451 passed, 0 new failures, 0 skipped.** The 1 failure is the **pre-existing wall-clock-coupled** `daily_driver` goal test (`test_list_goals_joins_lever_and_recommends_raise`, RAISE→HOLD as the real date 2026-06-09 advanced past its `_NOW=2026-06-07` fixtures) — stash-confirmed on HEAD, the owed clock-seam debt, not this change.
- Reflection — **the key needed extending, decisively.** Step 0 confirmed it, and upgraded the reason from "rare collision" to "common": cross-account *shared invited events* carry the same Google event id, so without `calendar_id` in the key the work pull silently overwrites the personal copy of every meeting both accounts are on. That is not an edge case — it is the normal case for a senior leader whose work and personal calendars overlap on the same meetings.
- Reflection — **the age-out was not a sweep, which corrected the swap-path assumption.** The brief's "swap ages out the personal corpus" assumed an account-wide deletion sweep. Step 0 found none — `sync_calendar` only tombstones per returned-cancelled event. So a swap's actual harm is collision-overwrite plus staleness (personal-only events never refreshed), not sweep-deletion. The load-bearing change is therefore collision-scoping the write path, exactly what was built; "scope the age-out per connection" was a non-issue because there was no sweep to scope.
- Reflection — **connection-scoped is right; the name anticipates more.** At the current `"primary"`-only pull, one connection = one calendar, so `calendar_id = connection id` is the correct granularity. A future need for per-calendar identity *within* one account (a person with several calendars on one login) would refine the `calendar_id` *value* (e.g. connection id + Google calendar id) without a rename or a new column — which is why the column is named `calendar_id` rather than `connection_id`. Disposition: not built now; the name carries the option.
- Enforcement layer: no new import-linter/AST contracts. The new DB-level invariants are the two unique constraints — `ux_meetings_tenant_calendar_event` (cross-account collision prevention) and `ux_connections_tenant_provider_config_ref` (a second account coexists, the same account upserts). The migration's reversible downgrade fails by design if a tenant has grown a second account (the state this exists to support) — the honest behaviour.
- methodology: Step 0 against the live stack did the decisive work twice — it upgraded the collision risk from rare to common (the shared-event-id finding, which a from-memory read would have under-weighted) and it dissolved the brief's age-out-sweep assumption (no sweep exists), redirecting the build to the change that actually mattered. ### S101 pivot finding (strategic, 2026-06-18) — the CDD-authoring pivot (D200)

The first live use of the S101 Map on the real 8-goal corpus surfaced, on first use, that **an auto-derived, read-only generic CDD has decreasing value as you look at it.** The links are machine-matched (166 emails attached to Get a job), the elements were script-seeded, the relationships are generic (every goal wears the same `SERVES`/`LEVER_FOR` with nothing said about what those elements are *for that goal*), and there is no surface to correct any of it. A generic graph is a tagging system in a graph's clothes; on whole-life personal goals it is wrong often enough that, uneditable, it cannot improve — and no correction means no learning, which guts the optimization layer that is the platform's differentiator. This is the artefact proving the reflection, exactly as Phase 2 intended and **faster than the formal dogfood week**; the week now reads against a known pivot rather than starting cold. The pivot is settled as **D200** (the CDD is authored per goal as the context layer, edited as the learning signal, co-evolving through a bidirectional human-proof gate; intermediaries/externals pulled forward from deferred depth to foundational defined context), with the **"graph's meaning is authored" principle** (`charter/principles.md`) and the **roadmap v13** re-sequence. The build sessions follow this decision; they do not precede it.
