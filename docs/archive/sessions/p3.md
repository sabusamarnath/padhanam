Substantive paragraph on the production-deployment shape: when production lands and `make migrate` is replaced by infrastructure-as-code, the equivalent two-phase orchestration looks like a CI job (or a Kubernetes Job manifest) that runs the same `python -m ops.migrate` against a production cluster, reading `ControlPlaneSettings` from the secret-manager backend rather than `.env`. The failure-mode handling changes in three concrete ways: (a) the runner gains a `--retry-failed-only` flag that reads each tenant's `alembic_version` table directly and skips tenants already at head, so a retry after a partial failure is bounded to the unmigrated tenants — at dev scale of 2 tenants the existing iterate-everyone idempotency is fine, but at 100+ tenants the no-op `alembic_version` queries become observable per-run cost. The runner's failure semantics stay the same — a per-tenant transactional failure raises and stops the affected tenant, but other-tenant migrations in the same parallel batch may continue. The architectural commitment from D32/D36 (no cross-tenant atomicity) is what makes parallelism safe; if cross-tenant atomicity were required, parallelism would need to be replaced by a Saga, and the production runner would be substantially more complex.
