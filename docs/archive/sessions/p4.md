  Reflection prompt 2 (pricing-table format choice) — Format (b) was chosen: a separate `ModelPricing` Pydantic model and a module-level `PRICING_TABLE` dict alongside `InferenceSettings`. Format (a) — pricing as a typed field on `InferenceSettings` — was rejected because pricing is pure code data, not environment-driven, and putting it on Settings would force callers to construct a Settings instance (with the required `litellm_master_key` secret) just to read pricing; tests would have to provide a master key for every cost-related fixture. Format (c) — YAML/TOML under `ops/` — was deferred until pricing complexity (multi-region rates, time-zoned rates, large rate cards) justifies the extra load surface; at the current single-region, two-row scale, file-IO is wasted complexity. The decision surfaced one concern worth flagging for Phase 2 framing: production pricing is rarely a single dict per model. Vendors publish per-region rates, time-zoned rates (off-peak discounts), tier rates (volume discounts), and reserved-capacity rates that differ from on-demand. The `PRICING_TABLE` shape committed at S14 is honest for the current scale but will need a structural change at the moment Phase 2 introduces multi-region or any rate-card complexity beyond a single price-per-model. Capturing as a forward note for Phase 2 framing rather than over-engineering at S14 — the YAML/TOML escape hatch (format c) is the cleanest landing once that complexity arrives, and the structural-promotion threshold convention is the right gate for when to pull it in.

  Reflection prompt 3 (cost-ceiling forward-affordance columns) — The migration's forward-affordance comments held against AST tests and tenant-isolation tests, but with one concern worth surfacing. The columns are guarded at the schema layer by NULL defaults (no value lands without an explicit write) and CHECK constraints (the action enum cannot accept unknown values), but no AST or import-linter rule prevents future code from accidentally reading or writing them. The S14 registry adapter's `Table` definition includes the cost-ceiling columns purely so SQLAlchemy reads them on `SELECT *`, but no use case touches them; a future session could add a consumer without realising that Phase 2 enforcement architecture has not landed. The structural-promotion threshold (a comment-level rule that bites three times across a package gets promoted to a parser- or AST-level test, per S11/S12) would apply if accidental consumption surfaces twice more — at that point the candidate is an AST test that walks `contexts/` and `apps/` for any reference to `cost_ceiling_usd_monthly` or `cost_ceiling_action` outside the registry adapter's `Table` definition and the migration file, and fails CI when one is found. Naming the candidate now so the structural promotion has an obvious shape if it bites; not promoting at S14 because the rule has not bitten yet, and structural enforcement that anticipates rather than responds to drift produces the wrong incentive structure (rules added before they bite are paper rules).
