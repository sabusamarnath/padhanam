# Package 5: Evaluation harness

Closed at S18 close. Reconciles against the v1 epic note at
[charter/packages/p5-epic.md](../../../charter/packages/p5-epic.md) per D43.

## Goal

The evaluation harness scaffolded as a bounded context at
`contexts/evaluation/`, with the data model that captures the
architecture's posture on human oversight per D53. Reading C: humans
are load-bearing in the scoring loop; the data model reflects that
even though UI for human review defers to a later package. At P5
close: tenant-authored scoring sheets exist as versioned, immutable,
role-gated data in per-tenant DBs; deterministic (`exact_match`) and
LLM-as-judge (prompt-applier) appliers run against agent outputs and
produce scores against those sheets; cost-per-successful-task is
computable from the trace cost data captured at P4; a CLI runner
(`padhanam eval run` and `padhanam eval report`) produces a regression
report comparing two runs of a scoring sheet against an interaction
set, rendered in markdown text or structured JSON. Recommendation
surfaces consuming the harness output (P11) and human-review UI are
out of scope.

## Architectural commitments shipped

Seven D-entries (D53-D59) — denser than P4's two (D49, D50) and
reflective of P5's wider design space (foundations, replay, cost-
query, regression report, async-ingestion handling). The structural
shape:

- **D53.** P5 evaluation harness framing — scoring sheet primitive
  (the user-facing name for what eval literature calls a rubric);
  per-tenant storage; deterministic primitives in code, prompt
  appliers as data; Reading-C posture (data model absorbs human
  review at the column level; UI defers to P10/P11). Committed at the
  P5-open strategic block, not at a build session. Kano: must-have.

- **D54.** Applier port shape — single polymorphic async `ApplierPort`
  with `applier_type` dispatch in the adapter. Build-time return-type
  deviation from framing recommendation (`str | None` instead of
  `RubricApplication`) recorded in the entry text per the structural-
  honesty argument. Kano: performance.

- **D55.** Score representation on `rubric_applications` — `text`
  with criterion-level interpretation. Direct SQL aggregation
  foreclosed in exchange for honest cross-rubric scoring; the
  criterion is the architectural authority on what its scores mean.
  Kano: must-have.

- **D56.** TraceQueryPort method shape — interface segregation;
  separate methods per access pattern (`get_trace` retains its full-
  trace shape for the recommendation engine; `get_costs_by_trace_ids`
  serves cost-rollup queries). The port grows by adding methods, not
  by widening existing ones. Kano: performance.

- **D57.** Cost-query path — two-layer abstraction
  (evaluation → observability use case → trace store port).
  `contexts/evaluation/` defines its own `CostQueryPort` + adapter
  that calls `contexts.observability.api.query_cost_by_trace_ids`;
  D27's vendor-isolation discipline holds end-to-end through the
  facade pattern. Import-linter refined to express D17's facade-as-
  public-surface mechanically. Kano: must-have.

- **D58.** Regression report shape — single-baseline comparison;
  per-criterion success-rate deltas joined across revisions by
  criterion name; aggregate-only cost-per-task; text and JSON output
  formats. Build-time field-name and field-set refinements from the
  S18 brief (revision-id over run-id; aggregate-only cost) recorded
  per the framing-prompt-as-recommendation methodology pattern.
  Kano: must-have.

- **D59.** Langfuse trace-ingestion asynchrony — polling-with-timeout
  at the cost-query path. `wait_for_trace_availability` on the
  LangfuseHTTPTraceQueryAdapter replaces S17b's 8s force-flush-and-
  sleep with honest waits. Tenant-filtered polling preserves D24's
  isolation discipline at the polling surface. Kano: must-have.

## Drift surfaced

- **D54 build-time return-type deviation from framing recommendation.**
  The S16 framing prompt named `RubricApplication` as the
  `ApplierPort.apply` return type; the build returned `str | None`
  per the structural-honesty argument that scoring is the applier's
  responsibility while record assembly belongs to the use case. Caught
  during build, recorded explicitly in D54's text and the S16
  reflection. First instance of the framing-prompt-as-recommendation
  pattern at P5; the pattern recurred at S17b's `>= 0` brief assertion
  adjustment (qwen at zero rates per D49) and at S18's
  `baseline_run_id` → `baseline_revision_id` field-name and
  CriterionDelta cost-field-set refinements.

- **S17b's `total_cost_usd > 0` brief assertion adjusted to `>= 0`
  during build.** The brief's positive-cost assertion was honest
  about architectural intent (cost is non-zero) but wrong for the
  dev posture (qwen2.5:7b is at zero rates per D49); the test
  honestly asserts `>= 0` and documents the deviation. First
  reconciliation case under the briefs/ convention introduced at
  `b6a1bcc`; the no-in-place-edits rule held — the brief stays at
  v1, the deviation lives in the session log reflection and the
  test docstring.

- **USD-currency assumption baked across cost-bearing surfaces
  without deliberate D-entry.** D49's OTel namespace
  (`gen_ai.cost.*_usd`), the `CostBreakdown` value-object field
  names (`total_usd`, `input_usd`, `output_usd`),
  `CostPerSuccessfulTaskResult.cost_per_task_usd`, and
  `AggregateMetrics.baseline_cost_per_task_usd` /
  `candidate_cost_per_task_usd` / `overall_cost_per_task_delta_usd`
  all bake USD as an architectural commitment without a deliberate
  framing-time choice. Caught at S17b post-close by operator
  question at S18 framing prep; corrected via the strategic commit
  `24561c9` adding a deferred-decisions entry committing the
  multi-currency evolution to Phase 2 plus a methodology Failure-
  modes entry naming the drift class
  ("implicit-assumption-as-architectural-commitment"). First
  instance of this drift class at P5 — distinct from the silent-
  deferral drift (D52 at P3-post-close) and the fabrication drift
  (PRFAQ name attribution at P3-post-close) the methodology
  document already names.

- **The S17a alembic version_num 32-character constraint.** The
  initial migration filename `0004_add_trace_id_to_rubric_applications`
  (40 chars) failed at first migrate attempt; renamed to
  `0004_add_rubric_apps_trace_id` mid-build. Operational drag at
  the migration-naming layer; not a forward-affordance failure but
  a small unwritten constraint worth documenting at the next

  convention.

- **The S17a/S17b/S18 script-driver OTel initialisation surface.**
  Bare-Python paths outside FastAPI need their own `TracerProvider`

## Durable lessons

- **The briefs/ convention earns its keep at first reconciliation.**
  Introduced mid-package at `b6a1bcc` (after S17a close, before S17b
  launch) under the methodology document's "Session brief
  preservation" section. The convention's load-bearing rule is
  no-in-place-edits: brief preservation is forward-looking
  specification; deviations land in the session log reflection or
  the relevant D-entry text. The S17b `>= 0` adjustment validated
  the rule at first reconciliation — the brief stayed at v1, the
  reflection captured the deviation, and the audit trail stays
  symmetric between intent and outcome. The S18 brief-to-build
  refinements (revision-id over run-id; aggregate-only cost) are
  the second reconciliation case; the rule continues to hold.

- **The drift-class taxonomy emerging from P5 has three named
  shapes.** Silent-deferral (omission across multiple sessions; D52
  at P3-post-close exemplifies). Fabrication (invention within a
  single artefact draft; PRFAQ name attribution at P3-post-close
  exemplifies). Implicit-assumption-as-architectural-commitment
  (a default that should have been a deliberate choice; USD-currency
  at S17b post-close is the first instance and the methodology
  Failure-modes entry names the class). The taxonomy lives in
  `charter/methodology.md`'s Failure modes section; the three
  classes share the property that the model's default was the wrong
  default and the operator's surfacing question was the recovery
  surface. The recurrence pattern: each drift class earns a
  Failure-modes entry on first instance per the methodology's
  discipline-vs-pattern asymmetry — descriptive observations need
  recurrence to earn naming, but corrective discipline-additions
  land on a single observed drift event.

- **The cost-query two-layer abstraction (D57) sets the structural
  precedent for every future cross-context observability consumer.**
  The pattern: the consumer defines its own port and adapter
  (`evaluation.CostQueryPort` + `CostQueryAdapter`); the adapter
  calls the source context's api facade
  (`contexts.observability.api.query_cost_by_trace_ids`). D27's
  vendor isolation holds end-to-end; D17's facade pattern provides
  the import target; the import-linter refinement at S17b made the
  facade-as-public-surface contract mechanically enforceable rather
  than convention-only. The recommendation engine at P11 inherits
  this pattern when it consumes evaluation data; the active testing
  scheduler at P12 inherits it when it consumes recommendation data.

- **Polling-with-timeout (D59) is the architectural answer to
  vendor async-ingestion behaviour, not a Langfuse-specific quirk
  workaround.** S17b's 8s force-flush-and-sleep was the brittle
  workaround; D59's polling shape is the discipline. Any future
  observability backend whose ingestion has an async window inherits
  the polling shape; backends that materialise traces synchronously
  return True immediately from the helper. The structural-promotion
  threshold applies asymmetrically here per the methodology's
  Failure-modes-vs-Patterns-observed asymmetry: corrective
  discipline-additions land on first observation; descriptive
  patterns wait for recurrence.

- **The api-as-stub-vs-api-as-implemented distinction surfaced at
  S17b is a methodology Patterns-observed candidate.** S6 shipped
  `contexts.inference.api` with both type re-exports and the working
  application-layer use case (`request_completion` calling the
  LiteLLMAdapter); S7 shipped `contexts.observability.api` with type
  re-exports only and a no-op stub adapter, because no consumer
  existed at S7 and shipping a half-built path would have been
  speculative. S17b inherited the implementation work — three of
  ten S17b commits landed on the observability side (real adapter,
  first application-layer use case, value-object surface). The
  framing-prompt contingency split at S17b ("commit 2 → 2a/2b if
  inference application surface needed exposing") was unnecessary
  because D17's facade rule means cross-context callable surfaces
  always exist. Likely recurrence at P11 when the recommendation
  engine consumes observability for trace aggregation; if the
  pattern recurs there with the same shape, the Patterns-observed
  threshold (third instance) is met and the methodology document
  gains a new entry.

  upload + two-track pipeline to pgvector + Neo4j + retrieval
  interfaces. The eval harness scores outputs; it does not ingest
  sources.

- **Agent CRUD (P7).** The authoring surface for agents that the
  eval harness scores. P5's interaction-set primitive is forward-
  compatible with agent-trajectory inputs (the `interactions.input`

  trajectories without schema variation).

  inference; the `ModelConfig` value object surfaces sampling
  parameters as forward-affordance fields not yet threaded through
  the inference port.

  is single-baseline per D58; multi-baseline tracking lives in run
  history with timestamps and per-revision aggregation. P9 builds
  the substrate; P11 consumes it for trend-aware optimisation
  recommendations.

- **Audit log viewer (P10).** Includes the human-review UI for
  evaluation per D53's Reading-C posture (data-substrate landed at
  S16; UI deferred). P10 implements the read surface for
  rubric_applications with `human_score`, `reviewed_by_user_id`,
