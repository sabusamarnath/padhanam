## Goal

Source ingestion as the agent runtime's data substrate. P6 ships
the upload-to-retrieval pipeline so that at P6 close, a tenant can
submit a source file through the CLI, the platform parses it,
embeds chunks into pgvector on the tenant's data plane, extracts
entities and relationships into Neo4j, and exposes the indexed
content through a unified retrieval interface ready for the agent
runtime at P8 to consume. A single `contexts/ingestion/` bounded
context owns the full vertical from upload through retrieval; the
pipeline runs asynchronously behind a per-stage status field on
the source row, with `SELECT ... FOR UPDATE SKIP LOCKED` against
pending rows as the queue mechanism. Two destination tracks
coordinate: pgvector indexing on per-tenant Postgres (per D32) and
graph indexing into a shared Neo4j instance (per D63's deviation
from D32's per-instance posture). A source becomes queryable only
when both tracks complete, enforced as a `state = 'indexed'`
predicate at retrieval time per D65's cross-track readiness
commitment.

## Architectural commitments shipped

Six D-entries (D60-D65) — denser than P4's two and P5's seven,
reflective of P6's two-vendor-surface design space (Ollama
embedding model joins LiteLLM at S20; Neo4j enters at S21) and
the cross-track coordination at S22. The structural shape:

- **D60.** P6 source-ingestion framing — asynchronous pipeline
  shape, one ingestion bounded context, per-stage status on the
  source row as the worker reentrancy seam, idempotent worker
  writes, Postgres `SELECT ... FOR UPDATE SKIP LOCKED` as the
  queue substrate (no new infrastructure dependency), CLI
  surface at `apps/cli/`, two-track coordination across
  pgvector and Neo4j, two architectural questions (Neo4j
  topology and within-tenant segmentation primitive) deferred
  to implementation. Committed at the P6-open strategic block.
  Kano: must-have.

- **D61.** Parsing scope at P6 close — markdown and plain text
  at S19 via `Parser` port and two adapters; PDF, DOCX, HTML
  defer to sessions with real consumers. `markdown-it-py` over
  `markdown` and `mistune` for ecosystem alignment and AST
  ergonomics. Build-time refinement: `markdown-it-py>=3.0`
  framing → `4.0.0` actual via lockfile resolution
  (mechanical class). Kano: must-have on the port shape;
  performance on specific format coverage.

- **D62.** Embedding model default and chunk-embedding column
  shape — `nomic-embed-text:v1.5` via Ollama through LiteLLM's
  OpenAI embeddings path; single `embedding vector(768)`
  column on chunks; HNSW `vector_cosine_ops` with pgvector
  defaults; `default_embedding_model` on InferenceSettings;
  PRICING_TABLE extends at zero rates. Build-time refinement:
  the model card's task-prefix requirement (`search_document:`
  for corpus, `search_query:` for query) lands as
  prefix-prepending in the adapter (architectural-cost class,
  recorded in D62 Choice text); per-stage `claim_pending_*`
  methods chosen over generalised `claim_pending_in_state(state)`
  (architectural-cost class, recorded in D62). Kano: must-have
  on both halves.

- **D63.** Neo4j topology — shared instance with tenant-property
  scoping enforced through a `TenantScopedNeo4jSession` wrapper
  plus the `neo4j-confined` import-linter contract plus the AST
  enforcement test plus tenant-isolation contract tests on both
  reads and writes. Explicit deviation from D32's per-instance
  Postgres posture, with reasoning (Neo4j Community has no
  multi-database equivalent; per-tenant containers cost ~1GB
  RAM per tenant in dev with linear operational complexity);
  three named production-deployment revisit triggers
  (residency, blast radius, security-review) recorded in the
  deferred-decisions entry. The user's risk-3 guidance
  ("the cleanest architectural shape is a tenant-aware Neo4j
  session wrapper, mirroring how Postgres-side tenant scoping
  works") was the operator-driven course-correction that
  rerouted the brief's per-query predicate-discipline framing

- **D64.** Graph extraction shape — Qwen 2.5 7B via LiteLLM

  on `(tenant_id, name, entity_type)` for entities and the
  five-component composite for relationships, MERGE for
  idempotent re-extraction. Build-time refinement: tool-calling

  via Ollama through LiteLLM produced malformed function
  arguments (`{"text": "<original prompt>"}`); JSON mode
  (`response_format={"type": "json_object"}`) produced clean
  schema-conformant output (structural-honesty class, recorded
  in D64 Choice text); `get_*_for_source(source_id)` →
  `get_*_by_chunk_ids(chunk_ids)` port-shape refinement at the
  GraphRepository (architectural-cost class). Kano: must-have

- **D65.** RetrievalClient port surface, cross-track readiness,

## Drift surfaced

- **markdown-it-py version drift at S19** (mechanical class).
  The brief's `markdown-it-py>=3.0` framing resolved to
  `4.0.0` at lockfile time; D61's Choice text was updated at
  build to reflect the actual version. Pattern: vendor library
  version drift between brief draft and build resolution.
  First instance of the framing-prompt-as-recommendation
  pattern at P6.

- **Parser-dispatch responsibility split at S19** (structural-
  honesty class). The brief positioned parser dispatch in the
  application layer; build surfaced via `lint-imports` that the
  dispatch logic needed to live partially in the adapter to
  avoid a layering violation (the application layer cannot
  know about adapter-specific resolution). Resolved by
  splitting `parser_dispatch.py` (file-extension-to-file-type)
  in application from `get_parser` (file-type-to-parser
  instance) in the adapter registry. Recorded in S19 reflection.

- **Worker shape architectural-cost at S19** (architectural-
  cost class). The brief named dedicated Compose services per
  tenant for the worker as the production-shape commitment;
  build chose `make ingest-worker` against the shared Compose
  service with a `--stages` flag (later) for development cost
  reasons. The brief's option remains valid for production;
  the deviation is honest about the architectural-cost trade-
  off and recorded in the S19 reflection plus the commit body.
  Production-shape worker topology defers to production-
  deployment context.

- **Ollama tool-calling fidelity gap resolved by JSON mode at
  S21** (structural-honesty class). Pre-write reconciliation
  probed `qwen2.5:7b` through LiteLLM via two paths: tool-
  calling (`tools=[{...}]` + `tool_choice="extract_graph"`)
  returned malformed function arguments (`{"text": "<original
  prompt>"}` rather than the schema-shaped structured output);
  JSON mode (`response_format={"type": "json_object"}`)
  returned clean schema-conformant output. D64's Choice text
  records the deviation; the LiteLLM-vendor-quirks-class pre-
  write reconciliation pattern's third load-bearing instance
  at P6 (after S6 and S20).

- **Two-method ChunkEmbedderPort shape at S22** (structural-
  honesty class). The brief proposed a single-method port with
  the task parameter (`embed(chunks, tenant_context, task)`);
  build surfaced that the retrieval adapter's query-side
  embedding has no Chunk to wrap (Chunk carries tenant_id,
  source_id, jurisdiction, chunk_index provenance fields the
  query lacks). Wrapping a query in a synthetic Chunk with
  fabricated provenance was rejected as dishonest. Resolved by
  splitting the port into `embed` (Sequence[Chunk] →
  Sequence[Embedding]) and `embed_query` (str →
  Sequence[float]); both methods carry the task parameter;
  D56's interface-segregation posture preserved. D65's Choice
  text records the refinement.

- **Cross-store readiness query in `neo4j_traverse` at S22**
  (structural-honesty class). The brief proposed the cross-
  track readiness filter as "a Cypher predicate against the
  chunk-source linkage in `neo4j_traverse`"; build surfaced
  that Neo4j has no chunk-source linkage natively (chunks live
  in per-tenant Postgres, not Neo4j). Resolved by a two-store
  query: `Neo4jTraverse._read_indexed_chunk_ids` queries per-
  tenant Postgres for the set of indexed chunk_ids; the set
  passes as a Cypher parameter for the
  `ANY(cid IN reachable.source_chunk_ids WHERE cid IN
  $indexed_chunk_ids)` predicate. The cross-store call is the
  structurally honest shape under D32+D63; D65's Choice text
  records the refinement.

- **Path-discrepancy and methodology-section-structure misses
  caught at the mid-package strategic commits.** The Ask David
  absorption initially surfaced as three deferred-decision
  candidates; operator pullback re-categorised into one
  design-session candidate (data retrieval), one design-session
  candidate (hierarchical topology), and two genuine deferred-

## Durable lessons

- **The framing-prompt-as-recommendation pattern earns lift to
  a top-level prescriptive principle at fourteen-plus
  instances.** The pattern is first observed at S6 and accumulates
  through P5 (D54 return-type deviation, D58 regression-report
  field shapes, D59 polling-with-timeout, S17b `>= 0`
  assertion adjustment, S18 `baseline_run_id` →
  `baseline_revision_id` refinement, the per-stage claim
  methods at S20 forecast, others) and P6 (D61 markdown-it-py
  version drift, D62 task-prefix and per-stage-method
  refinements, D63 mechanical-enforcement enrichment from the
  user's risk-3 guidance, D64 JSON-mode-over-function-calling,
  D64 `get_*_for_source` → `get_*_by_chunk_ids` port-shape
  refinement, D65 two-method ChunkEmbedderPort shape, D65
  cross-store readiness query, D65 CLI-commands-at-S22). The
  pattern's three-class taxonomy (mechanical / structural-
  honesty / architectural-cost) emerges from the S19 and S20
  reflections and holds across the larger sample. Promoted to
  a top-level prescriptive principle at this P6-close commit
  because the discipline now describes how briefs are
  structured (option space + recommendation), how build
  absorbs refinement (D-entry Choice text records the
  structurally honest shape), and how the briefs/ convention's
  no-in-place-edits rule remains auditable rather than
  ceremonial. The methodology document gains the principle as
  a top-level `##` section parallel to "Start simple; refactor
  at the structural-promotion threshold."

- **Pre-write reconciliation against vendor docs precedes brief
  drafting earns lift to a top-level prescriptive principle at
  four load-bearing instances.** The pattern's load-bearing
  instances span four LiteLLM-related sessions (S6 env-var
  quirks; S20 nomic-embed-text task-prefix requirement; S21
  Ollama tool-calling fidelity gap resolved by JSON mode; the
  S20 cost-attribution worst-case that did not materialise but
  produced the defensive `embedding_no_token_count` fallback
  path). The cost asymmetry is what makes the discipline
  inversely cheap: a brief drafted from memory that ships a
  vendor-specific topology bug costs the build session minutes
  to a full session of debugging plus a corrective commit; the
  pre-write check that catches it is fifteen minutes of doc-
  reading. The discipline lifts to a top-level prescriptive
  principle at this P6-close commit because every brief from
  here forward carries a "Pre-write reconciliation" section,
  and any session touching a vendor SDK or gateway abstraction
  in a new operation mode treats the reconciliation as non-
  negotiable. LiteLLM/Ollama integration in particular has a
  higher-than-baseline quirk surface that warrants explicit
  reconciliation against each new operation mode.

- **The user-driven course-correction pattern is observed,
  not prescribed.** Two named instances at P6 mid-package
  strategic blocks: the data-retrieval design-session
  elevation pullback at the Ask David absorption, and the
  product reframe absorption pullback. Both shared structure:
  model framing pushed past architectural altitude into
  commitment territory; operator-initiated reframe; charter
  absorption commit landed before drift accumulated. The
  pattern names the recovery surface, not a workflow gate;
  promoting it to a discipline would create a recursive
  expectation (the operator must vigilantly drift-recover
  from drift-recovery), which is not what produces the
  recovery. Lifts to a Patterns-observed entry at this P6-close
  commit so the recovery surface is documented when it fires
  and is reusable as a charter-absorption shape (small
  strategic commit, named pullbacks, charter absorbs the
  discipline). The discipline addition on the model side is
  to surface the question of audience and proposition before
  committing to the next architectural step at multi-turn
  architectural sequences.

- **The two-track coordination shape (vector + graph) holds
  cleanly through to retrieval.** At P6 close, the source row
  is the pipeline state-of-record per D60; the per-stage
  status field drives reentrancy; SKIP LOCKED keeps two
  workers from claiming the same source; idempotent worker
  writes on both stores (UPSERT on chunks.id for embeddings;
  Cypher MERGE on the composite uniqueness key for entities
  and relationships); cross-track readiness lands as a `state
  = 'indexed'` predicate at retrieval time per D65. The
  topology-asymmetry between D32's per-tenant Postgres and
  D63's shared-Neo4j shape produces a cross-store readiness
  query at S22 (`Neo4jTraverse._read_indexed_chunk_ids`
  pre-queries per-tenant Postgres for the indexed-chunk-id
  set) — the structurally honest shape under the topology
  choice, with the cost paid as one Postgres roundtrip per
  traverse. Forward-affordance for the data-retrieval design
  session: the cross-store query becomes a hot path under
  retrieval-heavy workloads above Phase 1 corpus sizes; the
  optional projection-based shape (denormalised ready flag on
  chunks; derived ready property on `:Entity`) lands at the
  design session if measurement evidence justifies the
  write-amplification trade-off.

- **Mechanical enforcement of vendor-confinement contracts
  scales with vendor-surface count.** P6 added two vendor
  surfaces (Ollama-served embedding model integration through
  LiteLLM at S20; Neo4j 5 Community at S21) and three import-
  linter contracts (`litellm-confined-apps`, `neo4j-confined`,
  `neo4j-confined-apps`) plus one AST enforcement test
  (`test_no_raw_neo4j_session`). The pattern is "every new
  vendor SDK that enters the codebase ships its own
  confinement contract on the same commit"; the structural-
  promotion threshold (third instance) bites because the
  litellm-confined → neo4j-confined parallel is structurally
  identical, suggesting that the next vendor SDK to enter the
  codebase (likely a different LLM provider or a different
  graph database) will inherit the same contract template
  without architectural reasoning at framing — the template
  itself is the discipline. Worth surfacing at the Phase 1
  close audit as a candidate for explicit contract-template
  documentation if the pattern recurs at another vendor entry.

## Delta against the v1 epic note (per D43)

The v1 epic note at `charter/packages/p6-epic.md` was written
at P6 open with a three-to-four-session forecast and "three to
five D-entries beyond D60" (D60 itself being the P6 framing
entry). Reality at P6 close diverges in five named ways:

1. **Four sessions, within the forecast range, upper end as
   predicted.** The v1 epic note forecast S19 (skeleton,
   parser, worker, queue), S20 (embedding + pgvector
   indexing — first track), S21 (graph extraction + Neo4j —
   second track), S22 if needed (retrieval interface + cross-
   track readiness + P6 close). All four sessions shipped, in
   the predicted order, with the upper-end forecast holding
   because P6's vendor surface (Ollama embedding integration
   at S20; Neo4j at S21; the retrieval surface at S22) was
   wider than P5's. The four-session shape is consistent with
   the epic note's "Three to four sessions" forecast.

2. **Six P6-era D-entries shipped versus the framing forecast
   of "three to five beyond D60."** D61 at S19; D62 at S20;
   D63 + D64 at S21; D65 at S22. Plus D60 at framing equals
   six P6-era D-entries. Above the upper bound of the forecast
   range (which named "three to five" beyond D60) by one
   entry; the additional density is at S21 where both the
   topology (D63) and the extraction shape (D64) earned
   independent D-entries rather than a combined entry. The
   architectural reason: D63 is a deviation from D32 (procurement-
   defensible reasoning required) while D64 is a per-session
   shape commitment with build-time refinement (JSON mode over
   tool-calling) — folding them together would have produced
   an unwieldy single entry that obscured the deviation
   reasoning. The forecast's "three to five" was honest at
   framing time; the at-build split is the structurally honest
   shape.

3. **Worker shape divergence: forecast dedicated Compose
   services per tenant; actual `make ingest-worker` against

   epic note forecast dedicated worker services per tenant as
   the production-shape commitment; build chose `make ingest-

   Production-shape worker topology defers to production-
