### Commit 1: `feat(p5/s18): regression report domain, comparison, and render functions`

Three logical pieces in one commit (the rendering is small enough that combining is cleaner than splitting):

- Domain value objects in `contexts/evaluation/domain/`:
  - `RegressionReport`: frozen dataclass with `baseline_run_id`, `candidate_run_id`, `per_criterion_deltas: list[CriterionDelta]`, `aggregate_metrics: AggregateMetrics`, `generated_at`.

- Comparison logic in `contexts/evaluation/application/regression_compare.py`:

- Render functions in `contexts/evaluation/application/render_report.py`:
  - `render_text(report: RegressionReport) -> str`: human-readable markdown table with per-criterion rows and aggregate footer.
  - `render_json(report: RegressionReport) -> str`: structured JSON for programmatic consumers.
- Unit tests covering: identical-runs (zero deltas), all-improvements, all-regressions, mixed, single-criterion, multi-criterion.

The introduction of `RegressionReport` and the comparison shape is the architectural decision captured by D58 (commit 5). The render functions are mechanical given the domain shape.

### Commit 2: `feat(p5/s18): Langfuse polling-with-timeout in cost-query path`

Replaces S17b's 8s force-flush-and-sleep with a polling-with-timeout shape:

- New helper in `contexts/observability/adapters/outbound/langfuse/adapter.py` (or alongside): `async def wait_for_trace_availability(trace_id: str, timeout_seconds: float = 30.0, poll_interval_seconds: float = 1.0) -> bool`
- Polls Langfuse via `get_trace(trace_id, ...)` until the trace returns non-None or the timeout elapses. Returns True on availability, False on timeout.
- The cost-query path (CostQueryPort adapter or upstream caller) calls this helper before invoking `get_costs_by_trace_ids` for traces that may not yet be ingested.
- Adapter unit tests with mocked HTTP: trace-immediately-available, trace-available-after-N-polls, trace-never-available-timeout.

The architectural decision is captured by D59 (commit 6). The polling-with-timeout choice over alternatives (sync wait, two-phase rendering) is grounded in: sync wait is brittle under variable Langfuse load; two-phase rendering complicates the CLI surface for a one-shot eval run; polling handles both fast-arrival and slow-arrival cases honestly with a documented timeout.

### Commit 5: `docs(p5/s18): record regression report shape as D58`

Append D58 to `charter/decisions.md`:

```
- **D58: Regression report shape — single-baseline comparison, per-criterion + aggregate views, text and JSON output** (Package P5, Session S18, 2026-MM-DD)
  - Choice: The regression report compares two runs (baseline vs candidate) of a scoring sheet against a single interaction set. The report carries per-criterion deltas (success-rate delta, cost-per-task delta) and aggregate metrics (overall success-rate delta, overall cost-per-task delta). Output renders in two formats: human-readable text (markdown table) and structured JSON (for programmatic consumers like P11's recommendation engine). Single-baseline at S18; multi-baseline regression tracking (run history with trend lines) defers to P11 territory or beyond.
  - Reasoning: The eval harness's user-facing question is "is the candidate better than the baseline?" — single-baseline comparison is the minimal answer, and the per-criterion + aggregate split serves both detail-oriented (which criterion regressed) and headline-oriented (overall delta) consumers. Text output serves the operator running CLI evaluation; JSON output serves programmatic consumers (P11 recommendation engine reads regression reports as evidence). Multi-baseline tracking (e.g., "this candidate vs the last 10 baselines") is a P11+ optimization-recommendation concern that requires run-history infrastructure beyond P5's scope; landing it now is paper architecture against an absent consumer. The single-baseline shape is forward-compatible: a multi-baseline report is a list of single-baseline reports plus aggregation, so the data model extends without restructuring.
  - Alternatives considered: Multi-baseline with trend tracking (rejected: paper architecture; P11 territory; absent consumer). Per-trace report (rejected: too granular for the harness's user-facing question; trace-level inspection lives in the optimization dashboard at P11). JSON-only output (rejected: text rendering for the CLI operator is load-bearing for case-study posture; the harness should be operable without programmatic tooling). Text-only output (rejected: programmatic consumers at P11 need the structured shape; rendering JSON from text is parse-error-prone).
  - Kano: must-have for P5 close; the regression report is the harness's user-facing surface and the substrate P11 reads.
```

### Commit 6: `docs(p5/s18): record Langfuse asynchrony handling as D59`

Append D59 to `charter/decisions.md`:

```
- **D59: Langfuse trace-ingestion asynchrony — polling-with-timeout at the cost-query path** (Package P5, Session S18, 2026-MM-DD)
  - Choice: Cost queries that may target recently-emitted traces wait for availability via polling. The `wait_for_trace_availability(trace_id, timeout_seconds=30.0, poll_interval_seconds=1.0)` helper polls Langfuse via the existing `get_trace` adapter method until the trace returns non-None or the timeout elapses. The cost-query path invokes the helper before `get_costs_by_trace_ids` for traces emitted within the same flow as the query. Default timeout is 30 seconds, default poll interval 1 second; both are tunable via use-case parameters.
  - Reasoning: Langfuse trace ingestion is asynchronous from OTel emission; the harness's CLI flow (replay → cost-aggregate → render) generates traces and queries them within seconds, exposing the async window. S17b's e2e test used an 8s force-flush-and-sleep, which is brittle (insufficient under variable load; wasteful when ingestion is fast). Polling-with-timeout is honest: it waits exactly as long as needed for fast ingestion and surfaces a clear timeout error for genuinely stalled traces. The 30s timeout is conservative for CLI flows; programmatic consumers can tune down for batch operations or up for high-load scenarios. Two-phase rendering (immediate report with cost-pending) was rejected for CLI flows because the CLI is a one-shot operation; the operator wants a complete report or a clear error, not a partial result they have to re-query.
  - Alternatives considered: Sync wait (rejected: brittle under variable Langfuse load; 8s might not be enough at peak ingestion lag, wasteful at quiet times). Two-phase rendering with cost-pending sections (rejected: complicates the CLI surface; one-shot CLI operations want complete results; the two-phase shape makes sense for streaming UI surfaces at P11 but not at S18). Webhook/push from Langfuse (rejected: requires Langfuse-side configuration not in the case study's control; breaks D27's vendor-portability posture).
  - Kano: must-have. Without a documented asynchrony handling, every cost-query consumer reinvents the pattern, and the case study posture cannot honestly claim "cost-aware optimization recommendations" at P11 if cost-query results are race-condition-prone.
```
