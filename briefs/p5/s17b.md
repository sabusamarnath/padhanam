  - Trace_id present but Langfuse returns no cost data: same handling.
  - Aggregation across heterogeneous criteria: cost-per-task averaged across all successful criterion-applications, not per-criterion. Per-criterion breakdowns are P11 territory.
- Unit test with fakes for repositories and CostQueryPort. Cover: all-successful path, mixed success path, excluded-trace-id path, empty-set path.

### Commit 7: `docs(p5/s17b): record TraceQueryPort method-shape as D56`

Append D56 to `charter/decisions.md`:

```
- **D56: TraceQueryPort method shape — interface segregation, separate methods per access pattern** (Package P5, Session S17b, 2026-MM-DD)
  - Choice: TraceQueryPort has two methods, not one widened method. `get_trace(trace_id, tenant_context) -> TraceRecord | None` retains its S7-era shape (now widened to TenantContext per sub-D50 application) for rich full-trace fetch by the recommendation engine's later use. `get_costs_by_trace_ids(trace_ids, tenant_context) -> dict[str, CostBreakdown]` is the new batch cost-only method serving cost-per-successful-task and aggregate cost queries. Each method serves a coherent access pattern; neither over-generalized.
  - Reasoning: Widening get_trace to a batch form forces cost-shaped consumers to filter span data they don't need, which compounds at the recommendation engine layer where the same TraceQueryPort is consumed for different access patterns. Collapsing to a generic get_traces(ids, fields) loses type safety and pushes field-selection complexity into every consumer. Interface segregation on ports is the principle: each method serves an access pattern with type-safe inputs and outputs. As observability access patterns multiply (recommendation engine adding aggregation queries at P11; active testing surface at P12), the pattern is to add methods, not widen methods. D17's facade pattern at the api.py level handles the public-surface stability concern; the port itself can grow methods without breaking consumers because each consumer depends on the methods it calls, not the entire port surface.
  - Alternatives considered: Widen get_trace to batch form (rejected: forces cost consumers to filter span data they do not need; access-pattern shape leaks across consumers; the recommendation engine and the cost-rollup have legitimately different needs). Generic get_traces(ids, fields) with field selection (rejected: loses type safety; pushes field-selection logic into every consumer; over-engineered for current scale and the consumer count). Single method serving both with optional field filter (rejected: same losses as the generic shape; complicates the implementation without simplifying the consumer side).
  - Kano: performance.
```

### Commit 8: `docs(p5/s17b): record cost-query two-layer abstraction as D57`

Append D57 to `charter/decisions.md`:

```
- **D57: Cost-query path — two-layer abstraction (evaluation → observability use case → trace store port)** (Package P5, Session S17b, 2026-MM-DD)
  - Choice: contexts/evaluation/ does not query Langfuse directly. The cost-query path is two layers: (1) contexts/observability/ owns the trace-store abstraction via TraceQueryPort and the LangfuseTraceQueryAdapter; (2) contexts/observability/application/query_cost_by_trace_ids exposes a use case that other contexts call via contexts.observability.api facade. contexts/evaluation/ defines its own CostQueryPort and an adapter that calls contexts.observability.api.query_cost_by_trace_ids. Two layers; each layer owns its concern.
  - Reasoning: D27 forbids vendor-specific code outside dedicated adapters. A direct Langfuse query in contexts/evaluation/application/ would put Langfuse-specific knowledge in a domain context that has no business knowing about Langfuse; the case study's posture treats this as paper architecture that compounds with every additional cost consumer. The two-layer abstraction puts vendor knowledge in observability adapters (where D27 wants it) and exposes a vendor-agnostic interface to consumers (evaluation today, P11 recommendation engine tomorrow). The pattern is the structural precedent for every future cross-context cost or trace consumer: the consumer defines its own port and adapter, and the adapter calls the source context's api facade. D17's facade pattern provides the import target; D57 commits to the access pattern that makes the facade load-bearing rather than ornamental.
  - Alternatives considered: Direct Langfuse query in evaluation (rejected: D27 violation; vendor knowledge leaks into evaluation domain; compounds across consumers). Single layer — evaluation imports observability's TraceQueryPort directly without an evaluation-side port (rejected: bypasses the application-layer use case; couples evaluation to observability's port surface, which is observability's internal concern, not its public contract). Trace data flowing through OTel pipeline into evaluation's own storage (rejected: paper architecture at Phase 1 scale; adds infrastructure complexity for a query that is a single HTTP fetch).
  - Kano: must-have.
```
