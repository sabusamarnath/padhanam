```
## D75: Agent aggregate shape, methodology lineage, hash-chain helper promotion, repository interface, auth posture, and CLI shape

**Decision.** The agent bounded context ships at S24 with the following architectural commitments.

**Aggregate shape.** Two frozen-dataclass aggregates following D31's revision-shape precedent and inheriting D74's structural pattern. `AgentTemplate` carries the human-stable identity plus methodology lineage: id, name, description, source_methodology_template_id (UUID, nullable for blank-created agents, immutable after construction), source_methodology_template_version (integer, nullable for blank-created agents, immutable after construction), created_by_user_id, created_at, archived_at. Description lives on AgentTemplate only and is immutable after creation; treating description as part of revision content would conflate metadata-stable identity with revision-evolving content. `AgentRevision` carries the per-revision content (agent_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at) plus the hash-chain fields (previous_revision_hash, this_revision_hash). Revisions are immutable per D31; updates create new revision rows. Archive marks the parent template's archived_at.

The paired-NULL invariant on AgentTemplate's lineage fields (both NULL or both populated; never one without the other) is enforced at the domain layer via `__post_init__` validation on the frozen dataclass: instantiation with exactly one of the two fields populated raises `ValueError`. The same invariant is enforced at the schema layer via the CHECK constraint named in the schema update; the two-layer enforcement matches the audit-context precedent of domain-layer validation backed by schema-layer constraint.

**Methodology lineage placement.** The lineage fields (source_methodology_template_id, source_methodology_template_version) live on AgentTemplate, not on AgentRevision. Reasoning: lineage is template-level identity (origin), not revision-level content (what changes between versions). Placement on the template structurally enforces D68's "set immutably on revision 1, preserved across all later revisions" because the template never changes after creation; the lineage cannot drift across revisions because it does not exist on the revision. The fields are nullable to accommodate blank-created agents per D68.

**Persistence shape.** Same JSONB-for-structured-fields and scalar-for-primitives pattern as D74. `source_ids` jsonb, `tool_allowlist` jsonb, `retrieval_strategy` jsonb, `filter_tree` jsonb on AgentRevision; `top_k` integer, `min_score` numeric, `model_selection` text, `system_prompt` text on AgentRevision. The AgentRevision row contains: agent_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at, previous_revision_hash, this_revision_hash. Name is read from the parent AgentTemplate at hash-compute time and not persisted on the revision row, mirroring S23's actual implementation pattern. AgentTemplate carries `id` uuid, `name` text, `description` text nullable, `source_methodology_template_id` uuid nullable, `source_methodology_template_version` integer nullable, `created_by_user_id` text, `created_at` timestamptz, `archived_at` timestamptz nullable.

**Hash-chain content surface.** Same shape as D74's audit-mirror per D26. SHA-256 over canonical JSON of a payload comprising the revision content fields plus `previous_revision_hash` as a key inside the payload. Format-f Decimal canonical encoder inherited unchanged. The hash spans: name (read from parent template at compute time), description (read from parent template at compute time), system_prompt, source_ids (sorted), tool_allowlist (sorted), retrieval_strategy, filter_tree, top_k, min_score, model_selection, plus previous_revision_hash. Excluded: agent_template_id, version, created_by_user_id, created_at, this_revision_hash. Methodology lineage fields are template-level and explicitly outside the revision hash because they are not part of revision content.

Name is read from the parent AgentTemplate at hash-compute time and included in the canonical-JSON payload as the `name` key, mirroring the methodology context's conceptual-denormalisation pattern from S23's actual implementation. Name is not persisted as a column on agent_revisions; the architectural argument for chain-self-containment is satisfied by the payload-key inclusion at compute time without the redundancy of a persisted denormalised column. If a future session demands stricter chain self-containment (e.g., S25's cross-context flow surfacing a real consumer need), the migration to a persisted column lands then with a real architectural reason.

Description is read from the parent AgentTemplate at hash-compute time and included in the canonical-JSON payload as the `description` key (with `""` as the deterministic value when description is NULL), mirroring the methodology context's actual implementation from S23. Description is template-level and immutable post-creation, so its inclusion in the revision hash is deterministic and stable across the chain; the earlier argument that inclusion would force new revisions on description updates does not apply because description does not update post-creation.

**Hash-chain helper promotion.** The hash-chain primitives currently at `contexts/methodology/domain/hash_chain.py` promote to `padhanam/security/hash_chain.py` at this session's commit 8 alongside the agent use cases. The promoted helper exports field-set-agnostic primitives only: `compute_revision_hash(content_payload: dict, previous_hash: str) -> str`, `canonical_json(payload: dict) -> bytes`, `_CanonicalJSONEncoder(json.JSONEncoder)`, `GENESIS_REVISION_HASH = "0" * 64`. Methodology-specific bits in the current helper (the `CONTENT_FIELDS` frozenset, the `_normalise_list_fields` function, the unused `filter_content_fields` defensive whitelist) do not promote; list-sort responsibility for list-shaped fields moves to the use case layer in both contexts. Each use case knows which of its fields are list-shaped and sorts them before constructing the content payload it passes to `compute_revision_hash`. The promotion treats hash-chain as a platform-level security primitive consistent with where AuthorizationError, check, OPERATOR_ROLE, and crypto.py live; the API shape is field-set-agnostic so future revision-shaped contexts inherit the primitive without re-cleaning the helper's field-name coupling. Cross-context import from contexts.methodology.domain into contexts.agent violates D17's independence contracts; the promotion is the structurally honest resolution. This is the second instance of the second-consumer-promotes pattern after S23's OPERATOR_ROLE promotion; the pattern is a Patterns-observed candidate at the next phase audit if a third instance fires (potentially at S25's cross-context flow or at a future revision-shaped context).

**Repository interface.** `AgentRepositoryPort` Protocol with `TenantContext` parameter on every method. Agent data is per-tenant per D32; routing flows through TenantContext per D50, mirroring the existing per-tenant adapters at `contexts/audit/`, `contexts/evaluation/`, `contexts/ingestion/`. Methods: `create_template(template, initial_revision, tenant_context) -> AgentTemplate`, `get_template(template_id, tenant_context, version=None) -> tuple[AgentTemplate, AgentRevision]`, `list_templates(tenant_context, include_archived=False) -> list[AgentTemplate]`, `add_revision(template_id, revision, tenant_context) -> AgentRevision`, `archive_template(template_id, tenant_context) -> AgentTemplate`. Cross-tenant access fails at the tenant-isolation contract test layer and at the data-layer predicate.

**Auth posture.** Agent CRUD use cases accept either tenant-context or operator-context as valid authentication; both produce authorised access. Reasoning: agents are tenant-user-owned per the P7 epic note's audience definition; tenant users CRUD their own agents through the tenant-context route. The CLI in operator-context per the dev-shape pattern from `apps/cli/_runtime.py` also CRUDs agents on behalf of a tenant; this is operator-as-platform-administrator, not operator-as-tenant-impersonator. AuthorizationError raised on unauthenticated callers (no role at all). The cross-context create-from-methodology flow at S25 inherits the same auth posture.

**CLI shape.** Five commands at `padhanam agent` namespace.
- `padhanam agent create --tenant <label> --config <path>` reads YAML or JSON config containing the full template-plus-revision-1 payload (name, description, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection); produces a new template with revision 1 (and source_methodology_template_id / source_methodology_template_version both NULL because this is blank-created); prints the new template_id and revision_id.
- `padhanam agent get --tenant <label> <template-id> [--version N] [--json]` retrieves the template plus the named or latest revision.
- `padhanam agent list --tenant <label> [--include-archived] [--json]` lists templates (default excludes archived).
- `padhanam agent update --tenant <label> <template-id> --config <path>` reads the same config shape minus the name; produces a new revision; prints the new revision_id and version number.
- `padhanam agent archive --tenant <label> <template-id>` marks the template's archived_at; revisions remain intact for audit.

The `create-from-methodology` subcommand is excluded from S24; lands at S25 alongside the cross-context flow it consumes.

**Alternatives considered.** Eight rejected alternatives weighed.

(a) Methodology lineage fields on AgentRevision rather than AgentTemplate; rejected because revision-level placement creates the enforcement burden that template-level placement avoids structurally; the fields would be repeated identically across every revision and a malicious or buggy update path could drift them.

(b) Hash-chain helper duplication in contexts/agent/domain/ rather than promotion; rejected on the same drift-cost argument that justified S23's OPERATOR_ROLE promotion. Two definitions of canonical-JSON encoding is exactly the failure mode the S23 review caught at pre-build; the structural-honesty resolution is the same shape applied to the same recurrence.

(c) Cross-context import of hash_chain from contexts.methodology.domain into contexts.agent; rejected because it violates D17's independence contracts and would require new import-linter exemptions.

(d) Repository without TenantContext parameter, with tenant routing at the use case layer; rejected because it inverts the per-tenant pattern the rest of the codebase follows (audit, evaluation, ingestion all carry TenantContext through the port chain) and would require a parallel routing mechanism for one context only.

(e) Operator-context required for all agent CRUD (mirroring D34 / D74 methodology pattern); rejected because agents are tenant-user-owned per the P7 epic note's audience definition; requiring operator-context would force every tenant user interaction through an operator role, which is wrong at the architectural level.

(f) Tenant-context required only (no operator-context override); rejected because the CLI runs in operator-context per the dev-shape pattern, and agent CRUD via the CLI is a real workflow at Phase 1; rejecting operator-context would force the CLI into a tenant-impersonation pattern that does not match its actual role.

(g) Single combined AgentTemplate + AgentRevision aggregate without revision split; rejected for the same reason D74 rejected the equivalent for methodology — D31's revision-shape precedent provides immutable-content-with-evolving-versions discipline that audit posture requires.

(h) As-is promotion of the existing methodology helper including `_normalise_list_fields` and `CONTENT_FIELDS`, with field-name coupling documented in the new module's docstring; rejected because the second-consumer moment is the cheapest moment to settle the helper's API shape. List-sort responsibility on the helper bakes in field-name assumptions that the next revision-shaped context would have to refactor or work around; moving the responsibility to the use case layer now makes the helper field-set-agnostic and avoids a third-time-around cleanup. The cost is small (each context's use case adds a `_sort_list_fields` call before constructing the content payload); the structural-honesty benefit is a clean primitive at `padhanam/security/`.

**Kano.** Performance. Aggregate shape and persistence choices preserve the architectural discipline (revision shape per D31, hash-chain per D26, per-tenant scope per D32, lineage as template-level immutable per D68) that S25's cross-context flow consumes and P8's agent runtime executes against. Hash-chain helper promotion is structural-honesty rather than feature work; the alternative (cross-context import or duplication) would degrade the architecture. CLI shape is delighter on operator ergonomics; the structural-honesty contribution sits at the architectural commitments above.
```

```
## Agent tables (per-tenant)

| Column                              | Type            | Constraints                                    |
|-------------------------------------|-----------------|------------------------------------------------|
| `id`                                | `uuid`          | primary key; default `gen_random_uuid()`       |
| `name`                              | `text`          | not null; UNIQUE among non-archived templates per partial index `ix_agent_templates_name_unique_active` |
| `description`                       | `text`          | nullable; immutable after creation per D75     |
| `source_methodology_template_id`    | `uuid`          | nullable for blank-created agents; immutable after construction per D75 |
| `source_methodology_template_version` | `integer`     | nullable for blank-created agents; immutable after construction per D75 |
| `created_by_user_id`                | `text`          | not null                                       |
| `created_at`                        | `timestamptz`   | not null; default `now()`                      |
| `archived_at`                       | `timestamptz`   | nullable                                       |

Methodology lineage fields are nullable together: either both NULL (blank-created agent) or both populated (created from methodology template at S25's cross-context flow).
```
