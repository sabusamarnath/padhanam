### D79 entry text (append to `charter/decisions.md` after D78, using the heading-style adopted from D69 onward)

```
## D79: Cross-context create_agent_from_methodology flow shape — agent-owned cloning via callable api-facade ports, MethodologyView and SourceLookup as consumer-side abstractions (P7 S25, 2026-05-10)

**Decision.** The `create_agent_from_methodology` use case lives in `contexts/agent/application/use_cases.py`. It consumes two callable Protocol ports defined at `contexts/agent/application/ports/`: `MethodologyLookup`, returning a `MethodologyView` frozen dataclass DTO defined in agent's application layer; and `SourceLookup`, with a single `assert_sources_exist(source_ids, tenant_context, principal)` method that raises `SourceNotFoundError` on missing IDs. Two adapters wired at `apps/cli/_runtime.py` translate the methodology and ingestion contexts' application-layer use cases into the consumer-shaped ports; methodology adapter wraps `get_methodology_template` and translates the (`MethodologyTemplate`, `MethodologyRevision`) tuple into `MethodologyView`; ingestion adapter wraps the source-read surface and synthesises the assert behaviour. Agent context contains zero imports from `contexts.methodology` or `contexts.ingestion` at the domain or application layer; verified by extending the existing cross-context independence import-linter contracts to cover the new cross-context relationships. Lineage records on the new `AgentTemplate` populate `source_methodology_template_id` and `source_methodology_template_version` (the resolved version, not the request's version=None) per D75's paired-NULL invariant. The cloned `AgentRevision` version 1 inherits content fields from the `MethodologyView`: system_prompt, retrieval_strategy, filter_tree, top_k, min_score, model_selection, tool_allowlist all copy verbatim; description copies from the methodology template envelope; source_ids come from the request payload after existence validation, not from the methodology (methodology templates do not carry tenant-scoped source_ids). The cloned agent is independent per D68: subsequent edits to the methodology template do not propagate to the agent, and subsequent edits to the agent do not propagate back to the methodology. Auth posture: agent write requires tenant-context-or-operator-context per D75; methodology read uses any-authenticated-context per D34's get/list pattern; source existence check uses tenant-context (or operator-context routed through the tenant) per D32. CLI surface: `padhanam agent create-from-methodology --tenant <label> --config <path>` with config shape accepting `methodology_template_id`, optional `methodology_version` (defaults to latest), `name`, `source_ids`; the use case resolves version=None to the latest version at clone time and records the resolved integer in lineage.

**Reasoning.** The api-facade-via-callable pattern is the established cross-context convention per D17; the S17b precedent (evaluation→inference) demonstrated callable-injection-at-construction as the structurally-honest cross-context shape. Wrapping each producer's use cases in a callable port avoids type imports at the consumer's domain or application layer while letting the wiring layer translate producer aggregates to consumer-shaped DTOs. Agent-context ownership of the cloning logic respects D68's independent-clones commitment: methodology is the read-only producer, agent is the write-side consumer that records lineage and persists the clone. Source existence validation at the use case boundary fails fast on bad source_ids rather than after AgentTemplate construction, which would leave orphan-reference revisions if persistence ran first; the validation also surfaces tenant-routing errors (source belongs to a different tenant) at the boundary rather than at retrieval time. The MethodologyView DTO defined in the consumer's application layer rather than as a re-export of MethodologyTemplate is the structurally-honest cross-context type pattern: shared types create coupling that the hexagonal seam exists to prevent. Tenant-context-or-operator-context auth for agent write inherits D75; methodology read inherits D34's get/list pattern; source check uses tenant-context per D32 because source data is tenant-scoped per D32 (source rows live on per-tenant Postgres).

**Alternatives considered.** Seven rejected alternatives weighed.

(a) Methodology context owns cloning via a `clone_to_agent` use case at `contexts/methodology/application/use_cases.py`. Rejected because methodology has no business knowing about agents per D17; the consumer-knows-mapping pattern fits agent-side ownership; methodology is platform-managed and audience-shifting it to know about tenant agents inverts the audience boundary D16's bounded contexts split establishes.

(b) Apps-layer orchestration service at `apps/cli/_clone_orchestrator.py` owning the cross-context flow and calling both contexts' use cases. Rejected because business logic belongs in the consumer's use case layer per the hexagonal pattern; an apps-layer orchestrator would replicate the architectural mistake the hexagonal seam exists to prevent (business logic in the wiring layer is unowned by any context's discipline).

(c) Direct cross-context import from `contexts.methodology.domain` into `contexts.agent.application`. Rejected because it violates D17's independence contracts; the import-linter contracts would break; the same shape as the S24 hash-chain helper promotion rationale (cross-context type imports always promote to a higher-altitude shared module or get abstracted via consumer-side ports).

(d) MethodologyView as a re-export of `MethodologyTemplate` plus `MethodologyRevision`. Rejected because cross-context type sharing creates the coupling D17 forbids and the consumer would inherit the producer's invariants (paired-NULL lineage on methodology, hash-chain semantics) that the agent context has no business asserting. A consumer-shaped DTO at the consumer's application layer is the structurally-honest shape and matches how evaluation handles inference results per S17b.

(e) Source attachment as a follow-on update step rather than at create-time. Rejected because the e2e demonstration value is weaker (two-step create-then-attach reads as architectural drag in the demo flow), the at-create-time validation surfaces source-not-found errors earlier in the user flow, and the at-create-time path matches how the existing blank-create with `--source-ids` works (inherits the same UX shape rather than diverging).

(f) CLI command without `--config` (all parameters as flags). Rejected because the existing agent CRUD pattern (S24's `create`, `update`) uses `--config` for the structured payload; create-from-methodology inherits the same shape for CLI surface uniformity; methodology_template_id and source_ids are awkward as flags (UUID arguments), comfortable as YAML.

(g) LVT system prompt drafted at build-time without preservation in the brief. Rejected because methodology IP benefits from operator review before paste, the system prompt is the methodology's primary content surface (not a default), and brief-preservation matches the framing-prompt-as-recommendation pattern's distinction between defaults (drafted at build-time) and substantive content (drafted at brief-time and reviewed before commit).

**Kano.** Performance for the cross-context architectural commitments (api-facade-via-callable shape, MethodologyView placement, lineage recording mechanics, source existence validation timing); delighter for CLI ergonomics (config-file-based create-from-methodology consistent with blank-create); must-have for the LVT template content surface because the bet's "one agent configured from a methodology template" demonstration depends on a real LVT system prompt rather than a placeholder.
```

```
You are an LVT (Lean Value Tree) methodology assistant. LVT structures product strategy as a four-level hierarchy: bet, initiative, epic, story. Each level cascades strategic intent downward and aggregates evidence upward.

Your role is to help users place work in the right level of the tree, identify when a level is misaligned with the level above, and surface drift between strategic intent and execution.

When a user describes work, locate it in the tree first.

A bet is a load-bearing strategic claim with named test conditions and falsifiable success criteria. Bets answer "what proposition are we testing in the market?"

An initiative is a coherent body of work aligned with one bet's success criteria. Initiatives answer "what concrete arc do we ship to test the bet?"

An epic is a shippable scope within an initiative that produces measurable outcomes. Epics answer "what ships, and how do we know it worked?"

A story is the smallest unit of value within an epic. Stories answer "what does the team do this week?"

When asked to assess work, locate it first, then check alignment upward (does this epic actually serve its initiative? does this initiative actually test its bet?) and decomposition downward (does this initiative break into shippable epics? do the stories aggregate to the epic's outcomes?).

Push back on weak placements. A bet without falsifiable success criteria is a vision statement. An initiative without measurable outcomes is a roadmap header. An epic without shippable scope is a wish. A story without acceptance criteria is a task.

Use the source materials attached to this agent for the user's specific bet, initiatives, epics, and stories. Cite specific source content when grounding assessments. When source materials contradict each other, surface the contradiction rather than papering over it.

Your output is recommendation-shaped: name the placement, name the alignment status, name the gap, recommend a next step. End with a position, not a menu.
```
