### D74: Methodology aggregate shape, hash-chain content surface, repository interface, and CLI shape

Append to `charter/decisions.md`:

```
## D74: Methodology aggregate shape, hash-chain content surface, repository interface, and CLI shape

**Decision.** The methodology bounded context ships at S23 with the following architectural commitments.

**Aggregate shape.** Two frozen-dataclass aggregates following D31's revision-shape precedent. `MethodologyTemplate` carries the human-stable identity (id, name, description, created_by_user_id, created_at, archived_at). `MethodologyRevision` carries the per-revision content (methodology_template_id, version, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection, created_by_user_id, created_at) plus the hash-chain fields (previous_revision_hash, this_revision_hash). Revisions are immutable per D31; updates create new revision rows. Retirement marks the parent template's archived_at, leaving revisions intact for existing-clone-references per D68.

**Persistence shape.** JSONB columns for the structured fields. `source_ids` jsonb (array of UUID strings; typically empty for templates per D68); `tool_allowlist` jsonb (array of opaque strings; opaque per D68 with no registry at P7); `retrieval_strategy` jsonb (per D66's strategy-name-plus-params shape; e.g. `{"strategy": "vector_only", "params": {}}`); `filter_tree` jsonb (per D67's typed-Boolean-tree shape; defaults to the empty-tree sentinel). Scalar fields (top_k integer, min_score numeric, model_selection text, system_prompt text) as native columns. The JSONB-as-configuration pattern matches `scoring_sheet_criteria.levels` per D55 and avoids cross-context relational coupling between methodology and the retrieval/filter abstractions.

**Hash-chain content surface.** SHA-256 over canonical JSON of a payload comprising the revision content fields plus `previous_revision_hash` as a key inside the payload, mirroring the audit-chain pattern at `contexts/audit/domain/events.py:67-81` per D26. Canonical JSON: sorted keys, no whitespace separators (`json.dumps(payload, sort_keys=True, separators=(",", ":"))`), UTF-8 encoded. Numeric fields stored as Postgres `numeric` type round-trip through `Decimal` in SQLAlchemy; for canonical-JSON determinism plus operator-readable audit-dump form, the canonical encoder converts `Decimal` values via `format(value.normalize(), "f")`, which produces canonical fixed-point lexical form regardless of magnitude (e.g. `Decimal("0.50")` and `Decimal("0.5")` both serialise to `"0.5"`; `Decimal("100")` serialises to `"100"` rather than the `str(...)`-form `"1E+2"`). At S23, `min_score` is the only Decimal-shaped field; future Decimal fields (cost ceilings, retrieval-tuning numerics, percentage thresholds) inherit the same handling via the central encoder. The audit precedent at `contexts/audit/domain/events.py:67-81` does not exercise this path; the methodology context extends the precedent additively rather than diverging from it. The hash spans: name (denormalised onto the revision for chain-self-containment), description, system_prompt, source_ids (with internal sort), tool_allowlist (with internal sort), retrieval_strategy, filter_tree, top_k, min_score, model_selection, plus `previous_revision_hash` as the chain-binding key. The hash does not span: methodology_template_id, version, created_by_user_id, created_at, this_revision_hash. Reasoning: the chain-binding mechanism is inclusion of the previous hash inside the canonical-JSON payload, which is the audit precedent under D26. The chain structure that does not appear in the hash (template_id, version, timestamps, this_revision_hash itself) is what makes the chain queryable as relational data; the content fields plus the chain-binding previous hash are what the integrity check actually verifies.

**Repository interface.** `MethodologyRepositoryPort` Protocol with no `TenantContext` parameter on any method. Methodology data is control-plane-scoped per D33; mutation auth flows through the use case layer (operator-context enforcement) mirroring `register_tenant`/`update_tenant_status`/`reveal_connection_config` per D34. Methods: `create_template(template, initial_revision) -> MethodologyTemplate`, `get_template(template_id, version=None) -> tuple[MethodologyTemplate, MethodologyRevision]`, `list_templates() -> list[MethodologyTemplate]`, `add_revision(template_id, revision) -> MethodologyRevision`, `archive_template(template_id) -> MethodologyTemplate`. Tenant-context callers reading methodology templates do so without policy gating because templates are platform-managed and visible across tenants by design (the inverse of agent isolation per the P7 epic note).

**Operator-context enforcement at use case layer.** All five use cases inherit the operator-context pattern from D34. `create_methodology_template`, `update_methodology_template`, `retire_methodology_template` require operator-context and reject tenant-context callers including own-tenant callers. `get_methodology_template` and `list_methodology_templates` accept any authenticated context (operator or tenant) per the platform-managed-templates-visible-across-tenants principle. `AuthorizationError` from `padhanam/security/policy.py` raised on rejection, mirroring `reveal_connection_config`'s rejection path. Per pre-build review, the `OPERATOR_ROLE` constant and `is_operator` predicate currently at `contexts/tenancy/application/use_cases.py` promote to `padhanam/security/policy.py` at this session's commit 8 alongside the methodology use cases, with the tenancy use cases updated to import from the new location. The promotion treats operator-context as a platform-level security primitive consistent with where `AuthorizationError` and `check` already live; the alternatives (cross-context application-to-application import forbidden by D17's independence contracts; duplication fragmenting the predicate definition) were both worse on structural-honesty grounds.

**CLI shape.** Five commands at `padhanam methodology` namespace.
- `padhanam methodology create --config <path>` reads a YAML or JSON file containing the full template-plus-revision-1 payload (name, description, system_prompt, source_ids, tool_allowlist, retrieval_strategy, filter_tree, top_k, min_score, model_selection); produces a new template with revision 1; prints the new template_id and revision_id.
- `padhanam methodology get <template-id> [--version N] [--json]` retrieves the template plus the named or latest revision; default human-readable, --json for machine-readable.
- `padhanam methodology list [--json]` lists all non-archived templates.
- `padhanam methodology update <template-id> --config <path>` reads the same config shape minus the name (which is immutable per the template aggregate); produces a new revision; prints the new revision_id and version number.
- `padhanam methodology retire <template-id>` marks the template's archived_at; existing clones unaffected per D68.

The --config file shape is YAML or JSON (auto-detected by extension; .yaml/.yml or .json). The CLI parses, validates against the methodology config schema, and constructs the domain aggregate at the use case boundary. Operator-context resolution at `apps/cli/_runtime.py` mirrors the P5 dev-shape pattern: short label 'operator' resolves to the operator role; the production CLI tenant resolution carryover from P5 close applies symmetrically here for Phase 2.

**Alternatives considered.** Nine rejected alternatives weighed.

(a) Single methodology-template aggregate without revision split; rejected because D31's revision-shape precedent provides the immutable-content-with-evolving-versions discipline that audit posture requires.

(b) Normalised tables for retrieval_strategy and filter_tree (separate strategy-row, separate predicate-tree-rows); rejected because the configuration is consumed atomically per agent invocation and never queried at the field level; relational normalisation buys join cost without analytical benefit.

(c) Single config jsonb collapsing all structured fields into one column; rejected because separate jsonb columns preserve the architectural distinction between retrieval (D66 concern), filter (D67 concern), source attachment, and tool allowlist; the cleaner schema also supports future analytical queries without column-pruning the jsonb.

(d) MethodologyRepositoryPort with TenantContext parameter for read uniformity across contexts; rejected because methodology data is structurally control-plane-scoped and pretending otherwise creates the same architectural confusion the tenancy-context-without-tenant-context pattern would create. Read-side filtering by tenant happens at the agent context (tenant-scoped), not at the methodology context (platform-scoped).

(e) Hash-chain over the entire revision row including chain metadata; rejected because chain metadata is the chain structure itself; including it makes the hash non-deterministic against the canonical content shape.

(f) Hash-chain over the methodology template plus all revisions ever; rejected because that is the audit-chain pattern (event chain), not the revision-chain pattern; methodology revisions chain forward per template, mirroring the `scoring_sheet_revisions` per-sheet revision pattern.

(g) Tenant-admin role distinct from operator role for methodology mutations; rejected because at Phase 1 the operator-context-or-tenant-context distinction from D34 covers the platform-admin case; tenant-admin role lands when tenant-facing methodology authoring UI surfaces (Phase 2 per the P7 epic note's out-of-scope).

(h) CLI flag-per-field shape rather than --config-file shape; rejected because the field set has nine substantive fields including two structured (retrieval_strategy, filter_tree) and two list-shaped (source_ids, tool_allowlist); flag-per-field would produce 9-12 flags including file references for the structured fields and would lose the schema-validatable-at-parse-time property that --config gains.

(i) Leaving `OPERATOR_ROLE` and `is_operator` at `contexts/tenancy/application/use_cases.py` and importing cross-context from methodology; rejected because cross-context application-to-application imports violate D17's independence contracts and would require new import-linter exemptions; promoting to `padhanam/security/policy.py` is the structural-honesty resolution and lifts a primitive that was always platform-level to its proper home.

**Kano.** Performance. The aggregate shape and persistence choices preserve the architectural discipline (revision shape per D31, hash-chain per D26, control-plane scope per D33, operator-context auth per D34) that future packages consume; alternative shapes would force retrofit at S24 (agent context) or P8 (agent runtime). The CLI shape is delighter on operator ergonomics; the structural-honesty contribution sits at the architectural commitments above.
```

## Methodology templates (control plane)

|-----------------------|-----------------|------------------------------------------------|

|---------------------------|-----------------|------------------------------------------------|

| `retrieval_strategy`      | `jsonb`         | not null; strategy-name-plus-params shape per D66 |
| `filter_tree`             | `jsonb`         | not null; typed Boolean tree per D67           |
| `top_k`                   | `integer`       | not null                                       |
| `min_score`               | `numeric`       | not null                                       |
| `model_selection`         | `text`          | not null                                       |
| `created_by_user_id`      | `text`          | not null                                       |
| `created_at`              | `timestamptz`   | not null; default `now()`                      |
| `previous_revision_hash`  | `text`          | not null; genesis sentinel `"0" * 64` for the chain head |
| `this_revision_hash`      | `text`          | not null; SHA-256 of canonical JSON of content fields plus previous hash per D74 |

`UNIQUE(methodology_template_id, version)` —
`methodology_revisions_template_version_unique`. Revisions are immutable
per D31; updates create new revision rows. The hash-chain spans content
fields per D74's content surface specification; chain metadata
(template_id, version, timestamps, chain pointers) is excluded from the
