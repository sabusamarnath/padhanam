**Package:** P16 (Phase 2-A, the whole-life causal daily driver per D156)

**Mode:** build session. Deliverable: code commits + session-log entry, charter-first.
**Predecessors:** S60b (`LoginVerifier` port, `DevPassphraseLoginVerifier` wired, `GoogleLoginVerifier` seam that raises, `POST /api/v1/auth/login`, login page, app shell), the dogfood-setup chore (personal tenant `00000000-0000-4000-8000-00000000d001`).

---

## Why this session exists

S60b shipped the sign-in seam but only the passphrase path is wired; `GoogleLoginVerifier` raises. The operator has created a Google OAuth client and wants to sign in with the data-rich account `operator@example.com` and dogfood as that user. S60c wires the real Google OpenID Connect (OIDC) login behind the existing `LoginVerifier` port, maps the account to the personal tenant, and mints the JWT the data routes already expect. This is gate-enabling and is the first real provider of the identity foundation; Apple and Microsoft Entra are the parallel-package follow-ons and are out of scope here.

---

## Step 0 — Pre-write reconciliation (settled against live code)

1. **Port shape (decisive).** The S60b `GoogleLoginVerifier` seam assumed `credential` = a client-obtained Google ID token (one-tap/GIS). The operator's setup is a server-side authorization-code flow. Correction: reuse the port, reshape the credential — `verify(credential=<authorization code>)`; `GoogleLoginVerifier` becomes the real OIDC adapter. Initiate/callback are thin HTTP wrappers.
2. **JWT minting and session.** `issue_dev_token` (HS256) mints; the browser carries it as `localStorage['dd_token']` + `Authorization: Bearer`. The callback ends in an HTML bridge page writing the same `dd_token` key — byte-identical session at the data routes.
3. **Config.** New `GoogleOAuthSettings` in `padhanam/config/`; secret + operator email through gitignored `.env`.
4. **The login page.** Wire the "Continue with Google" button to the initiate route.
5. **The callback path.** `GET /api/v1/auth/google/callback`, same-origin on `http://localhost:8000`; operator sets it as the OAuth client redirect URI.
6. **Egress.** The personal stack reaches Google's token + certs endpoints; tests mock the tokens.
7. **D-index.** D161 free (D160 highest).

## Acceptance criteria

1. The "Sign in with Google" button starts the Google OIDC flow at the initiate route.
2. The callback verifies a valid Google ID token, resolves `operator@example.com` to the personal tenant, mints the JWT, lands authenticated, redirects to `/app`.
3. An unmapped email is rejected cleanly (no tenant fabricated, no session minted).
4. The data routes authorize with the Google-minted session exactly as with the passphrase-minted one.
5. Tests pass from cleared bytecode with Google calls mocked; import-linter and AST/enforcement green; no vendor SDK in domain code.
6. **Operator-gated live run:** sign in with `operator@example.com`, past the unverified-app warning, land in the app shell as the personal tenant. Recorded in the smoke.
