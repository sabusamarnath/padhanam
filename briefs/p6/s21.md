**`charter/decisions.md`** — append D63 and D64. Indicative text follows; build refines.

```
- **D63: Neo4j topology — shared instance with tenant-property scoping plus contract tests** (Package P6, Session S21, 2026-05-XX)
  - Choice: P6 ships a single Neo4j 5 Community instance shared across all
    tenants, with tenant isolation enforced at two layers: property-based
    scoping (every node and relationship carries a `tenant_id` property;
    every Cypher query the routing layer issues includes a
    `WHERE n.tenant_id = $tenant_id` predicate or relationship-property
    equivalent) and tenant-isolation contract tests in
    `tests/contract/tenant_isolation/` extending the harness from D24 to
    cover the graph store on both reads and writes. The Compose stack
    adds one `padhanam-neo4j` service (Neo4j 5 Community pinned per D10)
    with bolt and HTTP endpoints used by all tenants. The Neo4j Python
    async driver wraps bolt connections; the routing layer per-tenant
    context determines the property predicate added to every query.
    This is an explicit deviation from D32's per-instance Postgres
    posture, recorded with reasoning here.
  - Reasoning: Neo4j Community Edition does not support multiple
    databases the way Postgres instances do; the equivalent of D32's
    per-instance posture would require one Neo4j container per tenant,
    costing roughly 1GB RAM per tenant in local dev and scaling
    operational complexity linearly with tenant count. At Phase 1
    corpus sizes the isolation discipline is what matters and contract
    tests verify it; per-instance posture is procurement-credible but
    pays meaningful local-dev cost without yet earning back proportional
    security or operational benefit. Reversible if production deployment
    context surfaces a need to upgrade to per-tenant containers; the
    deferred-decisions entry "Per-tenant topology for Neo4j" stays in
    the file as the activation marker for that revisit.
  - Alternatives considered: Per-tenant Neo4j containers (rejected at
    Phase 1 scope: ~1GB RAM per tenant in local dev, linear operational
    complexity, no Phase 1 evidence that property-based isolation is
    insufficient; revisit at production-deployment context). Defer-again
    to production (rejected: pushes a decision that has to land
    somewhere onto a future session that may lack full context too;
    lands the call where the implementation forces it). Neo4j 5
    Enterprise multi-database (rejected: licensing cost, contradicts
    local-first principle, premature commitment to enterprise tier).
    Per-tenant labels (e.g. `:Entity_tenant_a`) instead of properties
    (rejected: label proliferation at high tenant counts, schema
    explosion is operational concern, property-based scoping is the
    more flexible posture).
  - Kano: must-have. The topology gates the Compose service shape, the
    routing layer's query construction, the migration approach for
    graph schema, and the tenant-isolation contract tests.
```

```
- **D64: Graph extraction shape — Qwen 2.5 7B via LiteLLM structured output, single :Entity node, free-form entity_type, no taxonomy commitment** (Package P6, Session S21, 2026-05-XX)
  - Choice: Graph extraction over parsed chunks reuses the inference
    default model (Qwen 2.5 7B per D15) via LiteLLM's function-calling
    or structured-output mode. A new `EntityExtractor` port at
    `contexts/ingestion/ports/entity_extractor.py` defines the contract
    `extract(chunks: Sequence[Chunk]) -> ExtractionResult`; the LiteLLM
    adapter calls the same gateway path the embedding and inference
    adapters use, with a prompt that yields
    `{entities: [...], relationships: [...]}` as JSON. The graph schema
    at S21 commits to a single `:Entity` node type with properties
    `tenant_id`, `jurisdiction`, `name`, `entity_type` (free-form
    string), `source_chunk_ids` (array), `created_at`. Relationships
    are typed Neo4j edges with properties `tenant_id`, `jurisdiction`,
    `source_chunk_id`, `created_at`; the relationship type itself comes
    from the extraction prompt. Entity uniqueness is keyed on
    `(tenant_id, name, entity_type)` for idempotent re-extraction via
    MERGE. Relationship uniqueness is keyed on (tenant_id, source_id,
    target_id, relationship_type, source_chunk_id). No commitment to a
    taxonomy of entity types or relationship types; the build session
    settles the small initial set the extraction prompt produces.
    Additional node types (e.g. `:Regulation`, `:System`, `:Verdict`)
    for future use cases explicitly do not land at S21; the architecture
    does not foreclose them, and the data-retrieval design session
    inherits the question of richer graph shapes and projection
    patterns.
  - Reasoning: Reusing Qwen 2.5 7B matches D15's single-default-model
    posture for inference, avoids new model dependencies on constrained
    dev hardware, and keeps the LiteLLM gateway as the single inference
    surface. LiteLLM's function-calling against Qwen 2.5 7B via Ollama
    produces reliable JSON without bespoke parsing. Single `:Entity`
    node type with free-form `entity_type` is the conservative shape:
    it ships extraction without committing to a taxonomy that might be
    wrong for the use cases the platform encounters; multi-node-type
    architectures are additive at the schema layer and not foreclosed.
    Reversible if eval surfaces extraction-quality problems with Qwen
    2.5 7B; the framing-prompt-as-recommendation pattern absorbs the
    refinement.
  - Alternatives considered: Specialised extraction model (GLiNER,
    REBEL) pulled into Ollama (rejected at this scope: new model
    dependency, smaller benefit for Phase 1 corpus sizes, revisit if
    eval surfaces gaps). Distinct LLM for extraction, different from
    chat default (rejected: D15's single-default-model posture is
    procurement-defensible and operationally simpler). Free-form
    prompting without function calling (rejected: bespoke JSON parsing
    is fragile, structured-output produces reliable JSON). Fixed
    entity-type enum (rejected: commits the architecture to a taxonomy
    that may not fit consumer use cases; defer the taxonomy choice
    until a real consumer drives it). Composite-key uniqueness with
    opaque `entity_id` (rejected: (tenant_id, name, entity_type) is
    human-readable for debugging and audit, supports MERGE directly).
  - Kano: must-have on the EntityExtractor port shape and the schema
    baseline; performance on the specific entity-type and relationship-
    type space the extraction prompt produces.
```

```
## Graph storage (Neo4j 5, shared instance, tenant-property scoping)

Lands at S21 per D63 and D64. Single Neo4j 5 Community instance
shared across all tenants. Tenant isolation enforced at the property
level on both nodes and relationships; every routing-layer query
includes a tenant predicate. Contract tests under
`tests/contract/tenant_isolation/` verify cross-tenant access fails.

### `:Entity` nodes

| Property | Type | Notes |
| --- | --- | --- |
| `tenant_id` | `String` | non-empty; constrained by tenant-isolation predicate |
| `jurisdiction` | `String` | first-class per D12 |
| `name` | `String` | extracted from chunks |
| `entity_type` | `String` | free-form; no taxonomy commitment per D64 |
| `source_chunk_ids` | `List<String>` | provenance back to chunks table |
| `created_at` | `DateTime` | |

Uniqueness: `(tenant_id, name, entity_type)`. Index per uniqueness.

### Relationships

Typed Neo4j edges (the relationship type comes from the extraction
prompt; no taxonomy commitment per D64). Properties:

| Property | Type | Notes |
| --- | --- | --- |
| `tenant_id` | `String` | non-empty; matches both endpoint nodes |
| `jurisdiction` | `String` | matches both endpoint nodes |
| `source_chunk_id` | `String` | provenance |
| `created_at` | `DateTime` | |

Uniqueness: (tenant_id, source_id, target_id, relationship_type,
source_chunk_id). MERGE on this composite key for idempotent
re-extraction.
```

## Acceptance criteria

1. `make up` brings up all existing services plus `padhanam-neo4j`; all healthy.
2. `make migrate` applies Postgres revision `0007_extend_state_enum` to both tenant databases idempotently and applies Neo4j migration `0001_base_constraints` to the shared graph instance idempotently.
3. `make lint` returns the expected import-linter contract count (existing 17 plus net additions from the new ports module if any); 0 broken.
4. `uv run pytest` returns greater than the S20 baseline (322 passed, 7 skipped) by the count of new tests added; existing tests untouched and passing.
5. End-to-end: `padhanam ingest run sample.md` against tenant a, then `make ingest-worker`; the source transitions through `parsed` to `embedded` to `indexed`; Neo4j contains `:Entity` nodes with `tenant_id = "tenant_a"`, `jurisdiction = "EU"`, non-empty names, free-form entity_types, and `source_chunk_ids` populated; relationships exist with consistent tenant scoping.
6. Tenant-isolation contract tests pass for both reads and writes against Neo4j.
7. The shared Neo4j instance contains zero `:Entity` nodes or relationships with empty or null `tenant_id`.
8. Worker reentrancy: stopping the worker mid-extraction (state in `extracting`) and restarting completes the source from scratch with no duplicated entities (MERGE deduplicates) and no orphaned relationships.
9. Worker idempotency: running the worker against an already-`indexed` source is a no-op.
10. Concurrency: the SKIP LOCKED concurrency test extends to cover the extraction stage; no double-extraction under concurrent worker simulation.
11. OTel traces from extraction requests appear in Langfuse with `tenant.id`, `tenant.jurisdiction`, and token-count attribution; cost-per-successful-task computation works against indexed sources, or the attribution gap is documented in reflection with a forward-affordance commitment.
12. Cypher queries from the routing layer all include a tenant-property predicate; verified by AST or pattern-test under `tests/_enforcement/`.
