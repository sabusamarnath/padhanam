# Session S19 — P6 source ingestion: bounded context, upload, parsing, worker, queue

Package P6 / Session S19. Build mode.

## Goal

At S19 close:

- A `contexts/ingestion/` bounded context exists with hexagonal layering per D16 and a new uv workspace member.
- Sources can be uploaded via CLI (`padhanam ingest run <file>`), validated against supported file types, written to per-tenant storage, and surfaced to a worker pool.
- A long-running worker (`padhanam ingest worker`) polls for pending sources via Postgres `SELECT ... FOR UPDATE SKIP LOCKED`, parses content from markdown and plain-text sources, writes chunks to a `chunks` table, and updates the source row's state through the parsing stage.
- Per-stage status (limited to the parsing stage at S19) drives reentrancy: re-running the worker against an already-parsed source is a no-op; re-running against a failed source reattempts.
- Tenant isolation extends to the new tables via the `tests/contract/tenant_isolation/` harness per D24.
- D61 records the parsing scope choice (markdown and plain text at P6 close; PDF, DOCX, HTML defer to sessions with real consumers) per the framing-prompt-as-recommendation pattern.
- The OTel TracerProvider initialisation pattern lifts to a shared helper at `padhanam/observability/init_tracing.py`. The ingestion worker is the fourth caller justifying the promotion threshold from S18 reflection.

## Pre-write reconciliation

Before any code lands, verify against current vendor docs and record any deltas in the S19 close session log reflection:

- Postgres 17 `SELECT ... FOR UPDATE SKIP LOCKED` semantics on the asyncpg + SQLAlchemy 2.0 async path. The syntax is stable since 9.5; verify the async driver delivers the locking guarantee and that row-level locks release on transaction commit.
- Markdown parsing library choice between `markdown` (CommonMark-conformant), `markdown-it-py` (faster, more extensible), and `mistune` (smallest dependency surface). Verify against PyPI for current stable version, pin to a digest-equivalent specific release, and choose based on heading-extraction cleanliness and dependency cost.
- typer's long-running command pattern for the worker loop, particularly graceful shutdown on SIGINT and SIGTERM, and partial-work commit semantics.
- Compose service shape for the worker: whether running as a separate `padhanam-ingestion-worker` service is the right shape or whether `make worker` running the same CLI command against the host environment is sufficient at S19 scale.

**`charter/decisions.md`** — append D61. Indicative text follows; build refines.

```
- **D61: Parsing scope at P6 close — markdown and plain text at S19; PDF, DOCX, HTML defer** (Package P6, Session S19, 2026-05-XX)
  - Choice: A `Parser` port at `contexts/ingestion/ports/parser.py` defines a single
    `parse(source: Source) -> ParsedContent` contract returning chunks plus structural
    metadata. Two adapters land at S19: `MarkdownParser` (using [chosen library
    pinned to vX.Y]) producing chunks split on heading boundaries with hierarchy
    preserved as metadata; `PlainTextParser` producing chunks split on
    paragraph boundaries (double-newline separators). Parser dispatch is by
    file extension. Unsupported formats produce a clear validation error at
    upload time, before the worker pulls the source. PDF, DOCX, and HTML defer
    to sessions with real consumers.
  - Reasoning: Markdown plus plain text is the smallest scope that exercises
    structure-aware chunking and the extension-dispatch seam meaningfully without
    committing to PDF parsing complexity at S19. PDF and DOCX add real dependency
    surface (pypdf, pdfplumber, python-docx) and structure extraction is non-trivial
    against either; landing them at S19 buys complexity ahead of consumer evidence.
    The parser-as-port shape commits the structural seam; format coverage extends
    incrementally as consumers arrive.
  - Alternatives considered: Markdown only at S19 (rejected: trivial without plain
    text, doesn't exercise extension dispatch); PDF at S19 (rejected: heavy dependency
    surface; structure extraction is non-trivial; defer until consumer evidence
    justifies); HTML at S19 (rejected: same reasoning; HTML ingestion overlaps
    with web-scraping concerns out of P6 scope); chunking by token count rather
    than structural boundaries (rejected: structure-aware chunking preserves
    semantic units that retrieval quality depends on; token-count chunking is a
    downstream refinement option for S20+).
  - Kano: must-have on the parser-as-port shape (gates every later parsing
    extension); performance on specific formats (markdown plus text is the floor;
    more formats are performance against richer corpus support).
```
