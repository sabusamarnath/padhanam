## Context-name call settled at the brief

The context name is `portfolio`, not `state_persistence`. Three reasons.

First, the karma prior-art domain language is portfolio-of-relationships per `docs/notes/prior-art-karma/spec.md`. Second, the Phase 2-A first case_type is PORTFOLIO_ITEM per the brief's own entity vocabulary, which is now charter-committed at `charter/architecture.md` Phase 2 domain vocabulary sub-section. Third, the four committed P11 contexts (`retrieval_evaluation`, `run_history`, `audit`, `optimization`) are all named by domain responsibility, not by infrastructural verb. `portfolio` is the symmetric choice.

The context name appears across two hundred plus references once committed (directory paths, import-linter contracts, CLI subcommand names, HTTP route prefixes, audit-event types, schema.md section headers, decision narratives). Settling at the brief avoids reconciliation-time renaming churn.

### Commit 2: Domain entities

```
feat(p13/s43): Case, DataPoint, Assertion domain entities
```

Add `contexts/portfolio/domain/case.py`, `data_point.py`, `assertion.py`. Frozen dataclasses per the existing convention (verified at pre-write reconciliation). Each entity carries:

- `Case`: id (UUID), tenant_id (UUID), title (str), case_type (str enum: PORTFOLIO_ITEM at Phase 2-A; substrate accepts other types), created_at, updated_at, status (str enum: OPEN, CLOSED, ARCHIVED).
- `DataPoint`: id (UUID), case_id (UUID), tenant_id (UUID), data_point_type (str enum: GOAL, STATUS, METHODOLOGY_APPLICATION at Phase 2-A; substrate accepts other types), value (JSON), authored_by (ActorReference; placeholder until S44 commits ActorContext), created_at, certainty (float between 0 and 1; default None pending tiered-by-salience implementation at P15).
- `Assertion`: id (UUID), data_point_id (UUID), tenant_id (UUID), assertion_type (str enum: INITIAL, REVISION), revises_assertion_id (UUID nullable; FK back to a prior Assertion if REVISION), value (JSON), authored_by (ActorReference), created_at.

Each entity uses `__post_init__` to enforce invariants (non-empty strings, type-enum membership, value-shape validation).

This commit also lands the new `layers-portfolio` import-linter contract plus the cross-context-independence contract extensions identified at pre-write reconciliation surface 6. The contract additions land at the same commit as the context skeleton per the S39 precedent (commit 3 at S39 landed the retrieval_evaluation context skeleton plus six import-linter contract updates in one commit).

### Commit 3: Revisable Protocol

```
feat(p13/s43): Revisable Protocol shape per D125
```

Add `padhanam/protocols/revisable.py` (path verifies at pre-write reconciliation). Define:

```python
class Revisable(Protocol):
    def revise(self, change: AssertionChange, actor: ActorReference) -> "Revisable":
        ...

    def revision_history(self) -> list[Assertion]:
        ...
```

The protocol contract: revisions append a new Assertion to the entity's revision history; the latest Assertion is the current state; prior Assertions are queryable. Implementations live at the entity level (DataPoint implements Revisable; Case may or may not implement Revisable per session-close decision).

`AssertionChange` lands as a value object in the same module or at `padhanam/protocols/types.py` per the reconciliation outcome at surface 4.

Unit tests cover the protocol contract: revising appends, history queries return ordered list, the latest assertion is the current state.

### Commit 5: Repository adapter

```
feat(p13/s43): Postgres repository adapter for portfolio context
```

Add `contexts/portfolio/adapters/postgres_portfolio.py`. Implement repository interface (defined at `contexts/portfolio/application/ports.py` or equivalent per convention). Methods:

- `save_case(case: Case) -> Case`
- `get_case(case_id: UUID, tenant_id: UUID) -> Case | None`
- `list_cases(tenant_id: UUID, case_type: str | None, status: str | None, cursor: str | None, page_size: int) -> CaseListResult` (cursor pagination per the canonical cursor codec at `charter/schema.md` cross-cutting binding shapes section).
- `save_data_point(data_point: DataPoint) -> DataPoint`
- `get_data_point(data_point_id: UUID, tenant_id: UUID) -> DataPoint | None`

- `save_assertion(assertion: Assertion) -> Assertion`
- `assertion_history(data_point_id: UUID, tenant_id: UUID) -> list[Assertion]` (ordered chronologically).

Tenant-isolation enforced at adapter level with bound-tenant defence-in-depth per the S31/S33/S39 precedent: every method requires tenant_id; cross-tenant queries return empty or None and emit a tenant-scope-violation security event per the existing convention.

### Commit 7: CLI subcommand

```
feat(p13/s43): padhanam portfolio CLI subcommand
```

Add `padhanam` CLI subcommand `portfolio` with action subcommands per the S41 `padhanam optimization` precedent. Actions at S43:

- `padhanam portfolio create-case --title="..." --case-type=PORTFOLIO_ITEM --status=OPEN` — invokes `create_case` use case; emits audit event; prints the new case_id.
- `padhanam portfolio create-data-point --case-id=... --data-point-type=GOAL --value='{...}'` — creates an initial DataPoint with an INITIAL Assertion.
- `padhanam portfolio revise-data-point --data-point-id=... --value='{...}'` — invokes `revise_data_point` use case; appends a REVISION Assertion.
- `padhanam portfolio list-cases [--case-type=...] [--status=...]` — invokes `list_cases` use case; prints the result.
- `padhanam portfolio get-case --case-id=...` — invokes `get_case_detail` use case; prints case plus data points plus latest assertions.

The CLI provides the smoke write path. Without it, criterion 12 (live-stack smoke end-to-end against the read surface) has no honest way to produce Cases to read short of raw SQL fixture seeding, which would bypass the audit-events port and structurally compromise the audit-trail discipline P3 established.

Wiring lands at the CLI composition root per the existing pattern (matching the S41 wiring shape that added optimization wiring as composition-root entries #15-#18).

Unit and integration tests cover the CLI surface; the integration test exercises the use case layer end-to-end with a fake repository.
