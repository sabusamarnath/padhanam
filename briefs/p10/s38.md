practice has now fired 16 times and surfaces structural drift
reliably; S38 is no exception.

1. **Existing ingestion context shape.** The brief assumes
   HTTP routes consume existing application use cases at
   `contexts/ingestion/application/` directly. The P9 epic
   committed to this approach. Confirm at reconciliation
   that the use cases return shapes compatible with HTTP DTO
   construction (specifically: list/get/status semantics
   exist or can be assembled from existing primitives without
   refactoring the ingestion context). If the existing use
   cases do not fit the HTTP shape, surface the gap as a
   structural finding rather than silently adapt. The fallback
   shape is a consumer-defined `IngestionReader` port mirroring
   `AuditEventReader` from S36; that fallback adds a port to
   the ingestion context and is not free. Surface before
   choosing.

2. **Auth error handler current registration.** Confirm at
   reconciliation: where exactly does
   `PrincipalTypeMismatchError` register today? The S37 work
   placed it inside `register_audit_error_handlers` per finding
   4 resolution. The relocation moves it to a new
   `register_auth_error_handlers` module. Identify every wire-
   point that needs updating: the registration call in
   `register_audit_error_handlers`, the composition root that
   invokes the registration functions, any tests that assert
   handler registration. Surface the full move surface before
   commit 2 lands.

3. **HTTP-route precedent across run_history.py and audit.py.**
   The third HTTP router after run_history and audit. Confirm
   the pattern's stability: DTO module naming, query parser
   module naming, error handler registration, dependency
   injection shape, security event firing inside route bodies
   rather than handlers. The pattern is now well-rehearsed;
   reconciliation confirms it has not drifted.

The ingestion management API surface holds to the framing
minimum: three read endpoints. Upload-over-HTTP and reindex

pull either in.

**Reasoning.** Three reasoning lines converge on this shape.

The auth error handler relocation activates at the threshold
named in the S37 deferred-decisions entry: a second router
raises `PrincipalTypeMismatchError` via the shared
`get_tenant_context` chokepoint. Ingestion at S38 is that
second router. Continuing to register the handler inside the
audit module forces each new router that uses the shared
dependency to either copy the registration or import from
audit; both are worse than a clean cross-cutting module. The
relocation cost is bounded (move one registration, update one
import path, wire one new call at composition root); the
deferral cost grows with each new router. The trigger fired
as scheduled.

The ingestion management API reuses existing application
use cases directly because the framing committed to this
approach at the P9 epic and because the use cases already
exist with shapes suited to read-side HTTP. Adding a
consumer-defined `IngestionReader` port mirroring the
audit-reader pattern adds incidental scope at S38 without
clear architectural value when the existing use cases fit.

fallback to a port lands only if shape mismatch surfaces.
The decision is deliberately reversible: if a future
session needs UX-shaped query semantics that the
application use cases cannot provide, a consumer-defined
port lands then.

The three-route minimum holds because no UI consumer has
materialised that needs upload-over-HTTP or reindex. The
P6 carryover's activation condition resolved to P10 under
D93, and Phase 1 close is substrate-only. Phase 2 UX
extends the surface when real consumer needs arrive.

ingestion router or imports from audit, both inferior to
a clean cross-cutting module.

(b) Add `PrincipalTypeMismatchError` handler to both
audit and ingestion modules without consolidating.
Rejected as duplication that grows linearly with new
routers.

(c) Introduce a consumer-defined `IngestionReader` port
at S38 mirroring the audit-reader pattern from S36.
Rejected on incidental-scope grounds when the existing
application use cases fit; reversible at any future
session that surfaces a real shape mismatch.

(d) Ship upload-over-HTTP at S38 in anticipation of
Phase 2 UX needs. Rejected on YAGNI: no consumer has
materialised; CLI upload covers the operator workflow
through Phase 1 close.

(e) Ship reindex-over-HTTP at S38. Rejected for the same

(f) Defer the ingestion management API to Phase 2

already considered and rejected this deferral.

**Kano.** Must-have on the auth error handler relocation

### Commit 4: ingestion HTTP routes

```
feat(p10/s38): HTTP routes for ingestion management
```

New module: `apps/api/routers/ingestion.py`. Three routes:

- `GET /ingestion/sources`: paginated list of sources for
  the tenant. Depends on `get_tenant_context`. Returns 200
  with `SourceListPageDTO` on success; 400 for malformed
  cursor or page_size out of range; 401 unauthenticated; 403
  on platform-operator token; 404 on tenant-not-in-registry;
  503 on registry-not-configured.

- `GET /ingestion/sources/{source_id}`: single source lookup
  for the tenant. Depends on `get_tenant_context`. Returns
  200 with `SourceDTO`; 404 for not-found in tenant scope or
  for cross-tenant attempts via fabricated source_id (the
  isolation contract is the same shape as audit's 404 on
  cross-tenant `get_audit_event`).

- `GET /ingestion/sources/{source_id}/status`: ingestion
  pipeline status for a specific source. Depends on
  `get_tenant_context`. Returns 200 with `SourceStatusDTO`;
  404 for source-not-found.

Each route invokes the existing ingestion application use
cases directly. Use case selection settles at reconciliation
once the use-case surface is confirmed.

`register_ingestion_error_handlers(app: FastAPI)` registers
audit-specific error classes: `SourceNotFoundError` if it
exists at the ingestion context, otherwise a new typed error
landed inside the ingestion application layer at S38.
Reconciliation surfaces which.

### Finding 1: ingestion application use-case shape (structural; user-resolved)

Brief assumption: HTTP routes consume existing
`contexts/ingestion/application/` use cases directly without
introducing a consumer-defined port. Reconciliation against
the application layer and the existing
`SourceRepositoryPort` surfaced the structural gap: the
`get_source` use case exists and fits `GET /ingestion/sources/
{source_id}` cleanly; the status route derives trivially from
`Source.state` + the three error-text fields on the
aggregate; but `list_sources` does NOT exist as either a use
case OR a port method. The fallback shape named in the brief
(consumer-defined `IngestionReader` port mirroring
`AuditEventReader` from S36) is one path; an alternative is
to extend the existing write-side port with a `list_sources`
method and add a `list_sources` application use case.

Two paths surfaced to the operator before any code landed:
(A) Extend the existing `SourceRepositoryPort` with
`list_sources` + add `list_sources` application use case.
HTTP route calls the application use case directly. Cheapest;
consistent with ingestion's own existing
read/write-co-located port pattern; diverges from the audit
S36 pattern at the HTTP boundary. (B) Stand up `IngestionReader`
port at `contexts/ingestion/ports/reader.py` mirroring
`AuditEventReader` exactly. Heavier; cleaner separation;
reinforces the consumer-port-plus-wiring-adapter methodology
candidate.

User-resolved: Path A. The duplication concern named in the
resolution captures the architectural reasoning: `IngestionReader`
and `SourceRepositoryPort` would both need `get_source`, creating
either real duplication across two ports or requiring a refactor
of `SourceRepositoryPort` that touches existing application
consumers with unbounded surface. D104 alternative (c) updated
accordingly; D104 reasoning gains a fourth paragraph naming
Path A explicitly. Commit 3 subject expands to
`feat(p10/s38): list_sources use case + SourceRepositoryPort
extension + HTTP DTOs/query parser`.
