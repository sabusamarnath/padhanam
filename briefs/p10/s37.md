## Substantive work (commits 2 onward)

### Commit 2: auth model extension

```
feat(p10/s37): platform-operator principal type on D23 signed-token backend
```

Extends the D23 signed-token backend to carry `principal_type`
as a discriminator field on the claim payload. The token
schema gains:

- `principal_type: "tenant" | "platform_operator"` (required)
- `tenant_id` becomes conditionally required: required when
  `principal_type == "tenant"`, prohibited when
  `principal_type == "platform_operator"`. Validation at
  token-decode time raises a structured error on violation.

Existing token-issuance paths default to `principal_type:
"tenant"` for backwards compatibility with all existing test
fixtures and dev flows. The dev-backend token-mint helper
gains a new mode to issue platform-operator tokens for tests
and dev usage.

New dependency function at the auth layer:
`get_platform_operator_principal(token: Token) ->
PlatformOperatorPrincipal`. Returns a control-plane scope
marker. Rejects tenant-typed tokens with HTTP 403. Rejects
unsigned or expired tokens with HTTP 401 (delegated to the
existing token-verification chokepoint).

The existing `get_tenant_context` dependency extends with a
discriminator check at entry: tenant-typed tokens flow
through unchanged; platform-operator-typed tokens raise HTTP
403.

### Commit 3: audit HTTP routes

```
feat(p10/s37): HTTP routes for audit reader on both destinations
```

New module: `apps/api/routers/audit.py`. Four routes:

- `GET /audit/events/{event_id}`: per-tenant single-event
  lookup.
- `GET /audit/events`: per-tenant paginated list.
- `GET /platform/audit/events/{event_id}`: control-plane
  single-event lookup.
- `GET /platform/audit/events`: control-plane paginated list.

Query-string vocabulary for both list routes mirrors the S36
seven-filter port surface (`timestamp_range_start`,
`timestamp_range_end`, `actor`, `action_verb`,
`resource_type`, `resource_id`, `correlation_id`,
`jurisdiction`) plus `cursor` and `page_size`.

## Appendix D — Pre-write reconciliation outcomes

Pre-write reconciliation fired its fifteenth instance at
S37 session-open. Four findings surfaced, four resolutions
captured via user-question.

**Finding 1 — Existing `Principal.roles` field contradicts
D103 alternative (b) framing.** The auth module at
[padhanam/security/auth.py](../../padhanam/security/auth.py)
carries `Principal.roles: frozenset[str]` populated from the
token's `roles` claim. The codebase already uses this for
operator gating at
[apps/api/routers/tenant_audit.py:91](../../apps/api/routers/tenant_audit.py#L91)
via `OPERATOR_ROLE not in principal.roles`. The brief's D103
alternative (b) "Role-list claim" framed role-list as a
hypothetical Phase 2 future, but role-list is already
production code. Surfaced as a user-question; resolved to
**revise D103 alternative (b)** to acknowledge the existing
roles field and frame `principal_type` as structurally
complementary (the discriminator anchors `tenant_id`'s
conditional validity at token-decode time, which roles
cannot do cleanly because `tenant_id` is required at decode
time today). The discriminator choice itself stands as
drafted. D103's reasoning section also revised to add a
fifth reasoning line on the complementarity claim.

**Finding 2 — DTO module naming.** Brief drafted
`apps/api/routers/audit_dtos.py` (no underscore prefix,
plural). Precedent at run-history is
`apps/api/routers/_run_history_dto.py` (underscore-prefixed
private, singular). Surfaced as a user-question; resolved to
**match precedent**: `_audit_dto.py` and sibling
`_audit_query.py` for the query-string parser. Mechanical
absorption.

**Finding 3 — Dev-mint helper for platform-operator
tokens: with or without `OPERATOR_ROLE` in `roles`?**
Two conceptually distinct categories: `OPERATOR_ROLE` gates
tenant-scoped operator actions (tenant_audit endpoint at
S12, registry mutations at S10); platform-operator-typed
principals have no tenant scope and read the control-plane
chain. Surfaced as a user-question; resolved to **omit
`OPERATOR_ROLE` by default**. Tests that want both
semantics mint a tenant-typed token with `OPERATOR_ROLE`
plus a platform-operator-typed token, exercising the two
surfaces separately. Charter D103 absorbs this as
alternative (j).

**Finding 4 — Error handler registration shape.** Brief
implied a new audit error handler set; question was whether
to extend `register_run_history_error_handlers` in place or
land a parallel `register_audit_error_handlers`. Surfaced
as a user-question; resolved to **parallel function** at
`apps/api/_errors.py` alongside the existing one. The
composition root calls both. Mirrors the additive pattern;
preserves the option to refactor to a generic
`register_error_handlers` at a future cleanup moment.
Charter D103 absorbs this as alternative (i).

**Mechanical absorptions (no user-question):**

- Error handler module location: brief draft `apps/api/errors.py`
  → actual `apps/api/_errors.py` (S34 landed underscore prefix).
- "Eleven-path error response": brief language refers to
  verification scenarios in tests, not eleven error codes. The
  D98 handler today has 5 error codes (`malformed_cursor`,
  `invalid_filter_range`, `run_not_found`, `internal_error`,
  `validation_error`); S37 adds a sixth (`principal_type_mismatch`).
- Auth tests live at `tests/unit/padhanam/security/` not
  `tests/unit/apps/api/auth/` (the auth module lives at
  `padhanam/security/auth.py`).
- `AuditQueryRoutingError` already exists at the S36 port; HTTP
  layer translates to 400 per the port docstring's commitment.

Find-rate distribution at S37 session-open: one structural
finding (finding 1, charter-framing revision under
user-question resolution) plus three mechanical findings
(findings 2, 3, 4, all user-question resolved to recommended
options) plus four mechanical absorptions. Substrate-shaping
altitude at session-open continues to surface structural drift
the brief's prose-review pass cannot catch (finding 1 is the
load-bearing one for charter accuracy; findings 2-4 are smaller
shape questions whose answers feed commit 2 onward).
