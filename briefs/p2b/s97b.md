**Commit 2 — the composer.**
The daily check-in composer fires on `DAILY_SCHEDULED` (riding the existing FireTrigger idempotency — one fired_triggers row per tenant+user+day), queries the eligible daily-cadence homeostatic levers, sends the compact-list-plus-free-reply message to the operator's joined WhatsApp address, and creates the PENDING (`target_cell='checkin'`, stage `awaiting_report`, `proposed_intent` carrying the scheduled `beat_date` and the eligible levers). `feat(p2b/s97b): daily check-in composer + pending creation`

**Commit 3 — the parse.**
The parse use case loads the eligible levers (names + ids), passes them to `litellm_extractor` in JSON-mode, and returns only the levers the reply spoke to, each tagged `did` or `reported_didnt`. The use case (not the pure domain function) assembles the lever context, per D184. An unmentioned lever is absent from the output. Transitions the pending to `awaiting_confirm` with `proposed_action_summary` echoing the parsed write declaratively.
`feat(p2b/s97b): check-in reply parse + confirm transition`

**Commit 4 — the write-on-confirm.**
On the confirm reply (active-pending routes to the cell, resolves the pending), the write splits: a `did` inserts one `commitment_completions` row with `completed_at` stamped to the scheduled beat day; a `reported_didnt` inserts one `commitment_checkin_responses` row with `beat_date` = scheduled day and `outcome='reported_didnt'`; silence writes neither. Idempotent on `(tenant, commitment, beat day)` — a re-confirm or duplicate does not double-write. A correcting reply resolves the pending as cancelled.
`feat(p2b/s97b): three-state write-on-confirm, idempotent by beat day`
