- FastAPI exception handlers at the same module catching `MalformedCursorError` → 400, filter-validation errors (started_at_after > started_at_before, page_size bounds) → 400, the reader's bound-tenant-id rejection → 500 with security event (this is a defence-in-depth failure that should never fire in production; firing means a bug above the data layer). Pydantic 422 errors wrap to the project body shape via a `RequestValidationError` handler if such wrapping does not already exist.

Documented in D98 alternatives (a) — rejected option of rejecting requests where cursor is present alongside filter params, on grounds that detecting "filter changed" requires encoding filters into the cursor and increasing cursor size beyond opacity. ## Appendix A — D98 text (draft for commit 1)

### D98 — HTTP routes for run-history reader

**Context.** S33 landed `RunHistoryReader` plus its Postgres adapter plus composition-root wiring. The reader is inert from a UI consumer perspective until an HTTP transport surfaces it. P9 epic commits Phase 2 UX as the downstream consumer; HTTP is the layer that turns the reader from internal substrate to consumable surface.

**Decision.** Four shapes commit at S34:

1. **Response DTO shape.** Pydantic response models mirror `RunRecord`, `ChunkCitationRecord`, `EntityCitationRecord` 1:1. No flattening. Citation tuples surface as nested arrays per Pydantic v2's tuple-to-list serialisation. `source_snapshot` JSONB surfaces as `dict[str, Any]`. The storage-versus-render discipline from D96 holds at the HTTP boundary; rendering decisions defer to Phase 2 UX.

2. **Query parameter vocabulary.** Six query params for `GET /runs`: `agent_template_id` (repeated, maps to `tuple[UUID, ...] | None`); `agent_template_version` (repeated, `tuple[int, ...] | None`); `started_at_after` and `started_at_before` (paired, `tuple[datetime, datetime] | None` when both provided in correct order); `termination_reason` (repeated, `tuple[str, ...] | None`); `cursor` (opaque base64 string); `page_size` (int, 1 to 50). Empty repeated params map to `None` (no-filter), not empty tuple.

3. **Error response body shape and eleven-path map.** Body carries `error_code`, `message`, `correlation_id`, optional `details`. Eleven paths: bad UUID path param (422); bad query param type (422); page_size out of bounds (422 via FastAPI ge/le); malformed cursor (400, code `malformed_cursor`); started_at_after greater than started_at_before (400, `invalid_filter_range`); missing auth (401); cross-tenant attempt on `GET /runs/{id}` (404, fires `tenant_scope_violation` security event); missing run (404, no security event); unexpected exception or DB timeout (500, `internal_error`); method not allowed (405, FastAPI default); cross-tenant `GET /runs` (empty list, no error, no security event).

4. **Principal-derived tenant context.** Per S29b precedent at `apps/api/routers/agent.py`. Principal extracted from auth middleware; `TenantContext` constructed from principal; reader called with bound tenant_id. Reader's existing defence-in-depth handles cross-tenant attempts at the data layer; route layer enforces at the principal layer.

**Reasoning.** The four shapes hang on three load-bearing arguments. First, response-DTO-as-1:1-mirror preserves the storage-versus-render discipline that landed at D96 — the HTTP layer is a transport, not a rendering layer. Second, the eleven-path error map covers every distinguishable failure mode at the route boundary; consolidation (e.g., collapsing the three 400s onto a single code) would lose client diagnosability. Third, principal-derived tenant context inherits the S29b precedent rather than introducing a new auth pattern; the cross-tenant 404 firing a security event is the privacy-preserving-plus-auditable shape the principles already commit to.

**Alternatives considered.** (a) Reject requests where cursor is present alongside filter params; rejected because detecting "filter changed since cursor was issued" requires encoding filters into the cursor, increasing cursor size and breaking opacity. (b) Flatten citation tuples into a single discriminated citation list at the response shape; rejected per storage-versus-render symmetry with D96. (c) Surface JSONB `source_snapshot` as a Pydantic-typed `SourceSnapshot` model; rejected because the snapshot keys are intentionally schemaless per D96 to accommodate ingestion enrichment evolution. (d) Return 403 on cross-tenant `GET /runs/{id}`; rejected because confirming "this run exists but you don't have access" leaks existence; 404 is the privacy-preserving choice. (e) Fire security events on every list-no-results to maximise audit fidelity; rejected because list-no-results is structurally indistinguishable from genuine no-results, producing noise in the security log. (f) Use `tuple[X, ...]` directly in Pydantic response models with custom serialisers; rejected because Pydantic v2's default tuple-to-list serialisation is the standard JSON shape and consumers expect arrays. (g) Inline cursor encoding inside the HTTP layer rather than reusing the codec; rejected because S33's codec is the established opacity boundary and duplicating logic at the HTTP layer would create drift. (h) Use FastAPI's `BackgroundTasks` to defer security event firing off the request path; rejected because tenant-scope violations are operationally urgent and should fire synchronously. (i) Skip correlation_id in the error body if middleware doesn't already exist; rejected because forensic correlation across logs and security events requires the ID and the middleware addition is one commit. (j) Return cursor and page_size in the `RunListResponse` body even when they didn't change; rejected because the cursor is opaque and clients only need `next_cursor` for forward pagination at Phase 1.

**Kano.** Must-have on response DTO shape (without it the routes are unusable); must-have on principal-derived tenant context (without it the routes are insecure); performance on the eleven-path error map (a smaller map would work but degrades client diagnosability); performance on the query parameter vocabulary (a smaller vocabulary would work but degrades filter expressivity for Phase 2 UX); delighter on the correlation_id-in-error-body shape (operational forensics improvement beyond functional requirement).
