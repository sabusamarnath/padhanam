## Appendix A — D99 text

### D99 — Two-tier integration test strategy: default tier and live-LLM tier

**Context.** Top-ten slow integration tests at S35 close run ~695 seconds combined per the durations probe captured at `docs/notes/integration-test-slowness-investigation.md`. The cost is in test bodies executing real LLM inference via LiteLLM against `qwen2.5:7b` plus embedding models against Ollama, not in fixture overhead. Module-scope fixtures are correctly applied; engine.dispose patterns honour module scope. The investigation determined the fix shape is policy, not architecture: separating the tiers preserves test fidelity while restoring fast iteration cycles.

**Decision.** Integration tests exercising real LLM inference carry `@pytest.mark.live_llm`. The marker is registered in `pyproject.toml` under `[tool.pytest.ini_options].markers`. Default pytest collection excludes the marker via `addopts = "-m 'not live_llm'"` in the same section. A new Makefile target `make test-live-llm` (and the equivalent `uv run pytest -m live_llm`) runs the live tier explicitly. Operator runs the live tier at per-package close, weekly cadence, or per pre-PR validation; the default tier runs every session-hygiene iteration.

**Reasoning.** Real-LLM tests verify the inference integration end-to-end; mocking them defeats their purpose. The cost is intentional and load-bearing on what the tests assert. Tier separation pays the cost when fidelity is needed (per-package close, pre-PR) and defers it when iteration speed matters (session hygiene). The investigation note examined four alternatives and recommended this shape.

**Alternatives considered.** (a) Full mocking of LLM calls; rejected because the tests' value is real-LLM behaviour. (b) pytest-xdist parallelism with per-worker LLM queues; rejected because parallelism does not reduce total cost and adds Ollama-concurrency configuration complexity. (c) Shared-corpus rewrite for retrieval tests; rejected because it requires test-body changes for only partial coverage. (d) Accept the slowness; rejected because session hygiene becomes unworkable at 11-minute test runtimes. (e) Per-test mock-vs-real toggle; rejected as introducing brittle conditional behaviour.

**Kano.** Performance. The platform works without this but iteration speed materially improves with it.

## Appendix B — D100 text

### D100 — CLI settings flow through composition root, not fresh from environment per command

**Context.** Eleven methodology/tool CLI tests fail at S35a session-open because the test fixture's `CONTROL_PLANE_HOST_OVERRIDE=127.0.0.1` does not propagate to CLI commands invoked via `typer.testing.CliRunner`. Each command currently constructs `ControlPlaneSettings()` fresh from the environment; the fixture override applies only to the fixture's own cleanup repo. The pattern surfaces a deeper architectural asymmetry: `apps/api` constructs composition objects at startup and threads them through dependency injection, while `apps/cli` constructs settings per command at the consumer. The asymmetry was invisible until the test fixture surface forced it.

**Decision.** CLI commands consume settings (and any other shared cross-command state) from the composition root, not from fresh construction per command. The CLI entry point at `apps/cli/__main__.py` (or the resolved equivalent) constructs `ControlPlaneSettings` once at typer-app initialisation, attaches it to a typer Context (`ctx.obj`), and commands consume from context. CliRunner-driven tests override at the entry point level via environment-variable injection through `CliRunner(env={...})` or via Context object substitution.

**Reasoning.** The pattern matches the `apps/api` composition-root discipline that S29b through S34 reinforced. Architectural symmetry between the two composition roots was implicit before D100; D100 makes it explicit. The benefit is structural: any future shared state (settings, observability handles, tenant-registry clients) follows the same threading discipline; tests stop being blocked by env-var-propagation gaps; the principle that "Secrets are read through `padhanam/config/` exclusively" is honoured at the right architectural layer.

**Alternatives considered.** (a) Environment monkeypatch in the fixture; rejected per the operator's "comprehensive solution, not a patch" framing. The patch resolves the symptom but leaves the apps/api-vs-apps/cli asymmetry in place. (b) Wrap CliRunner with a settings-aware proxy; rejected as test-only abstraction that masks rather than fixes the source-level issue. (c) Move settings construction to module-level globals; rejected as worsening testability and contradicting the no-`os.getenv` principle. (d) Use environment variables exclusively (no override mechanism); rejected because integration tests legitimately need to override against the loopback Postgres rather than the docker-internal hostname.

**Kano.** Performance. The platform works without this but ongoing test friction and the architectural asymmetry compound.
