## Appendix D — pre-write reconciliation findings (preserved at session close)

Five surfaces walked at session-open per the brief's reconciliation protocol; one further structural finding surfaced mid-commit-3. Outcomes:

**Surface 1 — exact identity of failing tests.** Brief's stated distribution absorbed mechanically: two TRUNCATE-without-CASCADE (`test_two_concurrent_workers_no_double_processing_full_pipeline`, `test_full_role_aware_clone_and_edit_flow_against_live_stack`); two psql-missing (`test_search_against_empty_tenant_returns_no_results[a]`, `[b]`); two streaming-isolation (`test_streaming_endpoint_threads_correct_tenant_per_bearer_token`, `test_streaming_endpoint_unauthenticated_rejected_before_executor`). No drift.

**Surface 2 — methodology fixture pattern transferability.** Structural drift caught. The methodology fixture at `test_methodology_isolation.py` uses SQLAlchemy from host loopback against the control-plane Postgres (the D5 exception's 127.0.0.1:5433 binding). Per D5, the per-tenant Postgres containers (postgres-tenant-a, postgres-tenant-b) carry no host-port bindings by design — only Caddy:443 binds; control-plane is the explicit exception. SQLAlchemy-from-host cannot reach the tenant DBs. The brief's "mirror the methodology fixture pattern" instruction was right in spirit (use the codebase's existing test-infrastructure pattern) but wrong in specifics (the methodology fixture's mechanics don't transfer). User-question protocol fired; operator selected option 1 (in-tenant-container psql, matching `test_concurrent_workers.py::_exec_psql_tenant_a` and `test_create_from_methodology_flow.py::_exec_psql_tenant`) as the structurally honest substitute. No new D-entry required; the pattern is established codebase convention. Option 2 (extend D5 with a new D102 to add loopback bindings for tenant DBs) was rejected on three counts: it inverts D5's deliberate restriction, introduces an architectural D-entry just to enable a test fixture, and touches infrastructure config when a test-only fix touches only test fixtures.

**Surface 3 — streaming-isolation diagnostic.** Failure shape is `AgentRuntimeComposition.__init__() missing 1 required positional argument: 'run_history_writer'`. Not the brief's named alternatives (empty-tables / FK-TRUNCATE) and not a real isolation gap. Pure test-scaffolding staleness, identical class to the S35 carryover fix on `test_agent_sse_endpoint.py::_runtime_with_script`. The test pre-dated S31's addition of `run_history_writer` to `AgentRuntimeComposition`. User-question protocol fired; operator selected fold-in. Fix at commit 4: add a `_NullRunHistoryWriter` to `_build_app` with a no-op `record_run`. No isolation logic touched.

**Surface 4 — FK shape on chunks-to-run_chunk_citations.** Confirmed `run_chunk_citations.chunk_id REFERENCES chunks(id) ON DELETE SET NULL` per migration `0011_create_run_history`. The TRUNCATE+CASCADE fix at commit 2 used explicit-table-list shape (`TRUNCATE TABLE chunks, sources, run_chunk_citations`) per the brief's recommendation, not the CASCADE keyword. The production ORM-deletion path (chunks deleted via repository, SET NULL fires on the citation rows) is unaffected because TRUNCATE bypasses FK-action triggers; the ORM path uses DELETE statements that go through the FK action.

**Surface 5 — tenant data state at session-open.** Tenants a and b populated as expected (D101 wipe-guard from S35a is doing its job). Search returned 5 results pre-fix, confirming the "pass-because-empty-when-empty, fail-when-populated" failure mode the carryover entry described.

**Mid-commit-3 finding — deliberate-violation cycle exposed primary isolation mechanism.** The brief named a deliberate-violation cycle as the test-correctness verification step: introduce a code change that breaks isolation, run the contract test, observe failure, revert. Executed against `contexts/ingestion/adapters/outbound/retrieval/pgvector_search.py` by removing the `s.tenant_id = :tenant_id AND c.tenant_id = :tenant_id` predicate from the search SQL. After rebuild + force-recreate of padhanam-api, the contract test still PASSED. Structural finding: D32's per-database topology is the *primary* isolation mechanism; the SQL predicate is defense-in-depth within each per-tenant DB. Each tenant's search runs against its own Postgres instance (postgres-tenant-a vs postgres-tenant-b), which only contains its own data; removing the in-DB predicate cannot cause cross-tenant leakage at this contract surface because no cross-tenant data exists in either DB. The contract test catches *catastrophic* failures (resolver mis-routing routing tenant_b's CLI to tenant_a's DB; seed-into-wrong-DB; predicate-removal-with-shared-data) but cannot catch in-DB-predicate-only failures by design of the per-tenant topology. This is meaningful methodology signal worth surfacing at the Phase 1 close audit: the deliberate-violation cycle's value depends on whether the test's architectural assumption matches the system's actual isolation mechanism. For per-tenant-DB contracts the cycle exposes the architectural assumption; the contract test is honest about user-visible behaviour but cannot fully verify every component of the isolation stack.
