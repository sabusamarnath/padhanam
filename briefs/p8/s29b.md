## Appendix A. D90 exact text

**D90: Streaming runtime architecture — structured event vocabulary at domain layer, streaming as only executor pathway, nested OTel span hierarchy with simple audit, transport-neutral runtime with SSE adapter (P8 framing, S29b, 2026-05-12)**

**Choice.** The agent runtime exposes its full state machine to consumers via eleven structured event types living at the domain layer (`contexts/agent/domain/events.py`): `InvocationStarted`, `IterationStarted`, `LLMCallStarted`, `ContentDelta`, `ToolCallProposed`, `ToolCallExecuting`, `ToolCallCompleted`, `IterationCompleted`, `InvocationCompleted`, `InvocationFailed`, `InvariantBlocked`. The `AgentExecutor` Protocol becomes streaming-only: `invoke(...)` returns `AsyncIterator[AgentEvent]`. Non-streaming callers wrap the stream via a `collect_to_result` helper at the application layer that synthesises `AgentResult` from a terminal `InvocationCompleted` event.

Inference port gains `stream_completion(...)` returning `AsyncIterator[CompletionChunk]` where chunks carry text delta, accumulated tool calls, and a final cost on the terminal chunk. The LiteLLM adapter implements with vendor isolation preserved per D4.

OTel span hierarchy nests four levels: `agent.invocation` (parent), `agent.iteration` (per-loop children), `gen_ai.llm_call` and `agent.tool_call` (grandchildren under iterations). Cost attributes roll up across the hierarchy; D49's attribute schema extends to iteration and tool-call levels; D57's two-layer cost-query abstraction continues to work across the new hierarchy.

Audit stays at two rows per invocation regardless of termination reason (start at `InvocationStarted`; end at one of `InvocationCompleted`, `InvocationFailed`, `InvariantBlocked`). The asymmetry between fine-grained traces and simple audit is deliberate: traces answer operational questions ("what can we learn about this agent's performance"); audit answers compliance questions ("what happened, can we prove it"). Different resolution needs.

The SSE transport lives in `apps/api/` as an adapter that translates domain events to SSE wire format. The runtime stays transport-neutral; later transport additions (WebSocket, gRPC) touch only the adapter layer, not the runtime.

**Reasoning.** The four sub-choices that compose D90:

Sub-choice 1 (structured events at the maximum granularity with content deltas for animation) commits the substrate that makes the runtime observable to consumers in product form. The bet's "observability as foundation" principle commits this; raw token streaming alone collapses the runtime to "an LLM with extra steps" from the consumer's perspective. The gallery pre-population content at Phase 2 demos against these events.

Sub-choice 2 Option C (nested traces, simple audit) reflects the asymmetric resolution needs of operational and compliance data. Per-iteration audit would multiply audit volume by up to 10x per invocation without adding compliance value; per-iteration traces give the P11 recommendation engine the iteration-granularity substrate it needs.

Sub-choice 3 Option A (streaming as only path) collapses the runtime to one set of behaviours. Non-streaming callers wrap; the runtime stays one thing.

Sub-choice 4 Option A (events at domain layer) keeps the runtime transport-neutral per the no-vendor-SDKs-in-domain-code standing rule and the LiteLLM isolation precedent.

The consumer-port-plus-wiring-adapter pattern receives its fourth reinforcement at the SSE transport boundary, consistent with S26a-1 (MethodologyLookup), S26a-2 (RoleLookup), S27b (AgentRetrievalClient + MethodologyOverridesLookup), S28b (ToolDefinitionsLookup + ToolInvoker). The pattern earns continued methodology-promotion-candidate status for the Phase 1 close audit.

**Alternatives considered.** (a) Raw LLM token streaming only, no structured events; rejected because it collapses the runtime to a chatbot from the consumer's perspective and removes the substrate the gallery demo needs. (b) Flat OTel span with events for state changes instead of nested hierarchy; rejected because it constrains P11's queryable surface to invocation-level data, removing the iteration-granularity recommendations the engine needs. (c) Two executor pathways (separate streaming and non-streaming methods); rejected because it duplicates the runtime and creates two implementations that must stay in sync; the wrap-via-collect-to-result helper is simpler. (d) Event types at transport layer (`apps/api/`) rather than domain layer; rejected because it couples the runtime to SSE and contradicts the no-vendor-in-domain-code rule; transport-neutral runtime is the Phase 1 norm. (e) Per-iteration audit alongside per-iteration spans (sub-choice 2 Option B); rejected because audit volume increases without compliance value, and traces and audit have legitimately different resolution needs. (f) Streaming as opt-in via a `stream=True` parameter on a unified method; rejected because it makes streaming a feature toggle rather than the runtime's natural shape; the collapse to streaming-only is cleaner.

**Kano.** Must-have on the structured event vocabulary, the streaming-only executor, and the transport-neutral domain placement (these together are what the bet's "observability as foundation" principle commits in code at Phase 1 close, and what the S30b CLI and Phase 2 consumer-grade UX consume). Performance on the nested span hierarchy (the P11 recommendation engine consumes; iteration-granularity recommendations are the differentiator the recommendation surface ships). Delighter on the asymmetric trace-versus-audit resolution (Option C); it costs nothing extra but produces a cleaner separation between operational and compliance data than either extreme would.
