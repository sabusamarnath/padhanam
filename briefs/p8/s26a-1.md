### Commit 2: `feat(p8/s26a): add Role aggregate to methodology context`

Add the role aggregate within `contexts/methodology/`:

- `application/ports/role_repository.py`: `RoleRepositoryPort` Protocol. Methods: `create_template`, `get_template`, `list_templates`, `add_revision`, `archive_template`. - `application/use_cases.py`: extend with `create_role_template`, `get_role_template`, `list_role_templates`, `update_role_template`, `retire_role_template`. Mirror methodology use case patterns.
- `adapters/outbound/postgres/role_repository.py`: `PostgresRoleRepository` implementing the port. Resolves connection through the control-plane settings per D34.

Tests: unit tests for each use case; hash-chain integrity test; auth contract test (operator-context required for writes).

### Commit 3: `feat(p8/s26a): refactor methodology_revisions to use role_refs`

Alembic revision `0011_methodology_role_refs` against the control-plane track:

1. Adds `role_refs jsonb NOT NULL DEFAULT '[]'::jsonb` to `methodology_revisions`.
2. For each existing methodology revision row: read the constraint bundle fields; INSERT a new `role_templates` row (named "{methodology_name}Role" or per a deterministic naming function; can be renamed later); INSERT a new `role_revisions` row with version 1 carrying the constraint bundle; UPDATE the methodology revision's `role_refs` to `[{"role_id": <new_role_uuid>, "role_version": 1, "overrides": null}]`.
3. DROPs constraint bundle columns from `methodology_revisions`.

Down-migration: re-adds columns, reads back from role aggregate via role_refs, drops role rows. Acceptable that down-migration is lossy if methodology has multiple role_refs (Phase 1 has only single-role methodologies; the down-migration's failure mode is explicit data loss for multi-role methodologies, which would only arise post-S26b).

Domain changes:

- `MethodologyRevision` frozen dataclass loses constraint bundle fields; gains `role_refs: tuple[RoleRef, ...]`.
- `RoleRef` frozen dataclass at `contexts/methodology/domain/methodology.py`: `role_id: UUID`, `role_version: int`, `overrides: Mapping[str, Any] | None`.
- Hash-chain content surface updates: `role_refs` (sorted by role_id for determinism) spans the methodology hash; constraint bundle no longer spans methodology hash (moves to role hash).

Use case changes:

- `create_methodology_template` signature accepts `role_refs: list[RoleRef]` (validates each role_id resolves to an existing role).
- `update_methodology_template` accepts new `role_refs`.
- `get_methodology_template` returns the new shape.
- `MethodologyView` DTO (D79's cross-context type at `contexts/agent/application/ports/`) updates: includes resolved role data (the role's content fields after applying methodology's overrides). The agent context's adapter at `apps/cli/_runtime.py` does the resolution, calling the role context's use case to fetch the role and applying overrides client-side. Resolution logic lives in the adapter, not in the use case.

Tests: hash-chain integrity after refactor; methodology revisions immutable; role_refs resolve to actual roles; methodology with non-existent role_id fails fast at use case boundary.
