## Goal

At S28b close, the platform's tool surface generalises beyond retrieval-as-only-callable. A `contexts/tools/` bounded context holds `Tool` and `ToolRevision` aggregates with hash-chain audit per D26, a six-category classification taxonomy with three classifications mapped to D82 invariants 1–3 at the invocation boundary, backward-compatibility checking at revision creation via schema diff, and a CLI surface for `padhanam tool create | get | list` that rejects Phase 1 authoring of classifications financial, communication, and legal per D89's prohibition. The `AgentLoopExecutor`'s hardcoded retrieval branch retires; the executor consumes two thin ports (`ToolDefinitionsLookup` and `ToolInvoker`) at the agent context, with wiring adapters at `apps/cli/_cross_context.py` calling the tools context's facade. Retrieval becomes a tool registered in the tool registry like any other tool. A defensive invariant check at invocation returns a structured error path via new `TerminationReason.INVARIANT_BLOCKED`. The BC stub produces a result stored as metadata on the revision and surfaces via a query on `ToolRepository` listing role-tool bindings with per-binding adoption-candidate status.

## Appendix A. D89 exact text

**D89: Tool registry aggregate, classification-to-invariant mapping, two-thin-ports replacement of retrieval branch, backward-compatibility stub at revision creation, Phase 1 authoring prohibition on high-classification tools (P8 framing, S28b, 2026-05-12)**

**Choice.** Tools land as a new bounded context at `contexts/tools/` per D68 and the P8 epic line. Tool and ToolRevision aggregates carry hash-chain audit per D26 and revision shape per D31. Classification taxonomy: six categories (read-only, drafting, user-affecting-with-consent, financial, communication, legal). Classification-to-invariant mapping at the invocation boundary: financial fires invariant 1 (per-transaction authorization); communication fires invariant 2 (per-invocation authorization, outbound); legal fires invariant 3 (explicit user action). Invariants 4 and 5 are not enforced at the tool registry: invariant 4 is structural (D26 append-only audit, D31 revision immutability); invariant 5 enforces at tool configuration time per D14.

The agent loop's view of tools at the agent context lands as two thin ports: `ToolDefinitionsLookup` (returns the tools available to a given agent, filtered by role allowlist and Phase 1 classification policy, formatted for the LLM) and `ToolInvoker` (executes a tool call, applies defensive invariant check, returns structured result). Both ports live at `contexts/agent/application/ports/`. The wiring adapters at `apps/cli/_cross_context.py` implement the ports by calling into the tools context. The hardcoded retrieval branch in `AgentLoopExecutor` retires; retrieval becomes a tool registered in the tool registry, invoked through `ToolInvoker` like any other tool.

Backward-compatibility testing at tool revision creation: a schema-diff stub compares input and output schemas of revision Rn versus Rn+1, produces a BC result (passed if schemas identical or strict supersets; failed otherwise) stored as metadata on the new revision. The result drives the "which roles can adopt the revision" signal via a query surface on `ToolRepository`. The query exists at S28b; the consumer-grade adoption UX defers to Phase 2.

Phase 1 authoring prohibition: tools of classification financial, communication, or legal cannot be authored at Phase 1. The CLI rejects with an error naming the per-invocation confirmation pathway deferred-decisions entry. The prohibition lifts when the confirmation pathway lands.

Defensive invariant enforcement at invocation: if a high-classification tool call somehow reaches the loop (defensive against future bugs or filter bypass), the `ToolInvoker` returns a structured error and the loop terminates with new `TerminationReason.INVARIANT_BLOCKED`.

Three new deferred-decisions entries land alongside D89: per-invocation confirmation pathway shape; rich BC testing; automated adoption flow on BC pass. Activation triggers per the deferred-decisions file.

**Reasoning.** The classification-to-invariant mapping is mechanical: three classifications map cleanly to three invariants per D82's consent-granularity-proportionate-to-danger principle. The remaining three classifications govern via standing consent at tool configuration per D14. Two thin ports rather than one fat registry port: pattern reinforcement of split-by-concern from S26a-1 (MethodologyLookup), S26a-2 (RoleLookup), S27b (AgentRetrievalClient + MethodologyOverridesLookup). Third reinforcement establishes Phase 1 norm. The agent loop's read-shape concern (what tools are available) and action-shape concern (invoke this) have different evolution velocities; collapsing them couples the loop's stability to registry concept evolution. BC stub at revision creation: substrate in code, sophistication deferred to consumer-evidence-driven session. Phase 1 authoring prohibition on high classifications: keeps configure-versus-run surfaces coherent; the alternative (allow authoring with silent runtime invisibility) is the worst UX shape because it accepts what cannot execute.

**Alternatives considered.** (a) One fat `ToolRegistry` port at agent context exposing lookup + invocation + classification rules + invariant policy; rejected because it couples the loop to registry concept evolution and contradicts split-by-concern reinforced at S26a-1, S26a-2, S27b. (b) Defensive-check-only at invocation without filtering at definitions lookup; rejected because exposing high-classification tools to the LLM (even with defensive blocking) means the LLM proposes calls that always fail, wasting tokens and producing user-confusing error responses. (c) Build the confirmation pathway at S28b; rejected because no Phase 1 consumer surfaces the need, the design choice (hand-off vs pause vs queue) requires consumer evidence, premature commitment risks wrong-shape substrate. (d) Allow Phase 1 authoring of high-classification tools with silent runtime filter; rejected because it produces configure-versus-run dissonance and is the worst UX shape. (e) Rich BC testing at S28b; rejected because the schema-diff stub produces a useful Phase 1 signal and the sophistication is better designed against the first false-result evidence. (f) Tool revision pinning at agent invocation time (latest revision wins); rejected because it produces silent drift on tool evolution and contradicts D88's independent-clones spirit; pin happens at role authoring time per commit 4. (g) Classification on the role allowlist rather than the tool revision; rejected because classification is a property of what the tool does, not what role uses it; tool authors set classification at the tool, allowlists reference tools.

**Kano.** Must-have on tool aggregate, classification taxonomy, invariant mapping at invocation boundary, two-thin-ports replacement. These are what the bet's intelligence-layer commitment is held by in code at Phase 1 close. Performance on the BC test mechanism (the differentiator for revision propagation; consumer evidence at Phase 2 refines the surface). Delighter on the two-thin-ports pattern's third reinforcement (Phase 1 norm established).
